# Microsoft Azure checklist

Copy this list into a pull request, design review or project kickoff and tick what applies.
Rules are grouped by level and sorted by score ([criteria](../RANKING.md)). Each links to the file that explains it and cites its sources.
*Automatable* names tools that can check the rule in CI (see the file's "How to enforce" section).

Also apply the [general checklist](general.md).

This file is generated by `python3 scripts/rank.py fix` from the guidelines. Don't edit it by hand.

## Recommended (6–8)

- [ ] `AZURE-1` (8) Deploy workloads into an Azure landing zone: put platform services such as management, connectivity and identity in their own subscriptions, and give each workload environment its own subscriptions. ([specific/azure](../specific/azure/README.md))
- [ ] `AZURE-5` (8) Authenticate workloads with managed identities, and pipelines and workloads outside Azure with workload identity federation, instead of client secrets, certificates or access keys. ([specific/azure](../specific/azure/README.md)) *Automatable: Azure Policy, Microsoft cloud security benchmark initiative, Checkov Terraform policies, PSRule for Azure rules.*
- [ ] `AZURE-7` (8) Assign Azure RBAC roles to groups rather than users, at the narrowest scope, keep at most three subscription owners, and give administrators just-in-time access with Privileged Identity Management. ([specific/azure](../specific/azure/README.md))
- [ ] `AZURE-9` (8) Deploy production workloads across availability zones in regions that have them, and prefer zone-redundant service configurations. ([specific/azure](../specific/azure/README.md)) *Automatable: Azure Policy, Microsoft cloud security benchmark initiative, Checkov Terraform policies, PSRule for Azure rules.*
- [ ] `AZURE-10` (8) Define all Azure resources as code in Bicep or Terraform, deploy them from a pipeline, and build on Azure Verified Modules. ([specific/azure](../specific/azure/README.md))
- [ ] `AZURE-2` (7) Agree on a naming convention and a set of required tags, such as application, environment and cost center, before you deploy, and enforce the tags with Azure Policy. ([specific/azure](../specific/azure/README.md)) *Automatable: Azure Policy, Microsoft cloud security benchmark initiative, PSRule for Azure rules.*
- [ ] `AZURE-3` (7) Set guardrails with Azure Policy: prefer built-in policies and initiatives, assign them at the highest suitable scope, and roll out each new assignment in audit mode before you switch it to deny. ([specific/azure](../specific/azure/README.md))
- [ ] `AZURE-6` (7) Use one Key Vault per application, environment and region, authorize access with Azure RBAC rather than legacy access policies, and turn on purge protection. ([specific/azure](../specific/azure/README.md)) *Automatable: Azure Policy, Microsoft cloud security benchmark initiative, Checkov Terraform policies, PSRule for Azure rules.*
- [ ] `AZURE-8` (7) Reach PaaS data services, such as Storage, SQL Database and Key Vault, through private endpoints, and block public traffic with the service firewall or turn public network access off. ([specific/azure](../specific/azure/README.md)) *Automatable: Azure Policy, Microsoft cloud security benchmark initiative, Checkov Terraform policies, PSRule for Azure rules.*
- [ ] `AZURE-11` (7) In Bicep, mark secret parameters and outputs with `@secure()`, don't give secure parameters default values, and read secrets from Key Vault with `getSecret()` or the `existing` keyword instead of passing them through outputs. ([specific/azure](../specific/azure/README.md)) *Automatable: Bicep linter, PSRule for Azure rules.*
- [ ] `AZURE-12` (7) Route resource logs to a central Log Analytics workspace with diagnostic settings, deployed at scale with Azure Policy, and start with a single workspace. ([specific/azure](../specific/azure/README.md)) *Automatable: Azure Policy, Microsoft cloud security benchmark initiative.*
- [ ] `AZURE-13` (7) Create a budget with actual and forecasted cost alerts for every subscription. ([specific/azure](../specific/azure/README.md))
- [ ] `AZURE-4` (6) Keep the management group hierarchy flat, ideally three or four levels, and group subscriptions by workload type, such as corp and online, not by environment or org chart. ([specific/azure](../specific/azure/README.md))
- [ ] `AZURE-14` (6) Assess each workload with the Azure Well-Architected Review, and act on Azure Advisor recommendations, which Advisor scores by pillar. ([specific/azure](../specific/azure/README.md))
