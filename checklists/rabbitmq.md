# RabbitMQ checklist

Copy this list into a pull request, design review or project kickoff and tick what applies.
Rules are grouped by level and sorted by score ([criteria](../RANKING.md)). Each links to the file that explains it and cites its sources.
*Automatable* names tools that can check the rule in CI (see the file's "How to enforce" section).

Also apply the [general checklist](general.md).

This file is generated by `python3 scripts/rank.py fix` from the guidelines. Don't edit it by hand.

## Strongly recommended (9–10)

- [ ] `RABBITMQ-1` (9) Declare queues whose messages must survive the loss of a node as quorum queues, and make `quorum` the default queue type of the virtual host. ([specific/rabbitmq](../specific/rabbitmq/README.md))
- [ ] `RABBITMQ-2` (9) Publish with publisher confirms, and consume with manual acknowledgements, acknowledging each message only after it has been processed. ([specific/rabbitmq](../specific/rabbitmq/README.md))
- [ ] `RABBITMQ-11` (9) Delete the default `guest` user, disable anonymous logins, and give each application its own user with only the permissions it needs. ([specific/rabbitmq](../specific/rabbitmq/README.md))

## Recommended (6–8)

- [ ] `RABBITMQ-3` (8) Make consumers idempotent: the same message can arrive twice, after a redelivery or when a publisher resends a message whose confirm it didn't receive. ([specific/rabbitmq](../specific/rabbitmq/README.md))
- [ ] `RABBITMQ-5` (8) Handle poison messages with the quorum queue delivery limit and a dead-letter exchange: keep the limit on (20 by default since RabbitMQ 4.0), and dead-letter messages that exceed it to a queue that someone monitors. ([specific/rabbitmq](../specific/rabbitmq/README.md)) *Automatable: Operator policies.*
- [ ] `RABBITMQ-12` (8) Use TLS for client connections with peer verification, and secure inter-node and CLI traffic too. ([specific/rabbitmq](../specific/rabbitmq/README.md)) *Automatable: `rabbitmq-diagnostics check_certificate_expiration`.*
- [ ] `RABBITMQ-4` (7) Don't let unroutable messages disappear: publish with the `mandatory` flag and handle returned messages, or give the exchange an alternate exchange. ([specific/rabbitmq](../specific/rabbitmq/README.md)) *Automatable: RabbitMQ Prometheus alerting rules.*
- [ ] `RABBITMQ-6` (7) Give every consumer a bounded prefetch, starting between 100 and 300, and tune it by measurement. ([specific/rabbitmq](../specific/rabbitmq/README.md))
- [ ] `RABBITMQ-8` (7) Keep connections long-lived, use separate connections for publishing and consuming, and give each thread its own channel. ([specific/rabbitmq](../specific/rabbitmq/README.md)) *Automatable: RabbitMQ Prometheus alerting rules.*
- [ ] `RABBITMQ-9` (7) Keep queues short: run enough consumers to keep up, cap queue length with a policy, and use a stream instead of a queue for large backlogs, replay or large fan-outs. ([specific/rabbitmq](../specific/rabbitmq/README.md)) *Automatable: Operator policies.*
- [ ] `RABBITMQ-10` (7) Configure dead-lettering, TTLs, length limits and delivery limits through policies, not through `x-` arguments hard-coded in applications. ([specific/rabbitmq](../specific/rabbitmq/README.md))
- [ ] `RABBITMQ-13` (7) Monitor with the built-in Prometheus plugin, and alert on queue depth, unacknowledged messages, consumer counts, connection churn and resource alarms. ([specific/rabbitmq](../specific/rabbitmq/README.md)) *Automatable: RabbitMQ Prometheus alerting rules.*
- [ ] `RABBITMQ-14` (7) Stay on a release series that still has community support, and upgrade along the supported rolling upgrade paths, with all stable feature flags enabled first. ([specific/rabbitmq](../specific/rabbitmq/README.md))
- [ ] `RABBITMQ-7` (6) Retry transient failures with the quorum queue's delayed retry (RabbitMQ 4.3 and later) instead of requeueing at once or building dead-letter cycles with TTLs. ([specific/rabbitmq](../specific/rabbitmq/README.md))
