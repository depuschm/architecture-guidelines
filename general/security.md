# Security

Design security in from the start rather than adding it at the end. Handling personal data lawfully, from collection to deletion, is in [Privacy and personal data](privacy.md), and sign-in in [Authentication and sessions](authentication.md).

> Entries are sorted by score from 1 to 10 ([criteria](../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Adopted references

- `10` [OWASP Application Security Verification Standard (ASVS)](https://asvs.owasp.org/): **our security requirements checklist** for applications.
- `9` [OWASP Top 10](https://top10.owasp.org/): the most critical web application risks. Use it for awareness, not as a complete checklist.
- `9` [OWASP Cheat Sheet Series](https://cheatsheetseries.owasp.org/): concise, practical guidance per topic.
- `8` [NIST Secure Software Development Framework (SP 800-218)](https://csrc.nist.gov/pubs/sp/800/218/final): practices for a secure development lifecycle.
- `7` [OWASP Secure Product Design Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Product_Design_Cheat_Sheet.html): secure design principles at the architecture level.
- `7` [CISA Secure by Design](https://www.cisa.gov/securebydesign): principles for shipping products that are secure by default.
- `7` [NCSC secure design principles](https://www.ncsc.gov.uk/collection/cyber-security-design-principles) (UK National Cyber Security Centre).

## Key rules

- `10` `SEC-1` **Deny by default, enforce least privilege, and check authorisation server-side on every request.** ([OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html))
- `10` `SEC-2` **Keep secrets out of code and repositories.** Store them in a secrets manager, scope access tightly, and rotate them. ([OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html))
- `9` `SEC-3` **Threat model early and revisit it as the design changes.** Ask: what are we working on, what can go wrong, what are we going to do about it, and did we do a good enough job? ([Threat Modeling Manifesto](https://www.threatmodelingmanifesto.org/), [OWASP Threat Modeling Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html))
- `9` `SEC-10` **Validate all input that crosses a trust boundary on the server, against a schema or an allowlist, before using it, and never deserialize untrusted data with a mechanism that can create arbitrary objects or run code.** Client-side checks can be bypassed and only give users quick feedback. Platform examples: `NODE-3`, `PY-7`, `PY-14`, `TS-8`, `NEXTJS-1`, `SVELTE-11` and `GODOT-13`. ([OWASP Input Validation Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html), [OWASP Deserialization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html))
- `9` `SEC-11` **Treat everything you ship to a client as public, including browser bundles, page payloads, mobile apps and game builds, and never build secrets into it.** Front-end frameworks mark which values reach the browser: see `NEXTJS-2`, `VUE-14` and `SVELTE-12`. ([OWASP ASVS 5.0, V13 Configuration](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x22-V13-Configuration.md), [OWASP Mobile Top 10, M1 Improper Credential Usage](https://owasp.github.io/www-project-mobile-top-10/2023-risks/m1-improper-credential-usage))
- `9` `SEC-12` **Never keep one user's or one request's data in state that a server process shares between requests, such as module-level variables or singletons: scope it to the request, or keep it in a backing service.** Otherwise data leaks between users, for example in server-side rendering (`SVELTE-5`, `VUE-6`) or in reused serverless instances (`HOST-4`). ([MITRE, CWE-488: Exposure of Data Element to Wrong Session](https://cwe.mitre.org/data/definitions/488.html), [Twelve-Factor App, VI Processes](https://12factor.net/processes))
- `8` `SEC-4` **Log security-relevant events, and keep secrets and sensitive personal data out of logs by removing, masking, hashing or encrypting them.** ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html))
- `8` `SEC-5` **Give each application and service its own identity, with only the permissions it needs, on every system it connects to, and never let it use a shared, default or administrator account.** The platform files name each system's mechanism, for example `PG-13`, `KAFKA-14`, `RABBITMQ-11`, `REDIS-11`, `K8S-8` and `GCP-5`. ([OWASP Microservices Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Microservices_Security_Cheat_Sheet.html), [OWASP ASVS 5.0, V13 Configuration](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x22-V13-Configuration.md))
- `8` `SEC-6` **Ship secure defaults so customers don't have to harden the product themselves.** ([CISA Secure by Design](https://www.cisa.gov/securebydesign))
- `8` `SEC-13` **Encrypt every network connection with TLS, including internal connections to databases, caches, message brokers and telemetry collectors, and make clients verify the server's certificate.** Being inside your network isn't a reason to trust a connection (`SEC-7`). Platform examples: `PG-14`, `RABBITMQ-12`, `REDIS-11`, `KAFKA-14` and `OTEL-10`. ([OWASP ASVS 5.0, V12 Secure Communication](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x21-V12-Secure-Communication.md), [NIST SP 800-207, Zero Trust Architecture](https://csrc.nist.gov/pubs/sp/800/207/final))
- `8` `SEC-14` **Authenticate workloads and pipelines with short-lived credentials issued for their identity, such as cloud managed identities or OpenID Connect workload identity federation, instead of long-lived keys or stored secrets.** Platform examples: `AWS-1`, `AZURE-5`, `GCP-4`, `GHA-5`, `GITLAB-3` and `TF-2`. ([OWASP Top 10 CI/CD Security Risks, CICD-SEC-6](https://owasp.github.io/www-project-top-10-ci-cd-security-risks/CICD-SEC-06-Insufficient-Credential-Hygiene), [OWASP ASVS 5.0, V13 Configuration](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x22-V13-Configuration.md))
- `8` `SEC-15` **Pin every dependency, including packages, base images, CI actions and infrastructure modules, to an immutable version, such as a lock file with hashes, an image digest or a commit SHA, install exactly what is pinned, and let a bot propose updates.** Version tags can be moved to point to different code. Platform examples: `NODE-4`, `PY-2`, `DOCKER-3`, `K8S-5`, `GHA-2`, `GITLAB-1` and `TF-10`. ([OWASP Software Supply Chain Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Software_Supply_Chain_Security_Cheat_Sheet.html), [OpenSSF Scorecard, Pinned-Dependencies](https://github.com/ossf/scorecard/blob/main/docs/checks.md#pinned-dependencies))
- `8` `SEC-16` **Separate production from non-production, and workloads from each other, with their own accounts or projects, credentials and data stores.** Platform examples: `AWS-2`, `AZURE-1`, `GCP-1`, `HOST-9` and `TF-5`. ([NIST SP 800-218, Secure Software Development Framework](https://csrc.nist.gov/pubs/sp/800/218/final), [OWASP Top 10 CI/CD Security Risks, CICD-SEC-6](https://owasp.github.io/www-project-top-10-ci-cd-security-risks/CICD-SEC-06-Insufficient-Credential-Hygiene))
- `8` `SEC-17` **Run only releases of runtimes, frameworks, databases and other platform software that still receive security fixes, apply their patch releases promptly, and plan each upgrade before the end-of-life date.** Platform examples: `NODE-5`, `PY-1`, `PG-16`, `RABBITMQ-14` and `MOBGAME-5`. ([OWASP Top 10:2025, A03 Software Supply Chain Failures](https://top10.owasp.org/2025/A03_2025-Software_Supply_Chain_Failures/), [NCSC, Obsolete products](https://www.ncsc.gov.uk/collection/device-security-guidance/managing-deployed-devices/obsolete-products))
- `7` `SEC-7` **Don't grant implicit trust based on network location. Authenticate and authorise every access (zero trust).** ([NIST SP 800-207, Zero Trust Architecture](https://csrc.nist.gov/pubs/sp/800/207/final))
- `7` `SEC-8` **Protect the software supply chain with build provenance and continuous dependency health checks.** ([SLSA](https://slsa.dev/), [OpenSSF Scorecard](https://scorecard.dev/))
- `6` `SEC-9` **Use STRIDE to enumerate threats per component, data flow and trust boundary.** ([Microsoft, Threat Modeling Tool threats (STRIDE)](https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-threats), [OWASP Threat Modeling Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Threat_Modeling_Cheat_Sheet.html))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [GitHub secret scanning push protection](https://docs.github.com/en/code-security/concepts/secret-security/push-protection): blocks pushes that contain hardcoded credentials before they reach the repository. Checks `SEC-2`.
- `6` [Gitleaks](https://github.com/gitleaks/gitleaks): detects passwords, API keys and tokens in git repositories and files, as a pre-commit hook or GitHub Action. Checks `SEC-2`.
- `6` [OpenSSF Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md): run as a GitHub Action; they score dependency-update tooling, known vulnerabilities, and signed releases with SLSA provenance. Partly checks `SEC-8`.
- `6` [Dependabot alerts](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts) and [version updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-version-updates): alert on vulnerable dependencies and keep them up to date. Partly checks `SEC-8`.
- `6` [GitHub artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations): signed build provenance for your artifacts, verifiable with `gh attestation verify`. Partly checks `SEC-8`.
- `6` [CodeQL, clear-text logging of sensitive data](https://codeql.github.com/codeql-query-help/python/py-clear-text-logging-sensitive-data/) ([JavaScript](https://codeql.github.com/codeql-query-help/javascript/js-clear-text-logging/)): code-scanning queries that flag sensitive data written to logs. Partly checks `SEC-4`.
