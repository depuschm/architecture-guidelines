# Astro

Scope: content-driven websites and web apps built with Astro, following the current (Astro 7) documentation: static and on-demand rendering, client and server islands, content collections, actions, middleware and sessions. UI framework components inside islands follow their own guidelines, such as [React](../react/README.md), [Vue](../vue/README.md) and [Svelte](../svelte/README.md). Framework-independent rules for accessibility, performance and security, such as WCAG, Core Web Vitals, sanitizing HTML before `set:html` (`WEB-8`) and security headers, are in [Web front end](../web/README.md), and deployment to Vercel, Netlify and Cloudflare is in [Serverless and edge hosting](../web-hosting/README.md). Actions, endpoints and middleware are backend code, so the [Node.js](../nodejs/README.md) and [Security](../../general/security.md) guidelines also apply to them.

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Adopted references

- `10` [Astro Docs](https://docs.astro.build/en/getting-started/): **the baseline.** Project structure, components, routing, on-demand rendering, server islands, actions, middleware, sessions, content collections, images, environment variables, view transitions, testing and the configuration reference.
- `8` [Islands architecture](https://docs.astro.build/en/concepts/islands/) (Astro Docs): the core concept: static HTML by default, client islands that ship JavaScript only for interactive components, and server islands for dynamic or personalized parts of a page.
- `8` [On-demand rendering](https://docs.astro.build/en/guides/on-demand-rendering/) (Astro Docs): adapters, prerendering by default, opting routes out of prerendering, `'server'` output, HTML streaming, cookies and responses.
- `8` [Content collections](https://docs.astro.build/en/guides/content-collections/) (Astro Docs): build-time and live collections, loaders, Zod schemas, references between collections, querying and generating routes from content.
- `7` [Actions](https://docs.astro.build/en/guides/actions/) (Astro Docs): type-safe backend functions with input validation, errors, form actions, and security for actions.
- `7` [Using environment variables](https://docs.astro.build/en/guides/environment-variables/) (Astro Docs): Vite's `PUBLIC_` prefix and the type-safe `astro:env` schema with client, server and secret variables.
- `7` [Upgrade to Astro v7](https://docs.astro.build/en/guides/upgrade-to/v7/) (Astro Docs): the breaking changes in Astro 7, such as Vite 8, the Rust compiler, stable route caching and the new Markdown processor, with an upgrade command.

## Key rules

### Rendering and islands

- `7` `ASTRO-1` **Keep Astro's default static output, and render a route on demand with `export const prerender = false` only when it needs request data, such as cookies or a session. Switch to `output: 'server'` only when most pages are rendered on demand.** Prerendered pages need no server function to render. ([Astro, Enabling on-demand rendering](https://docs.astro.build/en/guides/on-demand-rendering/#enabling-on-demand-rendering), ['server' mode](https://docs.astro.build/en/guides/on-demand-rendering/#server-mode))
- `7` `ASTRO-2` **Add a `client:*` directive only to framework components that must be interactive, and choose the lowest priority that works: `client:idle`, `client:visible` or `client:media` for most islands, and `client:load` only for visible UI that must be interactive at once.** Components without a directive render to HTML without JavaScript. This is how Astro follows `WEB-5`. ([Astro, Client islands](https://docs.astro.build/en/concepts/islands/#client-islands), [Template directives: client directives](https://docs.astro.build/en/reference/directives-reference/#client-directives))
- `6` `ASTRO-3` **Render personalized parts of an otherwise static or cached page as server islands with `server:defer` and fallback content, pass them only the props they need, and set a constant `ASTRO_KEY` from `astro create-key` for rolling or multi-region deployments and CDN-cached pages.** Props travel encrypted in a GET request that can be cached; when they make the URL longer than 2048 bytes, Astro sends a POST request that isn't cached. Without a constant key, a server can't decrypt props encrypted by another build. ([Astro, Server island fallback content](https://docs.astro.build/en/guides/server-islands/#server-island-fallback-content), [Caching](https://docs.astro.build/en/guides/server-islands/#caching), [Reusing the encryption key](https://docs.astro.build/en/guides/server-islands/#reusing-the-encryption-key))

### Content and assets

- `7` `ASTRO-4` **Manage sets of structured content in content collections with a schema, and prefer build-time collections: use live collections only when content must be fresh on every request.** Astro validates every entry against its schema and generates TypeScript types from it. ([Astro, Defining the collection schema](https://docs.astro.build/en/guides/content-collections/#defining-the-collection-schema), [Types of collections](https://docs.astro.build/en/guides/content-collections/#types-of-collections))
- `6` `ASTRO-5` **Keep local images in `src/` and render them with `<Image />` or `<Picture />` from `astro:assets`, and list only trusted remote hosts in `image.domains` or `image.remotePatterns`.** Astro optimizes these images and sets their dimensions, which prevents layout shift (`WEB-6`). Images in `public/` and from unlisted hosts aren't processed. ([Astro, src/ vs public/](https://docs.astro.build/en/guides/images/#src-vs-public), [`<Image />`](https://docs.astro.build/en/guides/images/#image-), [Authorizing remote images](https://docs.astro.build/en/guides/images/#authorizing-remote-images))

### Server code and security

- `9` `ASTRO-6` **Treat every action as a public endpoint: give it an `input` schema, and check authorization in its handler, not only in middleware or on the page that calls it.** Astro serves each action at `/_actions/<name>`, so it needs the same checks as API endpoints and on-demand pages (`SEC-1`, `SEC-10`). Gating actions in middleware ensures only that a session exists. ([Astro, Security when using actions](https://docs.astro.build/en/guides/actions/#security-when-using-actions), [Authorize users from an action handler](https://docs.astro.build/en/guides/actions/#authorize-users-from-an-action-handler), [Gate actions from middleware](https://docs.astro.build/en/guides/actions/#gate-actions-from-middleware))
- `9` `ASTRO-7` **Declare environment variables in the `env.schema` of the Astro config, give a variable `context: "client"` or the `PUBLIC_` prefix only if its value may be public, and read secrets with `access: "secret"` from `astro:env/server`.** Public client variables end up in the client bundle; secret server variables aren't part of any bundle. This is how Astro follows `SEC-11`. ([Astro, Variable types](https://docs.astro.build/en/guides/environment-variables/#variable-types), [Vite's built-in support](https://docs.astro.build/en/guides/environment-variables/#vites-built-in-support))
- `8` `ASTRO-8` **Render every page that depends on the visitor, such as pages behind a login or with personalized content, on demand, and check authentication on each request in middleware or in the page.** For prerendered pages, middleware runs once at build time, not on each request. ([Astro, Middleware](https://docs.astro.build/en/guides/middleware/), [On-demand rendering](https://docs.astro.build/en/guides/on-demand-rendering/))
- `7` `ASTRO-9` **Pass request data, such as the current user, from middleware to pages and endpoints in `context.locals`, and keep data that must last between requests in Astro sessions or a database.** `locals` lives for a single request, and sessions keep their data on the server instead of in cookies. This is how Astro follows `SEC-12`. Astro inlines the environment variables of a session driver's configuration into the build, so configure a driver that needs credentials in its own entrypoint file. ([Astro, Storing data in context.locals](https://docs.astro.build/en/guides/middleware/#storing-data-in-contextlocals), [Sessions](https://docs.astro.build/en/guides/sessions/), [Overriding the configuration at runtime](https://docs.astro.build/en/guides/sessions/#overriding-the-configuration-at-runtime))
- `7` `ASTRO-10` **Keep `security.checkOrigin` on, which is the default, and when a trusted proxy sets `X-Forwarded-Host`, list your hosts in `security.allowedDomains` instead of allowing all.** `checkOrigin` rejects cross-site form submissions to on-demand pages (CSRF), and Astro ignores `X-Forwarded-Host` unless it matches an allowed domain, which prevents host header injection into `Astro.url`. ([Astro, security.checkOrigin](https://docs.astro.build/en/reference/configuration-reference/#securitycheckorigin), [security.allowedDomains](https://docs.astro.build/en/reference/configuration-reference/#securityalloweddomains))
- `7` `ASTRO-11` **Turn on `security.csp`, which adds hashes for Astro's own scripts and styles to a CSP `<meta>` element on every page, add your other directives in its options, and don't add `'unsafe-inline'`. Test it with `astro build` and `astro preview`, because it doesn't work in the dev server.** This is how Astro follows `WEB-10`. It doesn't support `<ClientRouter />` or Shiki, and with `'unsafe-inline'` in a directive Astro drops that directive's hashes. ([Astro, security.csp](https://docs.astro.build/en/reference/configuration-reference/#securitycsp), [security.csp.directives](https://docs.astro.build/en/reference/configuration-reference/#securitycspdirectives))

### Navigation and accessibility

- `6` `ASTRO-12` **Prefer the browser's native cross-document view transitions, and add `<ClientRouter />` only for features that need it. With it, run code that must run on every page in an `astro:page-load` listener, and give every page a `<title>`, which the router announces to screen readers after each navigation.** With the router, bundled scripts run only once per visit, and Astro's CSP doesn't support it. ([Astro, Differences between native view transitions and `<ClientRouter />`](https://docs.astro.build/en/guides/view-transitions/#differences-between-browser-native-view-transitions-and-astros-clientrouter-), [Script re-execution](https://docs.astro.build/en/guides/view-transitions/#script-re-execution), [Route announcement](https://docs.astro.build/en/guides/view-transitions/#route-announcement))

### Testing and tooling

- `7` `ASTRO-13` **Type-check in CI with `astro check`, for example as `astro check && astro build`, and use the `strict` or `strictest` tsconfig template.** The dev server and `astro build` don't type-check, and `tsc` ignores `.astro` files. ([Astro, Type checking](https://docs.astro.build/en/guides/typescript/#type-checking), [tsconfig templates](https://docs.astro.build/en/guides/typescript/#tsconfig-templates), [astro check](https://docs.astro.build/en/reference/cli-reference/#astro-check))
- `6` `ASTRO-14` **Test `.astro` components with Vitest through `getViteConfig()` and the Container API, and run end-to-end tests with Playwright against a production build served by `astro preview`.** The Container API is still experimental and can change in minor releases. Follow the test rules in [Web front end](../web/README.md), such as `WEB-14` to `WEB-17`. ([Astro, Vitest and Container API](https://docs.astro.build/en/guides/testing/#vitest-and-container-api), [Playwright: launching a web server during the tests](https://docs.astro.build/en/guides/testing/#advanced-launching-a-development-web-server-during-the-tests), [Container API](https://docs.astro.build/en/reference/container-reference/))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [astro check](https://docs.astro.build/en/reference/cli-reference/#astro-check): runs diagnostics, including type-checking `.astro` and `.ts` files, and exits with code 1 when it finds errors; with `--minimumFailingSeverity warning`, warnings fail it too. Checks `ASTRO-13`.
- `7` [Content collection schema validation](https://docs.astro.build/en/guides/content-collections/#defining-the-collection-schema): built into Astro, which reports [an error](https://docs.astro.build/en/reference/errors/invalid-content-entry-data-error/) when a collection entry doesn't match its schema. Partly checks `ASTRO-4`.
- `6` [eslint-plugin-astro](https://ota-meshi.github.io/eslint-plugin-astro/rules/): [`astro/no-unsafe-inline-scripts`](https://ota-meshi.github.io/eslint-plugin-astro/rules/no-unsafe-inline-scripts/) flags inline scripts, which typically need `'unsafe-inline'` in a CSP, and [`astro/no-set-html-directive`](https://ota-meshi.github.io/eslint-plugin-astro/rules/no-set-html-directive/) flags every `set:html`, the unescaped HTML sink that `WEB-8` covers. Partly checks `ASTRO-11`.
- `5` [`astro:env` validation](https://docs.astro.build/en/reference/errors/env-prefix-conflicts-with-secret/): built into Astro, which raises an error when a variable declared with `access: "secret"` matches a prefix in `vite.envPrefix`, which would expose it in client bundles, and [when variables don't match their schema](https://docs.astro.build/en/reference/errors/env-invalid-variables/). Partly checks `ASTRO-7`.
