# Microsoft Azure

Scope: workloads on Microsoft Azure, from a single subscription to an enterprise landing zone. Cloud-neutral rules live elsewhere: least privilege (`SEC-1`) and secrets management (`SEC-2`) in [Security](../../general/security.md), resilience and monitoring in [Operations and reliability](../../general/operations-reliability.md), Terraform itself in [Terraform](../terraform/README.md), and pipelines that deploy to Azure in [GitHub Actions](../github-actions/README.md). For the other clouds, see [AWS](../aws/README.md) and [Google Cloud](../gcp/README.md).

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Key rules

### Organization and governance

- `8` `AZURE-1` **Deploy workloads into an Azure landing zone: put platform services such as management, connectivity and identity in their own subscriptions, and give each workload environment its own subscriptions.** Subscriptions are boundaries for policy, access, billing and scale. A landing zone accelerator deploys the recommended structure as code. ([CAF, What is an Azure landing zone?](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/), [CAF, Subscription considerations and recommendations](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/design-area/resource-org-subscriptions#organization-and-governance-recommendations))
- `7` `AZURE-2` **Agree on a naming convention and a set of required tags, such as application, environment and cost center, before you deploy, and enforce the tags with Azure Policy.** Most resource names can't be changed after creation. Tags are stored as plain text, so never put sensitive values in them. ([CAF, Define your naming convention](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/azure-best-practices/resource-naming), [CAF, Define your tagging strategy](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/azure-best-practices/resource-tagging), [Policy definitions for tagging resources](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/tag-policies))
- `7` `AZURE-3` **Set guardrails with Azure Policy: prefer built-in policies and initiatives, assign them at the highest suitable scope, and roll out each new assignment in audit mode before you switch it to deny.** ([CAF, Azure governance design area](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/design-area/governance#azure-governance-recommendations), [Safe deployment of Azure Policy assignments](https://learn.microsoft.com/en-us/azure/governance/policy/how-to/policy-safe-deployment-practices))
- `6` `AZURE-4` **Keep the management group hierarchy flat, ideally three or four levels, and group subscriptions by workload type, such as corp and online, not by environment or org chart.** Keep policy assignments at the root management group to a minimum. ([CAF, Management groups](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/design-area/resource-org-management-groups#management-group-recommendations))

### Identity and secrets

- `9` `AZURE-5` **Authenticate workloads with managed identities, and pipelines and workloads outside Azure with workload identity federation, instead of client secrets, certificates or access keys.** Where a service allows it, also turn off key-based access, such as Shared Key authorization for Storage. For GitHub Actions, see `GHA-5` in [GitHub Actions](../github-actions/README.md). ([Managed identities for Azure resources](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview), [Microsoft Entra Workload ID, Workload identity federation](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation), [Prevent authorization with Shared Key](https://learn.microsoft.com/en-us/azure/storage/common/shared-key-authorization-prevent))
- `8` `AZURE-6` **Use one Key Vault per application, environment and region, authorize access with Azure RBAC rather than legacy access policies, and turn on purge protection.** ([Secure your Azure Key Vault: identity and access management](https://learn.microsoft.com/en-us/azure/key-vault/general/secure-key-vault#identity-and-access-management), [data protection](https://learn.microsoft.com/en-us/azure/key-vault/general/secure-key-vault#data-protection))
- `7` `AZURE-7` **Assign Azure RBAC roles to groups rather than users, at the narrowest scope, keep at most three subscription owners, and give administrators just-in-time access with Privileged Identity Management.** ([Best practices for Azure RBAC](https://learn.microsoft.com/en-us/azure/role-based-access-control/best-practices))

### Networking

- `7` `AZURE-8` **Reach PaaS data services, such as Storage, SQL Database and Key Vault, through private endpoints, and block public traffic with the service firewall or turn public network access off.** A private endpoint alone doesn't block public access, and clients need DNS, usually private DNS zones, that resolves the service to the endpoint. ([Well-Architected Framework, Private endpoints](https://learn.microsoft.com/en-us/azure/well-architected/security/networking#private-endpoints), [What is a private endpoint?](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview))

### Reliability

- `9` `AZURE-9` **Deploy production workloads across availability zones in regions that have them, and prefer zone-redundant service configurations.** Zone support differs between services, so check each service's reliability guide. ([What are Azure availability zones?](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview#availability-zone-architectural-guidance), [Well-Architected Framework, Using availability zones and regions](https://learn.microsoft.com/en-us/azure/well-architected/design-guides/regions-availability-zones), [Reliability guides for Azure services](https://learn.microsoft.com/en-us/azure/reliability/overview-reliability-guidance))

### Delivery and operations

- `9` `AZURE-10` **Define all Azure resources as code in Bicep or Terraform, deploy them from a pipeline, and build on Azure Verified Modules.** Terraform is the better choice when you also manage other clouds or on-premises resources. ([Well-Architected Framework, Infrastructure as code](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/infrastructure-as-code-design), [Comparing Terraform and Bicep](https://learn.microsoft.com/en-us/azure/developer/terraform/comparing-terraform-and-bicep), [Azure Verified Modules](https://azure.github.io/Azure-Verified-Modules/))
- `7` `AZURE-11` **In Bicep, mark secret parameters and outputs with `@secure()`, don't give secure parameters default values, and read secrets from Key Vault with `getSecret()` or the `existing` keyword instead of passing them through outputs.** Anyone with access to the deployment history can read outputs that aren't secure. ([Bicep best practices: outputs](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/best-practices#outputs), [Use Key Vault to pass a secret during Bicep deployment](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/key-vault-parameter), [Linter rule: secure parameter default](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/linter-rule-secure-parameter-default))
- `7` `AZURE-12` **Route resource logs to a central Log Analytics workspace with diagnostic settings, deployed at scale with Azure Policy, and start with a single workspace.** Azure generates resource logs, but you can't query them until a diagnostic setting sends them to a workspace. ([Monitor Azure resources: diagnostic settings](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/monitor-azure-resource#diagnostic-settings-for-an-azure-resource), [Enable diagnostic settings with built-in policies](https://learn.microsoft.com/en-us/azure/azure-monitor/data-collection/diagnostic-settings-policy-built-in), [Design a Log Analytics workspace architecture](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/workspace-design#design-strategy))
- `7` `AZURE-13` **Create a budget with actual and forecasted cost alerts for every subscription.** Budgets only notify: they don't stop resources or spending. ([Cost Management, Create and manage budgets](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets), [CAF, Azure governance design area](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/landing-zone/design-area/governance))
- `6` `AZURE-14` **Assess each workload with the Azure Well-Architected Review, and act on Azure Advisor recommendations, which Advisor scores by pillar.** ([Azure Well-Architected Review](https://learn.microsoft.com/en-us/assessments/azure-architecture-review/), [Well-Architected Framework pillars](https://learn.microsoft.com/en-us/azure/well-architected/pillars), [Introduction to Azure Advisor](https://learn.microsoft.com/en-us/azure/advisor/advisor-overview))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [Azure Policy, Microsoft cloud security benchmark initiative](https://learn.microsoft.com/en-us/azure/governance/policy/samples/azure-security-benchmark): Defender for Cloud [assigns it by default](https://learn.microsoft.com/en-us/azure/defender-for-cloud/concept-regulatory-compliance-standards) and continuously reports resources that break it, for example Key Vaults without deletion protection or the RBAC permission model, apps without a managed identity, local authentication left on, and PaaS services with public network access. Other [built-in initiatives](https://learn.microsoft.com/en-us/azure/governance/policy/samples/built-in-initiatives) audit [zone resilience](https://learn.microsoft.com/en-us/azure/governance/policy/samples/built-in-initiatives#resilience) and [deploy diagnostic settings](https://learn.microsoft.com/en-us/azure/governance/policy/samples/built-in-initiatives#monitoring), and the [tagging policies](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/tag-policies) deny resources without required tags. Partly checks `AZURE-2`, `AZURE-5`, `AZURE-6`, `AZURE-8`, `AZURE-9` and `AZURE-12`.
- `6` [PSRule for Azure rules](https://azure.github.io/PSRule.Rules.Azure/en/rules/): tests Bicep and ARM templates in CI against rules aligned with the Well-Architected Framework, such as [Azure.KeyVault.RBAC](https://azure.github.io/PSRule.Rules.Azure/en/rules/Azure.KeyVault.RBAC/), [Azure.KeyVault.PurgeProtect](https://azure.github.io/PSRule.Rules.Azure/en/rules/Azure.KeyVault.PurgeProtect/), [Azure.KeyVault.Firewall](https://azure.github.io/PSRule.Rules.Azure/en/rules/Azure.KeyVault.Firewall/), [Azure.AppService.ManagedIdentity](https://azure.github.io/PSRule.Rules.Azure/en/rules/Azure.AppService.ManagedIdentity/), [Azure.Storage.LocalAuth](https://azure.github.io/PSRule.Rules.Azure/en/rules/Azure.Storage.LocalAuth/), [Azure.AppService.AvailabilityZone](https://azure.github.io/PSRule.Rules.Azure/en/rules/Azure.AppService.AvailabilityZone/), [Azure.Resource.UseTags](https://azure.github.io/PSRule.Rules.Azure/en/rules/Azure.Resource.UseTags/) and [Azure.Deployment.OutputSecretValue](https://azure.github.io/PSRule.Rules.Azure/en/rules/Azure.Deployment.OutputSecretValue/). Partly checks `AZURE-2`, `AZURE-5`, `AZURE-6`, `AZURE-8`, `AZURE-9` and `AZURE-11`.
- `6` [Bicep linter](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/linter): built into the Bicep CLI and the VS Code extension. [`secure-parameter-default`](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/linter#secure-parameter-default) flags defaults on secure parameters and [`outputs-should-not-contain-secrets`](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/linter#outputs-should-not-contain-secrets) flags secrets in outputs. Both are warnings by default, so set them to `error` in `bicepconfig.json` to fail the build in CI. Partly checks `AZURE-11`.
- `6` [Checkov Terraform policies](https://www.checkov.io/5.Policy%20Index/terraform.html) and [Bicep policies](https://www.checkov.io/5.Policy%20Index/bicep.html): misconfiguration checks before deployment, including Key Vault purge protection (`CKV_AZURE_110`), public network access (`CKV_AZURE_189`) and private endpoint (`CKV2_AZURE_32`), managed identity for App Service (`CKV_AZURE_71`), Shared Key authorization on Storage (`CKV2_AZURE_40`) and zone-redundant App Service plans (`CKV_AZURE_225`). Partly checks `AZURE-5`, `AZURE-6`, `AZURE-8` and `AZURE-9`.
