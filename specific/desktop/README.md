# Desktop apps (Electron and Tauri)

Scope: desktop apps for Windows, macOS and Linux whose user interface is a web front end, built with Electron (current major: Electron 45; the Electron team supports the latest three majors) or Tauri 2 (current release: 2.12). Tauri 2 also builds mobile apps, which these guidelines don't cover. The web content in a window follows [Web front end](../web/README.md) and the guidelines of its framework, such as [React](../react/README.md), [Vue](../vue/README.md) or [Svelte](../svelte/README.md). Electron's main process runs on Node.js, so the [Node.js](../nodejs/README.md) guidelines apply to it. Keeping secrets out of what you ship (`SEC-11`), validating input at trust boundaries (`SEC-10`) and staying on supported releases (`SEC-17`) are in [Security](../../general/security.md), and versioning and release builds are in [Releases](../../general/releases.md). Games sold on Steam also follow [Steam and PC games](../steam/README.md).

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Adopted references

- `10` [Security](https://www.electronjs.org/docs/latest/tutorial/security) (Electron): **the baseline for Electron apps.** The official checklist of 20 security recommendations, from context isolation, the sandbox and a Content Security Policy to navigation limits, IPC sender validation, custom protocols and fuses.
- `10` [Security](https://v2.tauri.app/security/) (Tauri): **the baseline for Tauri apps.** Trust boundaries between the Rust core and the WebView, permissions, command scopes, capabilities, runtime authority, the CSP, the isolation pattern, and threats across the application lifecycle.
- `8` [Process Model](https://www.electronjs.org/docs/latest/tutorial/process-model) (Electron): the main process, renderer processes, preload scripts and utility processes, and what each one may do.
- `8` [Inter-Process Communication](https://www.electronjs.org/docs/latest/tutorial/ipc) (Electron): the IPC patterns between renderer and main process, exposed through a preload script and `contextBridge`.
- `8` [Capabilities](https://v2.tauri.app/security/capabilities/) (Tauri): granting and denying permissions to windows and webviews, per platform, and what capabilities do and don't protect against.
- `7` [Electron Forge](https://www.electronforge.io/): the Electron project's all-in-one tool for packaging, code signing, creating installers and publishing apps, which combines Electron's first-party tools into one build pipeline.
- `7` [Distribute](https://v2.tauri.app/distribute/) (Tauri): building, bundling, versioning, signing and distributing Tauri apps for each platform and store.
- `7` [Performance](https://www.electronjs.org/docs/latest/tutorial/performance) (Electron): a checklist for fast Electron apps, from choosing modules and loading code late to not blocking the main process and bundling code.
- `7` [Code Signing](https://www.electronjs.org/docs/latest/tutorial/code-signing) (Electron): signing and notarizing macOS builds and signing Windows builds with Electron Forge and other tools.
- `6` [App Size](https://v2.tauri.app/concept/size/) (Tauri): a Cargo release profile for small binaries, and removing commands that no capability allows.

## Key rules

### Processes and IPC

- `9` `DESKTOP-1` **Keep Electron's secure renderer defaults: context isolation, the sandbox and `webSecurity` on, and Node.js integration off. Call `app.enableSandbox()` so that no window can turn the sandbox off.** Keeping Node.js integration off helps stop an XSS in a renderer from escalating into code execution on the user's machine, and turning off context isolation also turns off the sandbox. Never load remote content in a renderer with Node.js integration. ([Electron, Security: do not enable Node.js integration for remote content](https://www.electronjs.org/docs/latest/tutorial/security#2-do-not-enable-nodejs-integration-for-remote-content), [Enable context isolation](https://www.electronjs.org/docs/latest/tutorial/security#3-enable-context-isolation), [Enable process sandboxing](https://www.electronjs.org/docs/latest/tutorial/security#4-enable-process-sandboxing), [Do not disable webSecurity](https://www.electronjs.org/docs/latest/tutorial/security#6-do-not-disable-websecurity), [Enabling the sandbox globally](https://www.electronjs.org/docs/latest/tutorial/sandbox#enabling-the-sandbox-globally))
- `9` `DESKTOP-2` **In Electron preload scripts, expose a narrow API with `contextBridge.exposeInMainWorld`: one function per IPC message, using `ipcRenderer.invoke` for requests. Never expose `ipcRenderer` or its `send`, `invoke` or `on` methods, and don't pass the IPC event object to callbacks in the page.** Otherwise any script in the page can send arbitrary IPC messages, or reach `ipcRenderer` through `event.sender`. ([Electron, Security: do not expose Electron APIs to untrusted web content](https://www.electronjs.org/docs/latest/tutorial/security#20-do-not-expose-electron-apis-to-untrusted-web-content), [Context Isolation: security considerations](https://www.electronjs.org/docs/latest/tutorial/context-isolation#security-considerations), [IPC: renderer to main (two-way)](https://www.electronjs.org/docs/latest/tutorial/ipc#pattern-2-renderer-to-main-two-way))
- `9` `DESKTOP-3` **In Electron's main process, check the sender of every IPC message, for example the origin of `event.senderFrame`, and validate its arguments before acting on them.** Any web frame can send IPC messages, including iframes and, in some cases, child windows. This applies `SEC-10`. ([Electron, Security: validate the sender of all IPC messages](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages), [Context Isolation: security considerations](https://www.electronjs.org/docs/latest/tutorial/context-isolation#security-considerations))
- `8` `DESKTOP-4` **Treat the arguments of every Tauri command as untrusted input: deserialize them into specific types, check their values in the command, and enforce your own scopes in the command itself. Keep secrets and as much business logic as you can in the Rust core.** Capabilities decide which windows may call a command, but they don't protect against missing or incorrect checks in its implementation. This applies `SEC-10`. ([Tauri, Trust boundaries](https://v2.tauri.app/security/#trust-boundaries), [Command scopes](https://v2.tauri.app/security/scope/), [Capabilities: security boundaries](https://v2.tauri.app/security/capabilities/#security-boundaries), [Process model: the WebView process](https://v2.tauri.app/concept/process-model/#the-webview-process))
- `7` `DESKTOP-5` **Never block Electron's main process: use the asynchronous versions of Node.js APIs, avoid `ipcRenderer.sendSync` and `@electron/remote`, and move CPU-heavy, crash-prone or untrusted work to a worker thread or a utility process.** A blocked main process freezes the whole app. ([Electron, Performance: blocking the main process](https://www.electronjs.org/docs/latest/tutorial/performance#3-blocking-the-main-process), [Process Model: the utility process](https://www.electronjs.org/docs/latest/tutorial/process-model#the-utility-process), [IPC: using ipcRenderer.sendSync](https://www.electronjs.org/docs/latest/tutorial/ipc#using-ipcrenderersendsync))

### Permissions and web content

- `8` `DESKTOP-8` **Scope every Tauri plugin permission that reaches the system: allow file system access only to the base directories the app needs, such as `$APPDATA`, with deny scopes for sensitive paths, allow the shell plugin to run only named programs with argument validators, and allow the opener plugin only the URLs and paths it needs.** Deny scopes take precedence over allow scopes. ([Tauri, File System: scopes](https://v2.tauri.app/plugin/file-system/#scopes), [Command scopes](https://v2.tauri.app/security/scope/), [Shell: permissions](https://v2.tauri.app/plugin/shell/#permissions), [Opener: permissions](https://v2.tauri.app/plugin/opener/#permissions))
- `8` `DESKTOP-9` **Limit where Electron windows can go: block navigation in a `will-navigate` handler unless a parsed URL matches the pages you expect, deny new windows in `setWindowOpenHandler` by default, and pass only checked, allowlisted URLs to `shell.openExternal`.** Navigation and new windows are common attack vectors, and `openExternal` with untrusted input can run arbitrary commands. Compare parsed origins, not string prefixes. ([Electron, Security: disable or limit navigation](https://www.electronjs.org/docs/latest/tutorial/security#13-disable-or-limit-navigation), [Disable or limit creation of new windows](https://www.electronjs.org/docs/latest/tutorial/security#14-disable-or-limit-creation-of-new-windows), [Do not use shell.openExternal with untrusted content](https://www.electronjs.org/docs/latest/tutorial/security#15-do-not-use-shellopenexternal-with-untrusted-content))
- `7` `DESKTOP-6` **Give every window a Content Security Policy that allows only your own scripts, such as `script-src 'self'`: in Electron, send it as a header from `session.webRequest.onHeadersReceived`, or in a `<meta>` tag for pages that can't get headers; in Tauri, set `app.security.csp` in `tauri.conf.json`, because Tauri's CSP protection is off until you set it.** Don't load scripts from remote servers or CDNs, and don't turn off Tauri's injection of hashes and nonces. This is how desktop apps follow `WEB-10`. ([Electron, Security: define a Content Security Policy](https://www.electronjs.org/docs/latest/tutorial/security#7-define-a-content-security-policy), [Tauri, Content Security Policy](https://v2.tauri.app/security/csp/), [Tauri configuration: dangerousDisableAssetCspModification](https://v2.tauri.app/reference/config/#dangerousdisableassetcspmodification))
- `7` `DESKTOP-7` **Grant each Tauri window only the permissions it needs: give windows with different privileges separate capabilities, add a window to several capabilities only if it needs all their permissions, declare your own commands with `AppManifest::commands` in `build.rs` so that a window can call them only when a capability allows it, and let only higher-privileged windows create windows.** A window in several capabilities gets the permissions of all of them, by default every command the app registers is allowed for every window, and capabilities match windows by label, not by title. ([Tauri, Capabilities](https://v2.tauri.app/security/capabilities/), [Capabilities: security boundaries](https://v2.tauri.app/security/capabilities/#security-boundaries), [Capabilities for different windows and platforms](https://v2.tauri.app/learn/security/capabilities-for-windows-and-platforms/#apply-different-capabilities-to-different-windows))
- `7` `DESKTOP-10` **Serve Electron's local pages from a custom protocol with `protocol.handle` instead of `file://`, and flip the fuses you don't need when packaging, before code signing: turn off `RunAsNode`, `EnableNodeOptionsEnvironmentVariable`, `EnableNodeCliInspectArguments` and `GrantFileProtocolExtraPrivileges`, and turn on `EnableEmbeddedAsarIntegrityValidation` and `OnlyLoadAppFromAsar`.** An XSS in a page on `file://` can read any file on the machine, and with the default fuses the app's binary can be started as plain Node.js or with a debugger, which can be used to run commands through your app. ([Electron, Security: avoid the file:// protocol](https://www.electronjs.org/docs/latest/tutorial/security#18-avoid-usage-of-the-file-protocol-and-prefer-usage-of-custom-protocols), [Check which fuses you can change](https://www.electronjs.org/docs/latest/tutorial/security#19-check-which-fuses-you-can-change), [Electron Fuses](https://www.electronjs.org/docs/latest/tutorial/fuses#current-fuses))
- `6` `DESKTOP-11` **Use Tauri's isolation pattern when the front end has many dependencies or loads third-party content, and keep the isolation application small, with few dependencies and build steps.** It routes every IPC message through a sandboxed iframe that can validate or reject it before it reaches the Rust core. ([Tauri, Isolation pattern: when](https://v2.tauri.app/concept/inter-process-communication/isolation/#when), [Recommendations](https://v2.tauri.app/concept/inter-process-communication/isolation/#recommendations), [Tauri configuration: pattern](https://v2.tauri.app/reference/config/#pattern))

### Secrets and local data

- `9` `DESKTOP-12` **Never build API keys or other secrets into the app, and store users' credentials and tokens only in encrypted storage: in Electron, the asynchronous `safeStorage` API, which uses the operating system's cryptography, and in Tauri, for example, the Stronghold plugin.** An ASAR archive only conceals code from cursory inspection, and the front end of a Tauri app must never handle secrets. On Linux, `safeStorage.getSelectedStorageBackend()` returns `basic_text` when no secret store is available and data is encrypted with a hardcoded password. This applies `SEC-11`. ([Electron, ASAR Archives](https://www.electronjs.org/docs/latest/tutorial/asar-archives), [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage), [Tauri, Process model: the WebView process](https://v2.tauri.app/concept/process-model/#the-webview-process), [Stronghold](https://v2.tauri.app/plugin/stronghold/))

### Releases and updates

- `8` `DESKTOP-13` **Sign every release in the release pipeline: sign macOS apps with a Developer ID Application certificate and notarize them, and sign Windows executables and installers with one consistent identity, as `STEAM-16` describes.** Windows and macOS warn about or block unsigned apps, and macOS features such as `autoUpdater`, `safeStorage` and the cookie encryption fuse only work reliably in a signed app. ([Electron, Code Signing](https://www.electronjs.org/docs/latest/tutorial/code-signing), [macOS APIs that require code signing](https://www.electronjs.org/docs/latest/tutorial/code-signing#macos-apis-that-require-code-signing), [Tauri, macOS code signing: notarization](https://v2.tauri.app/distribute/sign/macos/#notarization), [Tauri, Windows code signing](https://v2.tauri.app/distribute/sign/windows/))
- `8` `DESKTOP-14` **Deliver updates only through a signed update mechanism over HTTPS: Electron's `autoUpdater`, for example through `update-electron-app`, in a signed app, or the Tauri updater with its signing key pair. Keep the update signing key in the CI secret store, and never set the Tauri updater's `dangerousInsecureTransportProtocol`.** Tauri verifies every update against the public key in `tauri.conf.json`, and if you lose the private key you can't ship updates to existing installs. On macOS, Electron's updater requires a signed app. ([Electron, Updating Applications](https://www.electronjs.org/docs/latest/tutorial/updates), [autoUpdater: macOS](https://www.electronjs.org/docs/latest/api/auto-updater#macos), [Tauri, Updater: signing updates](https://v2.tauri.app/plugin/updater/#signing-updates))
- `8` `DESKTOP-15` **Stay on an Electron major that the Electron team still supports, which is one of the latest three, on its latest minor release, and upgrade one major at a time. Update Tauri, the Rust compiler and Node.js just as promptly.** Each Electron release ships its own Chromium and Node.js, and exploits for their older versions are more widely available. This applies `SEC-17`. ([Electron, Security: use a current version of Electron](https://www.electronjs.org/docs/latest/tutorial/security#16-use-a-current-version-of-electron), [Electron Releases: version support policy](https://www.electronjs.org/docs/latest/tutorial/electron-timelines#version-support-policy), [Tauri, Keep your applications up to date](https://v2.tauri.app/security/lifecycle/#keep-your-applications-up-to-date))

### Testing

- `6` `DESKTOP-16` **Run end-to-end tests against the built app, for example with WebdriverIO's Electron or Tauri service, or with Playwright's experimental Electron support, and mock the IPC layer in front-end unit tests, for example with Tauri's `mockIPC`.** Follow the end-to-end test rules in [Web front end](../web/README.md), such as `WEB-15` and `WEB-17`. ([Electron, Automated Testing](https://www.electronjs.org/docs/latest/tutorial/automated-testing), [WebdriverIO, Electron](https://webdriver.io/docs/desktop-testing/electron), [Tauri, WebDriver](https://v2.tauri.app/develop/tests/webdriver/), [Tauri, Mock Tauri APIs](https://v2.tauri.app/develop/tests/mocking/))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [`app.enableSandbox()`](https://www.electronjs.org/docs/latest/tutorial/sandbox#enabling-the-sandbox-globally): built into Electron; called before the app is ready, it forces the sandbox in every renderer and overrides `sandbox: false` in any window. Partly checks `DESKTOP-1`.
- `7` [Tauri updater signature check](https://v2.tauri.app/plugin/updater/#signing-updates): built into the updater, which verifies every update against the public key in `tauri.conf.json` and can't be turned off, and [enforces TLS](https://v2.tauri.app/plugin/updater/#tauri-configuration) for update endpoints in production. Partly checks `DESKTOP-14`.
- `6` [@electron/fuses](https://github.com/electron/fuses/blob/main/README.md): flips fuses from a build script, or through Electron Forge's [Fuses plugin](https://www.electronforge.io/config/plugins/fuses). `npx @electron/fuses read --app` prints a packaged app's fuses for a check in CI, and `strictlyRequireAllFuses: true` fails the build when the Electron binary has a fuse that your configuration doesn't set. Partly checks `DESKTOP-10`.
- `6` [SignTool `verify`](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool#verify-command-options) and [`spctl --assess`](https://developer.apple.com/documentation/security/resolving-common-notarization-issues): in the release job, `signtool verify /pa` checks the signature of Windows files with the default authentication verification policy and returns 1 on failure, and `spctl -vvv --assess --type exec` reports whether a macOS app will run under the system policies in effect. Partly checks `DESKTOP-13`.
- `6` [npm audit](https://docs.npmjs.com/cli/v12/commands/npm-audit/) and [cargo audit](https://github.com/rustsec/rustsec/blob/main/cargo-audit/README.md): report npm packages and Rust crates with known vulnerabilities; `npm audit` exits with a non-zero code when it finds any, at or above `--audit-level`. Partly checks `DESKTOP-15`.
