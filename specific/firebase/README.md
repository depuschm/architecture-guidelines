# Firebase

Scope: web apps, mobile apps and games whose clients read and write Firebase directly: Cloud Firestore, Realtime Database, Cloud Storage for Firebase, Firebase Authentication, App Check and Cloud Functions for Firebase (2nd gen), with the current SDKs and tools (Firebase JavaScript SDK 13, `firebase-functions` 7 and the Firebase CLI 15). Because clients reach the data without a server of your own in between, Firebase Security Rules carry the server-side authorisation that `SEC-1` asks for, and everything in the client is public (`SEC-11` in [Security](../../general/security.md)). Sign-in in general is covered in [Authentication and sessions](../../general/authentication.md), consent and personal data in [Privacy and personal data](../../general/privacy.md), browser apps in [Web front end](../web/README.md), and store purchases, integrity checks and live operations with Remote Config in [Mobile games](../mobile-games/README.md). A Firebase project is a Google Cloud project, so [Google Cloud](../gcp/README.md) also applies to its IAM, secrets and billing. For a PostgreSQL-based backend of the same kind, see [Supabase](../supabase/README.md).

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Key rules

### Security Rules

- `10` `FIREBASE-1` **Start every Firestore database, Realtime Database and Storage bucket with rules that deny all access, and never deploy test-mode rules, `allow read, write: if true`, or rules that let any signed-in user (`request.auth != null`) reach all data.** Clients access the data directly, so the rules are the only safeguard: grant access per collection or path, based on `request.auth.uid`, custom claims or the data itself. This applies `SEC-1`. ([Firebase security checklist, Initialize rules in production or locked mode](https://firebase.google.com/support/guides/security-checklist#initialize-rules-in-production-or-locked-mode), [Avoid insecure rules](https://firebase.google.com/docs/rules/insecure-rules), [Basic Security Rules, Development-environment rules](https://firebase.google.com/docs/rules/basics#development-environment_rules))
- `8` `FIREBASE-2` **Write the rules for each new collection or path together with the code that uses it, keep the rules and index definitions (`firestore.rules`, `storage.rules` and `firestore.indexes.json`) in the repository, and deploy them with the Firebase CLI instead of editing them in the console.** Firebase advises treating rules like a database schema, and a CLI deploy overwrites rules that were changed in the console. This applies `OPS-14`. ([Firebase security checklist, Security rules are a schema](https://firebase.google.com/support/guides/security-checklist#add-rules-when-you-add-documents), [Manage and deploy Firebase Security Rules](https://firebase.google.com/docs/rules/manage-deploy#use_the), [Manage indexes: use the Firebase CLI](https://firebase.google.com/docs/firestore/query-data/indexing#use-firebase-cli))
- `8` `FIREBASE-4` **Validate every client write in the rules: allow only known fields with `request.resource.data.keys().hasOnly()`, check their types, and use `diff().affectedKeys()` to stop clients from changing fields such as an owner ID, a role or a balance.** When clients write directly, the rules are the server-side input validation that `SEC-10` asks for. ([Firestore, Control access to specific fields](https://firebase.google.com/docs/firestore/security/rules-fields), [Writing conditions: data validation](https://firebase.google.com/docs/firestore/security/rules-conditions#data_validation))
- `7` `FIREBASE-3` **Unit-test the rules with `@firebase/rules-unit-testing` against the emulators, asserting with `assertSucceeds` and `assertFails` that allowed requests succeed and forbidden ones fail, and run the tests in CI with `firebase emulators:exec`.** ([Firebase security checklist, Unit test security rules with the Local Emulator Suite](https://firebase.google.com/support/guides/security-checklist#unit-test-security-rules-with-emulators), [Build unit tests](https://firebase.google.com/docs/rules/unit-tests), [Integrate with your CI system](https://firebase.google.com/docs/emulator-suite/install_and_configure#integrate_with_your_ci_system))
- `7` `FIREBASE-5` **Keep fields that not every reader may see in a separate document, such as a private subcollection with its own rules, because rules allow or deny reads of whole documents.** Rules are also not filters: a query fails unless its constraints guarantee that the user may read every document it could return. ([Firestore, Allowing read access only for specific fields](https://firebase.google.com/docs/firestore/security/rules-fields#allowing_read_access_only_for_specific_fields), [Securely query data: rules are not filters](https://firebase.google.com/docs/firestore/security/rules-query#rules_are_not_filters))
- `7` `FIREBASE-6` **If you use anonymous authentication, protect all non-public data with rules that require a permanent sign-in provider or a verified email address, because anyone can create an anonymous account.** Use anonymous accounts only to keep a user's state until they sign in. ([Firebase security checklist, Anonymous authentication](https://firebase.google.com/support/guides/security-checklist#use-security-rules-that-require-sign-in-method))

### App Check, API keys and Authentication

- `8` `FIREBASE-8` **Treat Firebase API keys and Remote Config values as public: restrict each API key to the APIs it needs, use a separate restricted key for any API that isn't a Firebase service, and never put a Gemini Developer API key, a service account key or another server credential in a client.** Firebase API keys only identify the project, and users can read every Remote Config parameter their app receives. This applies `SEC-11`. ([Learn about and manage API keys for Firebase](https://firebase.google.com/docs/projects/api-keys), [Use separate, restricted API keys for any non-Firebase service](https://firebase.google.com/docs/projects/api-keys#use-separate-keys-for-specific-apis), [Firebase security checklist, Keep service account keys secret](https://firebase.google.com/support/guides/security-checklist#keep-service-account-keys-secret), [Remote Config, Policies and limits](https://firebase.google.com/docs/remote-config#policies-and-limits))
- `7` `FIREBASE-7` **Enforce App Check for every product that supports it, such as Firestore, Realtime Database, Cloud Storage, Authentication and callable functions, once its request metrics show that your current app versions send valid tokens.** App Check checks that requests come from your app on a genuine device; it complements Authentication and Security Rules and doesn't replace them. For server-side integrity checks in mobile games, see `MOBGAME-11`. ([Firebase launch checklist, App Check](https://firebase.google.com/support/guides/launch-checklist#app-check), [Monitor App Check request metrics](https://firebase.google.com/docs/app-check/monitor-metrics), [Enable App Check enforcement](https://firebase.google.com/docs/app-check/enable-enforcement), [App Check and Firebase Authentication](https://firebase.google.com/docs/app-check#how_is_related_to))
- `7` `FIREBASE-9` **Harden Firebase Authentication before launch: disable the sign-in providers you don't use, enable email enumeration protection, tighten the quota of the sign-in endpoints, and allow only your own domains.** These settings limit account guessing and brute-force attempts (`AUTH-14`). ([Firebase security checklist, Authentication](https://firebase.google.com/support/guides/security-checklist#authentication), [Firebase launch checklist, Authentication](https://firebase.google.com/support/guides/launch-checklist#authentication))

### Projects and environments

- `8` `FIREBASE-10` **Use a separate Firebase project for each environment, such as development, staging and production, register debug and release builds in different projects, and don't put unrelated apps in one project.** All apps in a project share its databases, buckets, functions and Analytics property. Develop and test on the emulators with a `demo-` project ID, so that code can't reach live resources by mistake. This applies `SEC-16`. ([Firebase security checklist, Set up development and staging projects](https://firebase.google.com/support/guides/security-checklist#set-up-dev-and-staging-projects), [Registering app variants with Firebase projects](https://firebase.google.com/docs/projects/dev-workflows/general-best-practices#registering-app-variants), [Avoiding multi-tenancy](https://firebase.google.com/docs/projects/dev-workflows/general-best-practices#avoiding-multi-tenancy), [Local Emulator Suite, Choose a Firebase project](https://firebase.google.com/docs/emulator-suite/connect_firestore#choose_a_firebase_project))

### Firestore data and cost

- `7` `FIREBASE-11` **Model Firestore data around the queries your screens run and what they cost: each document a query returns, each document a listener receives when it's added or changed, and each document a rule reads with `get()` or `exists()` is billed as a read.** Page with `limit()` and cursors rather than offsets, which bill the skipped documents; use aggregation queries such as `count()`, or keep aggregates up to date at write time, instead of reading whole collections; and put lists that keep growing in subcollections, because a document can't exceed 1 MiB. ([Understand Cloud Firestore billing: listening to query results](https://firebase.google.com/docs/firestore/pricing#listens), [Managing large result sets](https://firebase.google.com/docs/firestore/pricing#large-result-sets), [Cloud Firestore Security Rules](https://firebase.google.com/docs/firestore/pricing#firestore-rules), [Write-time aggregations](https://firebase.google.com/docs/firestore/solutions/aggregation), [Choose a data structure](https://firebase.google.com/docs/firestore/manage-data/structure-data), [Usage and limits](https://firebase.google.com/docs/firestore/quotas))
- `7` `FIREBASE-12` **Turn on point-in-time recovery and scheduled backups for production Firestore databases.** Without PITR, you can read past versions of your data only from the last hour; with it, from the last seven days. Scheduled daily or weekly backups need the Blaze plan and are kept for the retention period you set. This is how Firestore follows `DATA-8`. ([Firestore, Point-in-time recovery: PITR window](https://firebase.google.com/docs/firestore/pitr#pitr_window), [Back up and restore data](https://firebase.google.com/docs/firestore/backups))

### Cloud Functions

- `7` `FIREBASE-13` **Give Cloud Functions their credentials through Secret Manager, with `defineSecret()` bound only to the functions that need each secret, not through `.env` files or `functions.config()`.** `functions.config()` is deprecated, and deployments that still use it fail after March 2027. This is how functions follow `SEC-2` and `GCP-8`. ([Configure your environment: store and access sensitive configuration](https://firebase.google.com/docs/functions/config-env#secret-manager), [Secret parameters](https://firebase.google.com/docs/functions/config-env#secret-parameters), [Migrate from runtime configuration](https://firebase.google.com/docs/functions/config-env#migrate-config))
- `7` `FIREBASE-14` **Make event-triggered functions idempotent, for example by using the event ID as an idempotency key, turn on retries only for transient errors, and test on the emulators that a function's writes can't trigger it again in a loop.** Event-driven functions run at least once for each event. This applies `DATA-9`. ([Retry asynchronous functions: best practices](https://firebase.google.com/docs/functions/retries#best_practices), [Tips and tricks: write idempotent functions](https://firebase.google.com/docs/functions/tips#write_idempotent_functions), [Firebase security checklist, Prevent self-DOSes](https://firebase.google.com/support/guides/security-checklist#test-functions-with-emulators))

### Costs

- `7` `FIREBASE-15` **Set budget alerts on every project on the pay-as-you-go Blaze plan, add spend caps for the services that support them, such as Cloud Functions, and limit each function's maximum number of instances to what normal traffic needs.** Budget alerts only notify you; they don't stop spending, and functions scale out automatically during an attack. This is how Firebase projects follow `OPS-17` and `GCP-13`. ([Firebase launch checklist, Know your pricing plan limits and set budget alerts](https://firebase.google.com/support/guides/launch-checklist#pricing-plan), [Avoid surprise bills: set up budgets](https://firebase.google.com/docs/projects/billing/avoid-surprise-bills#set-up-budgets), [Firebase security checklist, Configure your Cloud Functions to scale for normal traffic](https://firebase.google.com/support/guides/security-checklist#configure-functions-to-scale-for-normal-traffic), [Manage functions: limit the maximum number of instances](https://firebase.google.com/docs/functions/manage-functions#limit_the_maximum_number_of_instances_for_a_function))

### Privacy

- `7` `FIREBASE-16` **Where users must consent to analytics or crash reporting, set the Google Analytics consent defaults in the app's configuration, update them with `setConsent()` when the user decides, and turn on Crashlytics opt-in reporting.** By default, no consent values are set and Crashlytics collects crash reports from every user. This is how Firebase apps follow `PRIV-5` and `PRIV-6`. ([Google, Set up consent mode for apps](https://developers.google.com/tag-platform/security/guides/app-consent#default-consent), [Configure Analytics data collection and usage](https://firebase.google.com/docs/analytics/ios/configure-data-collection#temporarily-disable-collection), [Customize your Crashlytics crash reports: enable opt-in reporting](https://firebase.google.com/docs/crashlytics/customize-crash-reports#enable-reporting))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [Security Rules unit tests](https://firebase.google.com/docs/rules/unit-tests): `@firebase/rules-unit-testing` runs your tests against the emulators, and [`firebase emulators:exec`](https://firebase.google.com/docs/emulator-suite/install_and_configure#integrate_with_your_ci_system) starts the emulators for them in CI and stops them afterwards. Checks `FIREBASE-3`, and partly `FIREBASE-1`, `FIREBASE-4`, `FIREBASE-5` and `FIREBASE-6`, as far as the tests cover them.
- `6` [GitHub secret scanning push protection](https://docs.github.com/en/code-security/reference/secret-security/supported-secret-scanning-patterns): blocks pushes that contain Google Cloud service account credentials. Partly checks `FIREBASE-8`.
- `5` [@firebase/eslint-plugin-security-rules](https://github.com/firebase/eslint-tools): Firebase's ESLint plugin for `.rules` files, first released in 2026. Its `no-open-reads` and `no-open-writes` rules flag reads and writes allowed with `if true`. Partly checks `FIREBASE-1`.
