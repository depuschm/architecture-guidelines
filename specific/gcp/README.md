# Google Cloud

Scope: workloads on Google Cloud, from a single project to an enterprise organization. Cloud-neutral rules live elsewhere: least privilege (`SEC-1`) and secrets management (`SEC-2`) in [Security](../../general/security.md), SLOs, resilience and monitoring in [Operations and reliability](../../general/operations-reliability.md), Terraform itself in [Terraform](../terraform/README.md), and pipelines that deploy to Google Cloud in [GitHub Actions](../github-actions/README.md). For the other clouds, see [AWS](../aws/README.md) and [Microsoft Azure](../azure/README.md).

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Key rules

### Resource hierarchy

- `8` `GCP-1` **Use one organization resource, with folders for environments or other policy boundaries, and a separate project for each workload in each environment.** Design the hierarchy around policies and access, not around the company's org chart. ([Decide a resource hierarchy for your landing zone](https://docs.cloud.google.com/architecture/landing-zones/decide-resource-hierarchy), [Enterprise foundations blueprint, Organization structure](https://docs.cloud.google.com/architecture/blueprints/security-foundations/organization-structure))
- `6` `GCP-2` **Label projects and resources consistently, for example with application, environment, cost center and owner, and set the labels from infrastructure as code.** Billing reports can break costs down by label. Never put sensitive data in labels. ([Enterprise foundations blueprint, Organization structure](https://docs.cloud.google.com/architecture/blueprints/security-foundations/organization-structure), [Well-Architected Framework, Foster a culture of cost awareness](https://docs.cloud.google.com/architecture/framework/cost-optimization/foster-culture-cost-awareness), [Labels overview](https://docs.cloud.google.com/resource-manager/docs/labels-overview))

### Identity and access

- `9` `GCP-3` **Don't grant basic roles, such as Owner, Editor and Viewer, in production. Grant predefined or custom roles to groups, at the smallest scope that works.** Basic roles include thousands of permissions across all services. ([Use IAM securely: least privilege](https://docs.cloud.google.com/iam/docs/using-iam-securely#least_privilege), [Roles overview: basic roles](https://docs.cloud.google.com/iam/docs/roles-overview#basic))
- `9` `GCP-4` **Don't use service account keys: attach service accounts to workloads that run on Google Cloud, use Workload Identity Federation for CI pipelines and workloads elsewhere, and block key creation with an organization policy.** When you federate with GitHub or another multi-tenant identity provider, restrict the provider with an attribute condition (see `GHA-5` in [GitHub Actions](../github-actions/README.md)). ([Best practices for service accounts: use keys only when there is no alternative](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts#use-keys), [Workload Identity Federation with deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines), [Best practices for Workload Identity Federation: attribute conditions](https://docs.cloud.google.com/iam/docs/best-practices-for-using-workload-identity-federation#multi-tenant-attribute-conditions))
- `7` `GCP-5` **Give each application its own single-purpose service account instead of a default service account, and grant users the Service Account User and Token Creator roles on individual service accounts, not on projects or folders.** Default service accounts may hold the Editor role on their project. ([Best practices for service accounts: single-purpose service accounts](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts#single-purpose), [project and folder grants](https://docs.cloud.google.com/iam/docs/best-practices-service-accounts#project-folder-grants))

### Guardrails

- `8` `GCP-6` **Enforce the Google Cloud security baseline constraints in every organization, including organizations created before 3 May 2024, which may not have them.** They disable service account key creation and upload, stop default service accounts from getting the Editor role, restrict sharing to your own domains and require uniform bucket-level access. ([Manage Google Cloud security baseline constraints](https://docs.cloud.google.com/resource-manager/docs/manage-baseline-constraints))
- `7` `GCP-7` **Add further Organization Policy constraints at the organization or folder level, starting from the enterprise foundations blueprint's set, and test each new policy in dry-run mode before you enforce it.** ([Organization Policy overview](https://docs.cloud.google.com/organization-policy/overview), [Enterprise foundations blueprint, Preventative controls](https://docs.cloud.google.com/architecture/blueprints/security-foundations/preventative-controls))

### Data protection

- `6` `GCP-8` **Keep secrets in Secret Manager, grant access per secret when one project holds secrets for many services, and reference secret versions by number instead of `latest`.** ([Secret Manager best practices](https://docs.cloud.google.com/secret-manager/docs/best-practices))
- `5` `GCP-9` **Put projects that hold sensitive data, for example in Cloud Storage or BigQuery, inside VPC Service Controls perimeters in addition to IAM, and run each new perimeter in dry-run mode first.** Careless enablement can break applications. ([Overview of VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/overview), [Best practices for enabling VPC Service Controls](https://docs.cloud.google.com/vpc-service-controls/docs/enable))

### Reliability

- `9` `GCP-10` **Deploy production workloads across multiple zones, and across regions where your availability or recovery targets require it.** A zonal resource, such as a Compute Engine VM, is affected when its zone has an outage. ([Compute Engine, Regions and zones](https://docs.cloud.google.com/compute/docs/regions-zones), [Well-Architected Framework, Build highly available systems through resource redundancy](https://docs.cloud.google.com/architecture/framework/reliability/build-highly-available-systems), [Google Cloud deployment archetypes](https://docs.cloud.google.com/architecture/deployment-archetypes))

### Delivery and operations

- `9` `GCP-11` **Manage the organization's foundation and all workloads as code with Terraform, applied from a pipeline that validates changes against your policies, as the enterprise foundations blueprint does.** ([Well-Architected Framework, Automate and manage change](https://docs.cloud.google.com/architecture/framework/operational-excellence/automate-and-manage-change), [Enterprise foundations blueprint, Deployment methodology](https://docs.cloud.google.com/architecture/blueprints/security-foundations/deployment-methodology), [Terraform blueprints and modules for Google Cloud](https://docs.cloud.google.com/docs/terraform/blueprints/terraform-blueprints))
- `7` `GCP-12` **Route audit logs from the whole organization to a central project with an aggregated sink, and turn on Data Access audit logs for services that handle sensitive data.** Except for BigQuery, Data Access audit logs are off by default. ([Cloud Logging, Aggregated sinks](https://docs.cloud.google.com/logging/docs/export/aggregated_sinks), [Cloud Audit Logs overview](https://docs.cloud.google.com/logging/docs/audit), [Enterprise foundations blueprint, Detective controls](https://docs.cloud.google.com/architecture/blueprints/security-foundations/detective-controls))
- `7` `GCP-13` **Create Cloud Billing budgets with alert thresholds for each billing account or project, and send the alerts to the owners or to Pub/Sub for automated responses.** An alerts-only budget doesn't cap spending. ([Cloud Billing, Create, edit, or delete budgets and budget alerts](https://docs.cloud.google.com/billing/docs/how-to/budgets))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [Organization Policy constraints](https://docs.cloud.google.com/organization-policy/reference/org-policy-constraints): the Organization Policy service enforces them, so resource configurations that break them can't be created. The baseline constraints include `iam.managed.disableServiceAccountKeyCreation`, `iam.disableServiceAccountKeyUpload`, `iam.automaticIamGrantsForDefaultServiceAccounts`, `iam.allowedPolicyMemberDomains` and `storage.uniformBucketLevelAccess`. Checks `GCP-6`, and partly `GCP-4`.
- `6` [Security Command Center, Compliance Manager cloud controls](https://docs.cloud.google.com/security-command-center/docs/compliance-manager-cloud-controls): continuous detective controls, which [replace Security Health Analytics](https://docs.cloud.google.com/security-command-center/docs/concepts-security-health-analytics) for new activations, such as [Restrict Legacy IAM Roles](https://docs.cloud.google.com/security-command-center/docs/compliance-manager-cloud-controls#restrict-legacy-iam-roles), [Restrict User Managed Service Account Keys](https://docs.cloud.google.com/security-command-center/docs/compliance-manager-cloud-controls#restrict-user-managed-service-account-keys), [Block Service Account Key Creation](https://docs.cloud.google.com/security-command-center/docs/compliance-manager-cloud-controls#block-service-account-key-creation), [Use Custom Service Accounts for Compute Engine Instances](https://docs.cloud.google.com/security-command-center/docs/compliance-manager-cloud-controls#define-non-default-service-account), [Define Service Perimeters in VPC Service Controls](https://docs.cloud.google.com/security-command-center/docs/compliance-manager-cloud-controls#define-service-perimeter) and [Enable Audit Logs for All Services](https://docs.cloud.google.com/security-command-center/docs/compliance-manager-cloud-controls#enable-audit-logs-for-allservices). All except Restrict User Managed Service Account Keys need the Premium tier. Partly checks `GCP-3`, `GCP-4`, `GCP-5`, `GCP-6`, `GCP-9` and `GCP-12`.
- `6` [IAM role recommendations](https://docs.cloud.google.com/policy-intelligence/docs/role-recommendations-overview) (Policy Intelligence): compare each principal's permissions with what it used in the last 90 days, and recommend removing or replacing roles, for example [to replace basic roles](https://docs.cloud.google.com/iam/docs/using-iam-securely#least_privilege). Partly checks `GCP-3`.
- `6` [Checkov Terraform policies](https://www.checkov.io/5.Policy%20Index/terraform.html): misconfiguration checks before deployment, including basic roles at organization, folder and project level (`CKV_GCP_115` to `CKV_GCP_117`), user-managed service account keys (`CKV2_GCP_3`), VMs using the default service account (`CKV_GCP_30`), project-level Service Account User or Token Creator grants (`CKV_GCP_41`) and audit logging for all services (`CKV2_GCP_5`). Partly checks `GCP-3`, `GCP-4`, `GCP-5` and `GCP-12`.
