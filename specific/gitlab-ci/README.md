# GitLab CI/CD

Scope: designing CI/CD pipelines on GitLab CI/CD, including CI/CD components, merge request pipelines, runners and deployments. Pipelines run with access to your code, secrets and cloud accounts, so many rules here are about keeping them secure. [GitHub Actions](../github-actions/README.md) covers the same concerns on GitHub. For general secrets and supply-chain rules, see [Security](../../general/security.md); for building container images, see [Docker](../docker/README.md).

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Key rules

### Security

- `9` `GITLAB-1` **Pin every `include` and CI/CD component to a commit SHA or to a release tag you trust, pin job images by digest, and let a bot such as Renovate propose updates.** Avoid `~latest`, branch names and versionless includes, and copy remote files into the repository or pin them with `include:integrity`. ([GitLab, Pipeline security: included configurations](https://docs.gitlab.com/ci/pipeline_security/#included-configurations), [Docker images](https://docs.gitlab.com/ci/pipeline_security/#docker-images), [CI/CD component security best practices](https://docs.gitlab.com/ci/components/#cicd-component-security-best-practices), [include:integrity](https://docs.gitlab.com/ci/yaml/#includeintegrity), [Renovate, GitLab CI/CD manager](https://docs.renovatebot.com/modules/manager/gitlabci/))
- `9` `GITLAB-2` **Keep secrets in an external secrets manager. If a secret must be a CI/CD variable, make it masked and hidden, and protected so that only pipelines for protected branches and tags receive it.** Masking only keeps values out of job logs: code that runs in the job can still read and send them. ([GitLab, Pipeline security: secrets storage](https://docs.gitlab.com/ci/pipeline_security/#secrets-storage), [CI/CD variables: protect](https://docs.gitlab.com/ci/variables/#protect-a-cicd-variable), [mask](https://docs.gitlab.com/ci/variables/#mask-a-cicd-variable), [hide](https://docs.gitlab.com/ci/variables/#hide-a-cicd-variable))
- `8` `GITLAB-3` **Authenticate to cloud providers and secret managers with ID tokens (`id_tokens`) instead of stored credentials, and restrict the trust policy to specific projects and protected branches or tags.** Where the provider supports it, add stable claims such as `project_id` to the `sub` claim, so that the policy isn't affected when a project or group is renamed or moved. ([GitLab, Use ID token claims in cloud trust policies](https://docs.gitlab.com/ci/secrets/id_token_authentication/#use-id-token-claims-in-cloud-trust-policies), [Configure a conditional role with OIDC claims](https://docs.gitlab.com/ci/cloud_services/#configure-a-conditional-role-with-oidc-claims))
- `8` `GITLAB-4` **Run a pipeline in the parent project for a merge request from a fork only after reviewing its changes, including changes to `.gitlab-ci.yml`.** That pipeline runs the fork's CI configuration with the parent project's variables and runners, and with the permissions of the person who starts it. ([GitLab, Run pipelines in the parent project](https://docs.gitlab.com/ci/pipelines/merge_request_pipelines/#run-pipelines-in-the-parent-project), [CI/CD variable security](https://docs.gitlab.com/ci/variables/#cicd-variable-security))
- `8` `GITLAB-5` **Don't use the shell executor or privileged Docker containers on runners that run jobs from several projects or untrusted users. Run privileged jobs only on isolated, ephemeral machines, and let runners that hold secrets or run privileged jobs take jobs from protected branches only.** ([GitLab, Security risks for different executors](https://docs.gitlab.com/runner/security/#security-risks-for-different-executors), [Reduce the security risk of privileged containers](https://docs.gitlab.com/runner/security/#reduce-the-security-risk-of-using-privileged-containers), [Prevent runners from revealing sensitive information](https://docs.gitlab.com/ci/runners/configure_runners/#prevent-runners-from-revealing-sensitive-information))
- `7` `GITLAB-6` **Keep the CI/CD job token allowlist enabled, and add only the groups and projects that need cross-project access.** With the allowlist turned off, jobs in any project can use their job token to access your project. ([GitLab, Control job token access to your project](https://docs.gitlab.com/ci/jobs/ci_job_token/#control-job-token-access-to-your-project), [Allow any project to access your project](https://docs.gitlab.com/ci/jobs/ci_job_token/#allow-any-project-to-access-your-project))
- `7` `GITLAB-7` **Pass parameters to pipelines as typed CI/CD inputs, and set the minimum role to use pipeline variables to `no_one_allowed` or Maintainer.** Where an input reaches a script, restrict it with a number or boolean type, `regex` or `options`: `posix_escape` doesn't make untrusted values safe. ([GitLab, Pipeline security: pass parameters](https://docs.gitlab.com/ci/pipeline_security/#pass-parameters-to-cicd-pipelines), [Restrict pipeline variables](https://docs.gitlab.com/ci/variables/#restrict-pipeline-variables), [CI/CD inputs: posix_escape](https://docs.gitlab.com/ci/inputs/#posix_escape))
- `6` `GITLAB-8` **Never commit `CI_DEBUG_TRACE` to CI configuration, and turn on debug logging only temporarily, while only team members can view job logs.** Debug logs contain every variable and secret available to the job. ([GitLab, Enable debug logging](https://docs.gitlab.com/ci/variables/variables_troubleshooting/#enable-debug-logging))
- `6` `GITLAB-9` **Keep separate caches for protected and unprotected branches, which is the default, and don't set `cache:unprotect`. Pass build outputs between jobs as artifacts, and use the cache only for dependencies such as downloaded packages.** ([GitLab, Use the same cache for all branches](https://docs.gitlab.com/ci/caching/#use-the-same-cache-for-all-branches), [cache:unprotect](https://docs.gitlab.com/ci/yaml/#cacheunprotect), [How cache is different from artifacts](https://docs.gitlab.com/ci/caching/#how-cache-is-different-from-artifacts))
- `6` `GITLAB-10` **Require Code Owner approval for changes to `.gitlab-ci.yml` and other CI configuration on protected branches.** Code Owner approval needs GitLab Premium or Ultimate. ([GitLab, Require Code Owner approval](https://docs.gitlab.com/user/project/repository/branches/protected/#require-code-owner-approval), [Code Owners](https://docs.gitlab.com/user/project/codeowners/), [CI/CD variable security](https://docs.gitlab.com/ci/variables/#cicd-variable-security))

### Pipeline design

- `7` `GITLAB-11` **Use `rules` instead of the deprecated `only` and `except`, and don't mix them in one pipeline. Add `workflow:rules` that choose between branch and merge request pipelines, so that a push to a branch with an open merge request doesn't start two pipelines.** ([GitLab, Deprecated keywords: only and except](https://docs.gitlab.com/ci/yaml/deprecated_keywords/#only--except), [Avoid duplicate pipelines](https://docs.gitlab.com/ci/jobs/job_rules/#avoid-duplicate-pipelines), [Switch between branch and merge request pipelines](https://docs.gitlab.com/ci/yaml/workflow/#switch-between-branch-pipelines-and-merge-request-pipelines))
- `6` `GITLAB-12` **Run merge request pipelines, and enable merged results pipelines so that each merge request is tested combined with the latest target branch. Add merge trains when many merge requests are ready to merge at the same time.** Merged results pipelines and merge trains need GitLab Premium or Ultimate. ([GitLab, Merge request pipelines](https://docs.gitlab.com/ci/pipelines/merge_request_pipelines/), [Merged results pipelines](https://docs.gitlab.com/ci/pipelines/merged_results_pipelines/), [Merge trains](https://docs.gitlab.com/ci/pipelines/merge_trains/))
- `6` `GITLAB-13` **Declare job dependencies with `needs`, so that each job starts as soon as the jobs it depends on finish, and give jobs that depend on nothing, such as linters, `needs: []`.** ([GitLab, Make jobs start earlier with needs](https://docs.gitlab.com/ci/yaml/needs/))
- `6` `GITLAB-14` **Share CI configuration as versioned CI/CD components with inputs instead of copying YAML between projects.** In components, replace hardcoded values with inputs and avoid global keywords, which would change every job in the including pipeline. ([GitLab, CI/CD components](https://docs.gitlab.com/ci/components/), [Replace hardcoded values with inputs](https://docs.gitlab.com/ci/components/#replace-hardcoded-values-with-inputs), [Avoid using global keywords](https://docs.gitlab.com/ci/components/#avoid-using-global-keywords), [Pipeline efficiency: reuse configuration](https://docs.gitlab.com/ci/pipelines/pipeline_efficiency/#reuse-configuration-with-cicd-components))

### Deployments

- `7` `GITLAB-15` **Deploy to production only through a protected environment: limit who can deploy, require deployment approvals, and scope production variables to that environment.** Protected environments and deployment approvals need GitLab Premium or Ultimate. ([GitLab, Deployment safety: protect production secrets](https://docs.gitlab.com/ci/environments/deployment_safety/#protect-production-secrets), [Protected environments](https://docs.gitlab.com/ci/environments/protected_environments/), [Deployment approvals](https://docs.gitlab.com/ci/environments/deployment_approvals/), [CI/CD variables: environment scope](https://docs.gitlab.com/ci/variables/#environment-scope))
- `7` `GITLAB-16` **Give each deployment job a `resource_group`, so that only one deployment to an environment runs at a time, and turn on "Prevent outdated deployment jobs".** Otherwise an older pipeline can finish last and overwrite a newer deployment. ([GitLab, Ensure only one deployment job runs at a time](https://docs.gitlab.com/ci/environments/deployment_safety/#ensure-only-one-deployment-job-runs-at-a-time), [Prevent outdated deployment jobs](https://docs.gitlab.com/ci/environments/deployment_safety/#prevent-outdated-deployment-jobs), [Resource group](https://docs.gitlab.com/ci/resource_groups/))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [CI Lint](https://docs.gitlab.com/ci/yaml/lint/): GitLab's built-in validation of `.gitlab-ci.yml`, with its includes, which can also simulate pipeline creation. Run it in the pipeline editor, with [`glab ci lint`](https://docs.gitlab.com/cli/ci/lint/) or through the [CI Lint API](https://docs.gitlab.com/api/lint/). Its [pipeline warnings](https://docs.gitlab.com/ci/debugging/#job-may-allow-multiple-pipelines-to-run-for-a-single-action-warning) flag rules that can start duplicate pipelines. Partly checks `GITLAB-11`.
- `7` [GitLab CI/CD settings](https://docs.gitlab.com/ci/variables/#restrict-pipeline-variables): setting "Minimum role to use pipeline variables" to `no_one_allowed` blocks pipeline variables. Other settings keep the [job token allowlist](https://docs.gitlab.com/ci/jobs/ci_job_token/#control-job-token-access-to-your-project) on (administrators of self-managed instances can enforce it for every project), keep [separate caches for protected branches](https://docs.gitlab.com/ci/caching/#use-the-same-cache-for-all-branches), and turn on [Prevent outdated deployment jobs](https://docs.gitlab.com/ci/pipelines/settings/#prevent-outdated-deployment-jobs). Partly checks `GITLAB-6`, `GITLAB-7`, `GITLAB-9` and `GITLAB-16`.
- `5` [Plumber](https://getplumber.io/docs/cli/issues): a CI/CD security scanner for GitLab CI and GitHub Actions, run as a CLI or a GitLab CI/CD component. Its GitLab controls flag includes on forbidden versions such as `latest`, `main` or `HEAD`, images not pinned by digest, unprotected and unmasked variables, and pipelines that enable `CI_DEBUG_TRACE`. Partly checks `GITLAB-1`, `GITLAB-2` and `GITLAB-8`.
- `5` [poutine](https://boostsecurityio.github.io/poutine/rules/debug_enabled/): a build pipeline scanner for GitHub Actions and GitLab CI. For GitLab, it flags `CI_DEBUG_TRACE`, and its [injection rule](https://github.com/boostsecurityio/poutine/blob/main/opa/rego/rules/injection.rego) flags inputs interpolated with `expand_vars` into scripts. Partly checks `GITLAB-7` and `GITLAB-8`.
- `5` [Checkov GitLab CI checks](https://www.checkov.io/5.Policy%20Index/gitlab_ci.html): `CKV_GITLABCI_2` flags job rules that create duplicate pipelines. Partly checks `GITLAB-11`.
