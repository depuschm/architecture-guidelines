# Go

Scope: services, command-line tools and game servers written in Go, on the two releases the Go team supports: Go 1.27 (August 2026) and Go 1.26 (February 2026). Go 1.25 stopped receiving fixes when Go 1.27 came out. For configuration, health checks, telemetry and resilience, follow [general/operations-reliability.md](../../general/operations-reliability.md); for secrets, authorization and the supply chain, [general/security.md](../../general/security.md); for test strategy and CI, the `TEST` rules in [general/testing-delivery.md](../../general/testing-delivery.md); for container images, [Docker](../docker/README.md); for databases, [PostgreSQL](../postgres/README.md); and for hosting, scaling and securing game servers, [Game servers and online services](../game-servers/README.md). The rules here cover what is specific to Go.

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Adopted references

- `9` [Go Style](https://google.github.io/styleguide/go/) (Google): **the baseline for code style**: the canonical [Style Guide](https://google.github.io/styleguide/go/guide), the normative [Style Decisions](https://google.github.io/styleguide/go/decisions), and [Best Practices](https://google.github.io/styleguide/go/best-practices) for naming, package size, errors, interfaces, concurrency, contexts, global state and tests. A few points refer to Google's internal libraries, such as its own `log` package.
- `8` [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments) (Go wiki): the comments most often made in Go code reviews, such as contexts, goroutine lifetimes, error handling, interfaces and package names, each with a short name to cite in a review. [Go Test Comments](https://go.dev/wiki/TestComments) adds those for tests.
- `8` [Security Best Practices for Go Developers](https://go.dev/doc/security/best-practices) (Go): scanning for known vulnerabilities with govulncheck, keeping Go and dependencies up to date, fuzzing, the race detector and `go vet`.
- `8` [Organizing a Go module](https://go.dev/doc/modules/layout) (Go): the official layouts for a package, a command, a module with several commands, and a server project, with `internal/` and `cmd/` directories.
- `8` [Go Modules Reference](https://go.dev/ref/mod) (Go): `go.mod` and `go.sum`, minimal version selection, module proxies, the checksum database and private modules.
- `7` [Effective Go](https://go.dev/doc/effective_go) (Go): idiomatic use of the core language, including interfaces, concurrency, errors, `panic` and `recover`. It was written for Go's release in 2009 and isn't actively updated, so it doesn't cover generics, modules or newer libraries.
- `7` [Release History](https://go.dev/doc/devel/release) (Go): the release policy, under which each major release is supported until there are two newer major releases, and what each minor release fixed.
- `7` [Accessing relational databases](https://go.dev/doc/database/) (Go): the `database/sql` guides to opening a handle, querying, transactions, cancellation, the connection pool and avoiding SQL injection.
- `7` [A Guide to the Go Garbage Collector](https://go.dev/doc/gc-guide) (Go): how `GOGC` and the memory limit (`GOMEMLIMIT`) trade memory for CPU time. It advises a memory limit, with 5–10% headroom, for a service in a container with a fixed memory limit, and none for a command-line tool whose memory use depends on its input.
- `6` [Go Runtime](https://heroiclabs.com/docs/nakama/server-framework/go-runtime/) (Heroic Labs, Nakama): writing Nakama server modules in Go. The plugin must be built for the same platform, with the same Go version and the same versions of shared dependencies as the Nakama binary; [Dependency Pinning](https://heroiclabs.com/docs/nakama/server-framework/go-runtime/go-dependencies/) explains how.

## Key rules

### Code structure

- `6` `GO-1` **Lay out a service as "Organizing a Go module" describes for a server project: each command in `cmd/<name>/`, the packages that implement them under `internal/`, and each package named for what it provides, not `util`, `common` or `helper`.** Other modules can't import packages under `internal/`, so you can refactor them freely; move code into a module of its own only when other projects need it. ([Go, Organizing a Go module: Server project](https://go.dev/doc/modules/layout#server-project), [Go Code Review Comments, Package names](https://go.dev/wiki/CodeReviewComments#package-names), [Go Style, Util packages](https://google.github.io/styleguide/go/best-practices#util-packages), [Go blog, Package names](https://go.dev/blog/package-names#bad-package-names))
- `6` `GO-2` **Define interfaces in the package that uses them, keep them small, and return concrete types; don't add an interface before a consumer needs it, and don't export one from the implementing package only so that it can be mocked.** Likewise, use type parameters only when you would otherwise write the same code for several types, and an interface when you only call methods. ([Go Code Review Comments, Interfaces](https://go.dev/wiki/CodeReviewComments#interfaces), [Go Style, Interfaces](https://google.github.io/styleguide/go/decisions#interfaces), [Go blog, When To Use Generics](https://go.dev/blog/when-generics#one-simple-guideline), [Go Style, Generics](https://google.github.io/styleguide/go/decisions#generics))

### Errors

- `7` `GO-3` **Check every error, then either handle it or return it with added context, not both: don't discard errors with `_`, and don't log an error that you return.** Wrap with `%w` only when callers may need to inspect the cause, because the wrapped error becomes part of your API, and inspect errors with `errors.Is` and `errors.As` (or `errors.AsType` from Go 1.26), which also match wrapped errors, rather than with `==`, type assertions or string matching. ([Go Code Review Comments, Handle errors](https://go.dev/wiki/CodeReviewComments#handle-errors), [Go Style, Logging errors](https://google.github.io/styleguide/go/best-practices#error-logging), [Go blog, Whether to wrap](https://go.dev/blog/go1.13-errors#whether-to-wrap), [Go, errors package](https://pkg.go.dev/errors), [Go Style, Error structure](https://google.github.io/styleguide/go/best-practices#error-structure))
- `7` `GO-4` **Return an `error` for every failure a caller can expect, such as invalid input, failed I/O or bad configuration, and panic only for bugs that tests and reviews should catch, such as API misuse or a broken invariant. In a server, recover at the top of each goroutine that serves one connection, job or match.** A panic that reaches the top of any goroutine ends the whole process, with every other request or match in it; `net/http` recovers panics in `ServeHTTP`, but not in goroutines that a handler starts. ([Go Code Review Comments, Don't panic](https://go.dev/wiki/CodeReviewComments#dont-panic), [Go Style, When to panic](https://google.github.io/styleguide/go/best-practices#when-to-panic), [Effective Go, Recover](https://go.dev/doc/effective_go#recover), [Go spec, Handling panics](https://go.dev/ref/spec#Handling_panics), [net/http, Handler](https://pkg.go.dev/net/http#Handler))

### Context and concurrency

- `8` `GO-5` **Pass the request's `context.Context` along the whole call chain, from the incoming request to every outgoing call, as the first parameter, named `ctx`; never store it in a struct, and use the context-aware APIs, such as `QueryContext` and `http.NewRequestWithContext`.** Deadlines and cancellation then reach the database and the services you call: set the timeouts that `OPS-3` asks for with `context.WithTimeout`, and always call the `cancel` function it returns. Never pass a nil context. ([Go, context package](https://pkg.go.dev/context), [Go Code Review Comments, Contexts](https://go.dev/wiki/CodeReviewComments#contexts), [Go blog, Contexts and structs](https://go.dev/blog/context-and-structs), [Go, Canceling in-progress operations](https://go.dev/doc/database/cancel-operations))
- `8` `GO-7` **Never share a variable between goroutines without synchronization: hand data over on channels, or guard shared state, such as a cache, with a `sync.Mutex`, and run the tests with the race detector (`go test -race`) in CI.** The race detector finds only races in code that runs, so it needs tests that exercise the concurrent paths, and it typically makes programs 2 to 20 times slower. ([Effective Go, Share by communicating](https://go.dev/doc/effective_go#sharing), [Go wiki, Use a sync.Mutex or a channel?](https://go.dev/wiki/MutexOrChannel), [Go Security Best Practices, Race detector](https://go.dev/doc/security/best-practices#check-for-race-conditions-with-gos-race-detector), [Go, Data Race Detector](https://go.dev/doc/articles/race_detector))
- `7` `GO-6` **Make it obvious when each goroutine you start will end: give it a context to stop on, and wait for it with a `sync.WaitGroup` or an `errgroup.Group` from `golang.org/x/sync` before the code that started it returns or shuts down.** A goroutine blocked forever on a channel is never freed, and goroutines left running make memory use unpredictable. Prefer synchronous functions and let callers add concurrency. `errgroup.WithContext` cancels the group's context when one goroutine fails, and Go 1.27's `goroutineleak` profile reports many leaks. ([Go Code Review Comments, Goroutine lifetimes](https://go.dev/wiki/CodeReviewComments#goroutine-lifetimes), [Synchronous functions](https://go.dev/wiki/CodeReviewComments#synchronous-functions), [Go Style, Goroutine lifetimes](https://google.github.io/styleguide/go/decisions#goroutine-lifetimes), [errgroup package](https://pkg.go.dev/golang.org/x/sync/errgroup), [Go 1.27, Goroutine leak profile](https://go.dev/doc/go1.27#goroutineleak-profiles))

### HTTP servers

- `7` `GO-8` **Create every `http.Server` yourself and set its timeouts: always `ReadHeaderTimeout` and `IdleTimeout`, and `ReadTimeout` and `WriteTimeout` too unless handlers set their own deadlines. Don't serve with `http.ListenAndServe` or `http.Serve`, which can't set timeouts.** A zero timeout means no timeout, so a slow client can hold a connection and its goroutine as long as it likes. Handlers that need longer, such as uploads or streams, can extend their deadlines with `http.ResponseController`; limit request bodies with `http.MaxBytesReader`. This applies `API-11`. ([net/http, Server](https://pkg.go.dev/net/http#Server), [net/http, ResponseController](https://pkg.go.dev/net/http#ResponseController), [net/http, MaxBytesReader](https://pkg.go.dev/net/http#MaxBytesReader), [gosec, G112 and G114](https://github.com/securego/gosec/blob/master/RULES.md))
- `7` `GO-9` **Shut down on `SIGTERM`: derive the root context from `signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)`, and when it's done, call `Server.Shutdown` with a deadline shorter than the platform's grace period.** By default a `SIGTERM` makes a Go program exit. `Shutdown` stops listening and waits for active connections to go idle, but not for hijacked connections such as WebSockets: tell those to close from a function registered with `RegisterOnShutdown`. This applies `OPS-15` and `K8S-3`. ([os/signal, Default behavior of signals](https://pkg.go.dev/os/signal#hdr-Default_behavior_of_signals_in_Go_programs), [os/signal, NotifyContext](https://pkg.go.dev/os/signal#NotifyContext), [net/http, Server.Shutdown](https://pkg.go.dev/net/http#Server.Shutdown), [net/http, Server.RegisterOnShutdown](https://pkg.go.dev/net/http#Server.RegisterOnShutdown))

### Logging

- `6` `GO-10` **Log with `log/slog`: in a service, set a JSON handler on stdout as the default logger, with `slog.SetDefault(slog.New(slog.NewJSONHandler(os.Stdout, nil)))`, call the `...Context` logging methods so that handlers can add trace context, and give types that hold secrets a `LogValue` method that redacts them.** After `SetDefault`, the standard `log` package writes through the same handler. This applies `OPS-16` and `SEC-4`. ([Go blog, Structured Logging with slog](https://go.dev/blog/slog), [log/slog, Contexts](https://pkg.go.dev/log/slog#hdr-Contexts), [log/slog, SetDefault](https://pkg.go.dev/log/slog#SetDefault), [log/slog, Customizing a type's logging behavior](https://pkg.go.dev/log/slog#hdr-Customizing_a_type_s_logging_behavior))

### Dependencies and toolchain

- `8` `GO-12` **Build with a supported Go release, one of the two newest major versions, at its latest minor version, and run `govulncheck` on every change in CI and regularly on the code or binaries you have deployed.** The Go team fixes critical problems, including security problems, in the supported releases by issuing minor releases. Set the `toolchain` line in `go.mod` to the release you build with, so that the `go` command, with its default `GOTOOLCHAIN=auto`, switches to it when a local toolchain is older. This applies `SEC-17`. ([Go, Release policy](https://go.dev/doc/devel/release#policy), [Go Security Best Practices, Keep your Go version and dependencies up to date](https://go.dev/doc/security/best-practices#keep-your-go-version-and-dependencies-up-to-date), [Scan source code and binaries](https://go.dev/doc/security/best-practices#scan-source-code-and-binaries-for-vulnerabilities), [Go Toolchains](https://go.dev/doc/toolchain), [govulncheck](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck))
- `7` `GO-11` **Commit `go.mod` and `go.sum`, change dependencies only with `go get` or `go mod tidy` in a reviewed change, and fail CI when `go mod tidy -diff` reports a difference.** Keep the public module proxy and checksum database for public modules, and list private modules in `GOPRIVATE`, which keeps them away from both, instead of setting `GOSUMDB=off`, which stops checking any module against the checksum database. This applies `SEC-15`. ([Go blog, How Go Mitigates Supply Chain Attacks](https://go.dev/blog/supply-chain), [Go wiki, Should I commit my go.sum file?](https://go.dev/wiki/Modules#should-i-commit-my-gosum-file-as-well-as-my-gomod-file), [Go Modules Reference, go mod tidy](https://go.dev/ref/mod#go-mod-tidy), [Private modules](https://go.dev/ref/mod#private-modules), [Authenticating modules](https://go.dev/ref/mod#authenticating))

### Data and output

- `9` `GO-13` **Never build SQL statements or HTML by formatting or concatenating strings with values: pass values to SQL as arguments for placeholders (`?` or `$1`), and render HTML with `html/template`, not `text/template`.** Convert a value to `template.HTML` or another of its trusted types only if it comes from a trusted source or a sound HTML sanitizer, because it is inserted without escaping. This applies `SEC-18` and `WEB-8`. ([Go, Avoiding SQL injection risk](https://go.dev/doc/database/sql-injection), [html/template](https://pkg.go.dev/html/template), [html/template, HTML](https://pkg.go.dev/html/template#HTML))
- `7` `GO-14` **Open one `sql.DB` for each database when the program starts and share it, because it is a connection pool that is safe for concurrent use, and close every `sql.Rows` with `defer rows.Close()` and check `rows.Err()`.** By default the pool opens a new connection whenever all are busy, with no limit: if all your instances together could open more connections than the database accepts, cap them with `SetMaxOpenConns`, so that callers wait for a free connection, or add a pooler (`PG-9`). ([Go, database/sql Open](https://pkg.go.dev/database/sql#Open), [Go, Managing connections](https://go.dev/doc/database/manage-connections), [Go, Querying for data: multiple rows](https://go.dev/doc/database/querying#multiple_rows))

### Testing and code quality

- `7` `GO-15` **In CI, fail the build on unformatted code (`gofmt -l`), on any `go vet ./...` finding and on linter findings, for example from Staticcheck or golangci-lint.** `go test` runs only a high-confidence subset of the vet checks, which leaves out checks such as `lostcancel` and `copylocks`, so run `go vet` on its own. ([Go Code Review Comments, Gofmt](https://go.dev/wiki/CodeReviewComments#gofmt), [Go Style Guide, Formatting](https://google.github.io/styleguide/go/guide#formatting), [go command, Test packages](https://pkg.go.dev/cmd/go#hdr-Test_packages), [Go, cmd/vet](https://pkg.go.dev/cmd/vet), [Staticcheck](https://staticcheck.dev/docs/))
- `6` `GO-16` **Fuzz the code that parses untrusted input, such as request decoders and network protocol handlers, with `go test -fuzz`, and test code with timers, timeouts or background goroutines inside `synctest.Test` instead of waiting in real time.** Commit the failing inputs that fuzzing saves under `testdata/fuzz`, which `go test` then runs as regression tests. `synctest.Test` runs the test on a fake clock, waits for its goroutines to exit, and fails if they deadlock. ([Go Security Best Practices, Fuzzing](https://go.dev/doc/security/best-practices#test-with-fuzzing-to-uncover-edge-case-exploits), [Go Fuzzing](https://go.dev/doc/security/fuzz/), [testing/synctest](https://pkg.go.dev/testing/synctest))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [go vet](https://pkg.go.dev/cmd/vet): `go vet ./...` exits with a non-zero status when it reports a problem. Its `lostcancel` check reports `cancel` functions that aren't called on every path, `copylocks` reports locks copied by value, `errorsas` reports wrong arguments to `errors.As`, and from [Go 1.27](https://go.dev/doc/go1.27#vet) `printf` reports `%w` operands that are pointers to an error type. Checks `GO-15`, and partly `GO-3` and `GO-5`.
- `7` [Data Race Detector](https://go.dev/doc/articles/race_detector): `go test -race` reports the data races that happen while the tests run, with the stacks of the conflicting accesses, and exits with a non-zero status (66 by default). Partly checks `GO-7`.
- `7` [go mod tidy -diff](https://go.dev/ref/mod#go-mod-tidy): prints the changes that `go.mod` and `go.sum` need without making them, and exits with a non-zero status if there are any; [`go mod verify`](https://go.dev/ref/mod#go-mod-verify) fails when a downloaded module in the cache has changed. Partly checks `GO-11`.
- `6` [gofmt](https://pkg.go.dev/cmd/gofmt): `gofmt -l .` lists the files whose formatting differs from gofmt's; fail CI when it lists any. Partly checks `GO-15`.
- `6` [govulncheck exit codes](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck#hdr-Exit_codes): `govulncheck ./...` exits with a non-zero status when it finds known vulnerabilities, in the standard library or in dependencies, that affect the code, unless you ask for JSON, SARIF or OpenVEX output. It analyzes source code with the Go version on the `PATH`, and a binary with the version that built it, so it covers that release's standard library too. Partly checks `GO-12`.
- `6` [golangci-lint](https://golangci-lint.run/docs/linters/): runs many linters in one pass, with errcheck, govet, ineffassign, staticcheck and unused on by default; errcheck reports unchecked errors. Also enable [errorlint](https://golangci-lint.run/docs/linters/configuration/#errorlint) with its `comparison` and `asserts` checks, for errors compared with `==` or type assertions, [containedctx](https://golangci-lint.run/docs/linters/configuration/#containedctx) for contexts stored in structs, [noctx](https://golangci-lint.run/docs/linters/configuration/#noctx) for HTTP, network and database calls made without a context, and [sloglint](https://golangci-lint.run/docs/linters/configuration/#sloglint) with `context: all` for `slog` calls without a context. Checks `GO-15`, and partly `GO-3`, `GO-5` and `GO-10`.
- `6` [gosec](https://github.com/securego/gosec/blob/master/RULES.md): G112 reports an `http.Server` without `ReadHeaderTimeout`, G114 the `net/http` serve functions that can't set timeouts, G201 and G202 SQL built with format strings or concatenation, G203 unescaped data in HTML templates, G701 SQL injection found by taint analysis, and G118 unused `cancel` functions, goroutines that use `context.Background()` where a request context exists, and I/O loops that never check `ctx.Done()`. It exits with status 1 on findings, and also runs inside golangci-lint. Partly checks `GO-5`, `GO-6`, `GO-8` and `GO-13`.
- `6` [Staticcheck checks](https://staticcheck.dev/docs/checks/): more than 150 checks for bugs, performance problems and style, such as [SA1012](https://staticcheck.dev/docs/checks/#SA1012) for a nil `context.Context`. Run `staticcheck ./...` in CI, or through golangci-lint, which enables it by default. Checks `GO-15`, and partly `GO-5`.

## Tutorials and further reading

- `7` [A Tour of Go](https://go.dev/tour/) (Go): the official interactive introduction to the syntax and data structures, methods and interfaces, and concurrency primitives.
- `7` [How to Write Go Code](https://go.dev/doc/code) (Go): code organization in modules and packages, your first program, importing packages from your module and from remote modules, and testing, with the `go` command.
- `6` [Tutorial: Accessing a relational database](https://go.dev/doc/tutorial/database-access) (Go): querying, adding data and handling errors with `database/sql`, step by step.
- `6` [Tutorial: Getting started with fuzzing](https://go.dev/doc/tutorial/fuzz) and [Tutorial: Find and fix vulnerable dependencies with govulncheck](https://go.dev/doc/tutorial/govulncheck) (Go): writing and running a fuzz test, and scanning, assessing and fixing a vulnerable dependency.
- `6` [Routing Enhancements for Go 1.22](https://go.dev/blog/routing-enhancements) (Go blog): method matching and wildcards in `net/http`'s `ServeMux`, which cover the routing needs of many services without a third-party router.
- `6` [TableDrivenTests](https://go.dev/wiki/TableDrivenTests) (Go wiki): table-driven tests with named subtests, and running them in parallel with `t.Parallel()`.
- `6` [Learn Go with Tests](https://quii.gitbook.io/learn-go-with-tests) (Chris James, free online): the language, the standard library and building an HTTP server, through test-driven development.
- `5` [Go Concurrency Patterns: Context](https://go.dev/blog/context) and [Pipelines and cancellation](https://go.dev/blog/pipelines) (Go blog, 2014): how a server passes deadlines and cancellation to all the goroutines that handle a request, and how to build pipelines of goroutines that exit cleanly when a stage fails.
- `5` [The Go Programming Language](https://www.gopl.io/) (Alan Donovan and Brian Kernighan, 2015): a thorough book on the language, concurrency, packages and testing. It predates modules and generics.
