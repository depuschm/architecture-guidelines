# GraphQL

Scope: designing, securing and running GraphQL APIs, whatever the server language. The general rules in [API design](../../general/api-design.md) also apply, in particular backward compatibility (`API-2`) and designing the contract first (`API-4`), as do [Security](../../general/security.md) (`SEC-1` on authorization) and [Authentication](../../general/authentication.md). For TypeScript servers, see also [TypeScript](../typescript/README.md) and [Node.js](../nodejs/README.md).

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Adopted references

- `10` [Learn GraphQL](https://graphql.org/learn/) (GraphQL Foundation): **the baseline**: the core concepts, then the [Best Practices](https://graphql.org/learn/best-practices/) lessons on thinking in graphs, serving over HTTP, authorization, pagination, schema design, error handling, performance, security, federation and schema governance.
- `9` [GraphQL Specification](https://spec.graphql.org/September2025/) (September 2025 edition): the language, type system, validation and execution rules that every GraphQL server implements.
- `8` [GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html) (OWASP): **the baseline for security**: input validation, denial of service, access control, batching attacks and insecure default configurations.
- `7` [GraphQL over HTTP](https://http-spec.graphql.org/draft/) (GraphQL Foundation, working draft): how to serve and call GraphQL over HTTP: URLs, `GET` and `POST`, media types, status codes, and security notes.
- `7` [GraphQL Cursor Connections Specification](https://relay.dev/graphql/connections.htm) (Relay): the standard shape for cursor-paginated lists: connections, edges, `pageInfo` and the `first`, `after`, `last` and `before` arguments.

## Key rules

### Schema design

- `8` `GQL-1` **Evolve the schema without versions: add fields and types, mark what you plan to remove with `@deprecated(reason: …)` naming the replacement, and remove it only after usage tracking shows that clients have migrated, or the announced deadline has passed.** Removing or renaming fields, changing their types, making arguments required, or making a non-null field nullable breaks clients ([`API-2`](../../general/api-design.md)). ([GraphQL, Schema change management](https://graphql.org/learn/governance-versioning/), [Schema design: Versioning](https://graphql.org/learn/schema-design/#versioning), [GraphQL spec, @deprecated](https://spec.graphql.org/September2025/#sec--deprecated))
- `8` `GQL-2` **Change data only in mutations: keep query fields free of side effects, and don't execute a mutation sent with `GET`.** The specification requires every field except top-level mutation fields to be free of side effects, and GraphQL over HTTP forbids mutations over `GET`. ([GraphQL spec, Normal and serial execution](https://spec.graphql.org/September2025/#sec-Normal-and-Serial-Execution), [GraphQL over HTTP, GET](https://http-spec.graphql.org/draft/#sec-GET))
- `7` `GQL-3` **Design the schema around the business domain and the way clients use the data, not around the database tables behind it.** Agree on review criteria, such as naming, nullability and compatibility, and review every schema change against them, as `API-4` asks for any API contract. ([GraphQL, Thinking in graphs](https://graphql.org/learn/thinking-in-graphs/), [Review and validate schema changes](https://graphql.org/learn/schema-review/))
- `7` `GQL-4` **Paginate every list field that can grow, with cursor-based connections that follow the Relay connection specification, and cap the page size.** Opaque cursors let you change how the backend paginates later, and unbounded lists let one request fetch huge amounts of data. ([GraphQL, Pagination](https://graphql.org/learn/pagination/), [Relay, Cursor Connections Specification](https://relay.dev/graphql/connections.htm), [OWASP, Query limiting](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html#query-limiting-depth-amount))
- `6` `GQL-5` **Choose nullability field by field: keep a field nullable if it can fail or be denied on its own, make it non-null only where clients need the guarantee, and return lists as `[Item!]!`.** When a non-null field fails, the null spreads to its nearest nullable parent, and making a non-null field nullable later is a breaking change. ([GraphQL, Schema design: Nullability](https://graphql.org/learn/schema-design/#nullability), [Naming conventions: nullability patterns](https://graphql.org/learn/naming-design/#design-nullability-patterns-thoughtfully), [Schema change management: breaking changes](https://graphql.org/learn/governance-versioning/#identify-breaking-changes))
- `6` `GQL-6` **Return expected business errors, such as failed validation or a broken business rule, as typed results in the mutation's payload type, and keep the top-level `errors` array for unexpected failures.** Errors in the schema are typed and discoverable, and a payload type can gain fields without breaking clients. ([GraphQL, Error handling](https://graphql.org/learn/error-handling/), [Naming conventions: payload types](https://graphql.org/learn/naming-design/#wrap-mutation-results-in-payload-types))

### Security

- `9` `GQL-7` **Check authorization in the business logic layer that resolvers call, for every object and field a request reaches, including lookups by ID such as `node(id:)` and connection edges.** Checks written in individual resolvers drift apart between entry points, and knowing an object's ID doesn't mean the caller may see it. ([GraphQL, Authorization](https://graphql.org/learn/authorization/), [OWASP, Access control](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html#access-control))
- `8` `GQL-8` **Limit what one request can cost: reject operations above a maximum depth, number of aliases and root fields, and number of operations in a batch, and stop execution after a timeout. For public APIs, also consider query cost analysis and rate limits based on cost.** ([GraphQL, Security: demand control](https://graphql.org/learn/security/#demand-control), [OWASP, DoS prevention](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html#dos-prevention), [GraphQL Yoga, Preparing for production](https://the-guild.dev/graphql/yoga-server/docs/prepare-for-production))
- `7` `GQL-9` **If only your own clients call the API, execute only trusted documents in production: operations registered at build time and sent by ID.** Automatic persisted queries don't give this protection, because the server registers any operation a client sends. ([GraphQL, Security: trusted documents](https://graphql.org/learn/security/#trusted-documents), [GraphQL Yoga, Persisted operations](https://the-guild.dev/graphql/yoga-server/docs/features/persisted-operations), [Apollo, Differences from automatic persisted queries](https://www.apollographql.com/docs/graphos/platform/security/persisted-queries#differences-from-automatic-persisted-queries))
- `7` `GQL-10` **Mask unexpected errors in production, and turn off stack traces and debug output.** Detailed errors and field suggestions reveal the schema and the systems behind it, even when introspection is off. ([GraphQL, Security: error messages](https://graphql.org/learn/security/#error-messages), [OWASP, Secure configurations](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html#secure-configurations), [GraphQL Yoga, Error masking](https://the-guild.dev/graphql/yoga-server/docs/features/error-masking))
- `6` `GQL-11` **Refuse requests that a browser can send cross-site without a CORS preflight, such as form-encoded or multipart bodies and `GET` requests without a custom header, to prevent cross-site request forgery.** Apollo Server does this by default, and GraphQL Yoga has a plugin for it. ([GraphQL over HTTP, Exercise caution](https://http-spec.graphql.org/draft/#sec-Exercise-caution), [Apollo Server, Preventing CSRF](https://www.apollographql.com/docs/apollo-server/security/cors#preventing-cross-site-request-forgery-csrf), [GraphQL Yoga, CSRF prevention](https://the-guild.dev/graphql/yoga-server/docs/features/csrf-prevention))
- `5` `GQL-12` **Turn off introspection and GraphiQL in production for APIs that only your own clients use, and don't count on it as protection.** Public APIs usually keep introspection for their consumers' tools, perhaps only for authenticated users. Trusted documents and authorization give stronger protection than hiding the schema. ([GraphQL, Introspection in production](https://graphql.org/learn/introspection/#introspection-in-production), [Security: introspection](https://graphql.org/learn/security/#introspection), [OWASP, Introspection and GraphiQL](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html#introspection-graphiql))

### Performance and architecture

- `7` `GQL-13` **Batch and cache data loading within each request, with DataLoader or an equivalent, so that resolving a list doesn't call the backend once per item (the N+1 problem).** Create the loaders per request, so that cached data from one user's request never appears in another's. ([GraphQL, Performance: the N+1 problem](https://graphql.org/learn/performance/#the-n1-problem), [DataLoader, Caching per request](https://github.com/graphql/dataloader/blob/main/README.md), [OWASP, Server-side batching and caching](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html#server-side-batching-and-caching))
- `5` `GQL-14` **Start with one GraphQL service, and adopt federation only when several teams need to own and deploy parts of the graph independently.** Federation needs a gateway, a schema registry and a team to run them. ([GraphQL, Is GraphQL federation right for you?](https://graphql.org/learn/federation/#is-graphql-federation-right-for-you))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [GraphQL Inspector `diff`](https://the-guild.dev/graphql/inspector/docs/commands/diff): compares the schema in a pull request with the current one, sorts the changes into breaking, dangerous and safe, and fails when any change is breaking. Removing a deprecated field counts as breaking unless you turn on `suppressRemovalOfDeprecatedField`, and `considerUsage` checks breaking changes against real usage. Checks `GQL-1`.
- `6` [GraphQL ESLint](https://the-guild.dev/graphql/eslint/rules): lints schema and operation files in CI and the editor. [`relay-connection-types`](https://the-guild.dev/graphql/eslint/rules/relay-connection-types), [`relay-arguments`](https://the-guild.dev/graphql/eslint/rules/relay-arguments) and [`relay-page-info`](https://the-guild.dev/graphql/eslint/rules/relay-page-info) check that connections follow the Relay specification. [`require-deprecation-reason`](https://the-guild.dev/graphql/eslint/rules/require-deprecation-reason) (in `schema-recommended`) and [`require-deprecation-date`](https://the-guild.dev/graphql/eslint/rules/require-deprecation-date) check deprecations, and [`no-deprecated`](https://the-guild.dev/graphql/eslint/rules/no-deprecated) (in `operations-recommended`) flags client operations that still use deprecated fields. Partly checks `GQL-1` and `GQL-4`.
