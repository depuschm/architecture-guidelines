# Apache Kafka

Scope: designing topics, producers and consumers for Apache Kafka 4.x, which runs only in KRaft mode (ZooKeeper mode was removed in Kafka 4.0). Shared messaging rules aren't repeated here: publish events together with database changes through a transactional outbox (`DATA-4`, [general/data.md](../../general/data.md)), make operations safe to retry and evolve contracts compatibly (`API-1`, `API-2`, [general/api-design.md](../../general/api-design.md)), retry with backoff (`OPS-3`, [general/operations-reliability.md](../../general/operations-reliability.md)), and say which event-driven pattern you mean (`STYLE-8` to `STYLE-10`, [general/architecture-styles.md](../../general/architecture-styles.md)). For a queue-based broker, see [RabbitMQ](../rabbitmq/README.md). Features that only Confluent's products provide are marked as such.

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

- `8` [Design](https://kafka.apache.org/43/design/design/) (Apache Kafka docs): how producers, consumers, delivery semantics, transactions, share groups, replication and log compaction work, and the guarantees each gives.

## Key rules

### Topics and partitions

- `8` `KAFKA-1` **Choose each record's key by the ordering you need: records with the same key go to the same partition, and Kafka keeps order only within a partition.** Use the ID of the entity whose events must stay in order, such as a customer or order ID. ([Apache Kafka, Introduction](https://kafka.apache.org/43/getting-started/introduction/), [Design: load balancing](https://kafka.apache.org/43/design/design/#load-balancing), [Confluent, Partitioned Parallelism](https://developer.confluent.io/patterns/event-stream/partitioned-parallelism/))
- `7` `KAFKA-2` **Choose a topic's partition count when you create it, from the throughput and consumer parallelism you need, with room for growth.** A consumer group can't use more consumers than there are partitions, adding partitions sends existing keys to different partitions, and Kafka can't reduce the count. ([Apache Kafka, Modifying topics](https://kafka.apache.org/43/operations/basic-kafka-operations/#modifying-topics), [Confluent, Choose and Change the Partition Count](https://docs.confluent.io/kafka/operations-tools/partition-determination.html))
- `7` `KAFKA-3` **Create topics explicitly with their partition count, replication factor and retention, and turn off automatic topic creation on the brokers.** Auto-created topics get the broker defaults, and the default replication factor is 1. ([Apache Kafka, Adding and removing topics](https://kafka.apache.org/43/operations/basic-kafka-operations/#adding-and-removing-topics), [Broker configs: auto.create.topics.enable](https://kafka.apache.org/43/configuration/broker-configs/#auto.create.topics.enable), [default.replication.factor](https://kafka.apache.org/43/configuration/broker-configs/#default.replication.factor))
- `6` `KAFKA-4` **Set each topic's cleanup policy and retention on purpose: keep records at least as long as consumers may lag behind or need to replay them, and use compaction (`cleanup.policy=compact`) for topics where only the latest value per key matters.** `retention.ms` defaults to seven days. On a compacted topic, delete a key with a tombstone: a record with that key and a null value. ([Topic configs: retention.ms](https://kafka.apache.org/43/configuration/topic-configs/#retention.ms), [cleanup.policy](https://kafka.apache.org/43/configuration/topic-configs/#cleanup.policy), [Design: log compaction](https://kafka.apache.org/43/design/design/#log-compaction))

### Producers and durability

- `8` `KAFKA-5` **For data you can't afford to lose, use a replication factor of 3, `min.insync.replicas=2` and producer `acks=all`, and leave unclean leader election off.** `min.insync.replicas` defaults to 1, so an `acks=all` write can succeed when only one replica is in sync, and is lost if that replica then fails. ([Topic configs: min.insync.replicas](https://kafka.apache.org/43/configuration/topic-configs/#min.insync.replicas), [Design: availability and durability guarantees](https://kafka.apache.org/43/design/design/#availability-and-durability-guarantees))
- `7` `KAFKA-6` **Keep producer idempotence on, and set `enable.idempotence=true` explicitly, so that conflicting settings fail when the producer is created instead of silently turning it off.** Idempotence, on by default, stops retries from writing duplicates; it needs `acks=all`, `retries` above 0 and at most 5 in-flight requests per connection. ([Producer configs: enable.idempotence](https://kafka.apache.org/43/configuration/producer-configs/#enable.idempotence), [acks](https://kafka.apache.org/43/configuration/producer-configs/#acks))

### Consumers

- `8` `KAFKA-7` **Commit offsets only after the records are processed, and make processing idempotent, because after a failure Kafka redelivers the records since the last commit.** With automatic commits, finish every record returned by one `poll` before the next; if other threads process the records, turn off `enable.auto.commit` and commit the offsets they have finished. ([Design: message delivery semantics](https://kafka.apache.org/43/design/design/#message-delivery-semantics), [KafkaConsumer API: manual offset control](https://kafka.apache.org/43/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html), [microservices.io, Idempotent Consumer](https://microservices.io/patterns/communication-style/idempotent-consumer.html))
- `7` `KAFKA-8` **Don't let a record that can't be processed block its partition: after a bounded number of retries, write it with the error details to a dead-letter topic and move on.** Kafka Connect and Kafka Streams have dead-letter settings built in. Retry topics delay records that may succeed later, but lose per-key ordering, so use them only where order doesn't matter. ([Confluent, Error Handling Patterns in Kafka](https://www.confluent.io/blog/error-handling-patterns-in-kafka/), [Apache Kafka, Kafka Connect error reporting](https://kafka.apache.org/43/kafka-connect/user-guide/#error-reporting-in-connect), [Kafka Streams configs: errors.dead.letter.queue.topic.name](https://kafka.apache.org/43/configuration/kafka-streams-configs/#errors.dead.letter.queue.topic.name), [Spring for Apache Kafka, Non-blocking retries](https://docs.spring.io/spring-kafka/reference/retrytopic/how-the-pattern-works.html))
- `6` `KAFKA-9` **Keep the work for each `poll` well within `max.poll.interval.ms`, and lower `max.poll.records` when processing is slow.** A consumer that doesn't poll in time leaves the group, its partitions are reassigned, and its offset commits fail. ([KafkaConsumer API: detecting consumer failures](https://kafka.apache.org/43/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#failuredetection))
- `5` `KAFKA-10` **For consume-transform-produce flows between Kafka topics, get exactly-once processing from Kafka Streams or a transactional producer, and read the results with `isolation.level=read_committed`.** Transactions cover only writes to Kafka; when the output goes to another system, store the offsets with the output or rely on idempotent processing. ([Design: using transactions](https://kafka.apache.org/43/design/design/#using-transactions), [Design: message delivery semantics](https://kafka.apache.org/43/design/design/#message-delivery-semantics))
- `5` `KAFKA-11` **For queue-style work whose records are independent and need no ordering, consider a share group (production-ready since Kafka 4.2) instead of a consumer group.** A share group can have more consumers than partitions, acknowledges each record, and stops delivering a record after a limited number of attempts (5 by default). ([Design: the share consumer](https://kafka.apache.org/43/design/design/#the-share-consumer), [Upgrading: notable changes in 4.2.0](https://kafka.apache.org/43/getting-started/upgrade/#notable-changes-in-420), [Broker configs: group.share.delivery.count.limit](https://kafka.apache.org/43/configuration/broker-configs/#group.share.delivery.count.limit))

### Schemas

- `8` `KAFKA-12` **Give every topic a schema (Avro, Protobuf or JSON Schema) in a schema registry, and enforce a compatibility type for each subject.** Confluent Schema Registry defaults to `BACKWARD`, which lets consumers re-read old records; with it, upgrade consumers before producers. Apicurio Registry, under the Apache License, offers the same compatibility rules. ([Confluent, Schema Evolution and Compatibility](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html), [Apicurio Registry, Content rule reference](https://www.apicur.io/registry/docs/apicurio-registry/3.3.x/getting-started/assembly-rule-reference.html))
- `7` `KAFKA-13` **Register schemas from CI after a compatibility check, and set `auto.register.schemas=false` on producers in production.** Producers register new schemas themselves by default, which suits development but lets an untested schema reach production. ([Confluent, Schema Registry Best Practices](https://www.confluent.io/blog/best-practices-for-confluent-schema-registry/), [Schema Registry Maven plugin: test-compatibility](https://docs.confluent.io/platform/current/schema-registry/develop/maven-plugin.html#schema-registry-test-compatibility))

### Security

- `8` `KAFKA-14` **Authenticate every connection to the brokers with TLS client certificates or SASL over TLS, turn on the `StandardAuthorizer`, and give each application its own principal with only the ACLs it needs.** Kafka accepts unauthenticated, unencrypted clients unless you configure security, and SASL/PLAIN and SCRAM should only be used over TLS. Don't set `allow.everyone.if.no.acl.found=true`. ([Apache Kafka, Security overview](https://kafka.apache.org/43/security/security-overview/), [Authentication using SASL](https://kafka.apache.org/43/security/authentication-using-sasl/), [Authorization and ACLs](https://kafka.apache.org/43/security/authorization-and-acls/))

### Operations

- `7` `KAFKA-15` **Run production clusters with dedicated KRaft controller nodes, usually three or five, rather than nodes that are both broker and controller.** Combined mode should be avoided in critical environments. Clusters still on ZooKeeper must migrate to KRaft, using Kafka 3.9 as the bridge release, before they can upgrade to 4.x. ([Apache Kafka, KRaft: deploying considerations](https://kafka.apache.org/43/operations/kraft/#deploying-considerations), [KRaft: controllers](https://kafka.apache.org/43/operations/kraft/#controllers), [Upgrading to 4.0](https://kafka.apache.org/43/getting-started/upgrade/#upgrading-servers-to-401-from-any-version-33x-through-39x))
- `7` `KAFKA-16` **Monitor consumer lag for every consumer group, and the brokers' under-replicated and under-min-ISR partition counts, and alert when lag keeps growing or those counts aren't 0.** ([Apache Kafka, Monitoring](https://kafka.apache.org/43/operations/monitoring/), [Checking consumer position](https://kafka.apache.org/43/operations/basic-kafka-operations/#checking-consumer-position))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [Schema Registry Maven plugin](https://docs.confluent.io/platform/current/schema-registry/develop/maven-plugin.html#schema-registry-test-compatibility) (Confluent): in CI, `test-compatibility` checks the project's schemas against a Schema Registry, [`test-local-compatibility`](https://docs.confluent.io/platform/current/schema-registry/develop/maven-plugin.html#schema-registry-test-local-compatibility) checks them against earlier local versions without a registry, and `register` registers them. Checks `KAFKA-12`, and partly `KAFKA-13`.
- `7` [buf breaking](https://buf.build/docs/breaking/): for Protobuf schemas kept in the repository, compares them in CI with a previous version, such as the main branch, and reports changes that break the wire format or generated code. Partly checks `KAFKA-12`.
- `5` [CreateTopicPolicy](https://kafka.apache.org/43/javadoc/org/apache/kafka/server/policy/CreateTopicPolicy.html) (Apache Kafka): a policy class you write and set in `create.topic.policy.class.name`; the controller runs it for every topic creation and rejects topics whose replication factor, `min.insync.replicas` or retention is outside the range you allow. Partly checks `KAFKA-3`, `KAFKA-4` and `KAFKA-5`.
