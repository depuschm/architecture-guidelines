# MongoDB

Scope: designing, securing and running MongoDB for applications, self-managed (Community and Enterprise) or on MongoDB Atlas (Atlas Core and Atlas Infinite clusters, and the Free and Flex tiers). The guidelines cover MongoDB 9.0, the current major version, and 8.0 and 7.0, which are supported until October 2029 and August 2027. Architecture-level data rules, such as data ownership, consistency between services and backups, are in [general/data.md](../../general/data.md) (`DATA-1`, `DATA-5`, `DATA-8`), and validating input, service identities and TLS in [general/security.md](../../general/security.md) (`SEC-5`, `SEC-10`, `SEC-13`). Driver code also follows [Node.js](../nodejs/README.md) or [Python](../python/README.md), and connecting from serverless functions is covered in [Serverless and edge hosting](../web-hosting/README.md). For a relational system of record, see [PostgreSQL](../postgres/README.md); for caching, [Redis and caching](../redis/README.md); and for a document database that clients call directly, [Firebase](../firebase/README.md).

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Key rules

### Data modeling

- `8` `MONGO-1` **Design each collection from the application's read and write patterns: embed data that is read or updated together, and reference data that grows without bound, has many items on the child side, is written at different times or exists on its own.** MongoDB's core modeling principle is that data accessed together is stored together. A write to one document is atomic, so embedding also removes the need for most multi-document transactions. ([MongoDB, Data Modeling](https://www.mongodb.com/docs/manual/data-modeling/), [Best Practices: link related data](https://www.mongodb.com/docs/manual/data-modeling/best-practices/#link-related-data), [Best Practices: atomicity](https://www.mongodb.com/docs/manual/data-modeling/best-practices/#atomicity))
- `8` `MONGO-2` **Keep documents bounded: cap arrays with the subset pattern or move their items to a separate collection, and move fields that aren't read together into separate documents.** An unbounded array can exceed the 16 MiB document limit and slows down its indexes, and indexed arrays perform best with fewer than 1,000 elements. Large documents fill the RAM that the working set needs. Store files over the limit with GridFS. ([MongoDB, Avoid Unbounded Arrays](https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/unbounded-arrays/), [Bloated Documents](https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/bloated-documents/), [Limits: BSON documents](https://www.mongodb.com/docs/manual/reference/limits/#bson-documents), [Development Checklist: schema design](https://www.mongodb.com/docs/manual/administration/production-checklist-development/#schema-design))
- `7` `MONGO-3` **When the shape of a document changes, add a `schemaVersion` field, and make the code's queries and updates handle every version that can still be in the collection.** The schema versioning pattern keeps old and new documents side by side and avoids large migrations; a field stored in different places in different versions may need an index for each place. ([MongoDB, Maintain Different Schema Versions](https://www.mongodb.com/docs/manual/data-modeling/design-patterns/data-versioning/schema-versioning/))
- `7` `MONGO-4` **Once a collection's schema is established, add a `$jsonSchema` validator and keep the default behavior, which rejects invalid inserts and updates.** The database then enforces types and allowed values for every client that writes, in addition to validating input at the trust boundary (`SEC-10`). ([MongoDB, Schema Validation](https://www.mongodb.com/docs/manual/core/schema-validation/), [Specify JSON Schema Validation](https://www.mongodb.com/docs/manual/core/schema-validation/specify-json-schema/), [Best Practices: enforce schema with validation rules](https://www.mongodb.com/docs/manual/data-modeling/best-practices/#enforce-schema-with-validation-rules))

### Indexes and queries

- `7` `MONGO-5` **Create an index for every frequent query, order compound index keys by the ESR guideline (equality, then sort, then range), and check each query with `explain("executionStats")`: it should use an index scan (`IXSCAN`) and examine about as many documents as it returns.** MongoDB creates only the `_id` index for you. Every index slows down writes, so drop the ones that `$indexStats` shows unused. On Atlas, the Performance Advisor suggests indexes for slow queries. ([MongoDB, Development Checklist: schema design](https://www.mongodb.com/docs/manual/administration/production-checklist-development/#schema-design), [The ESR Guideline](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/), [Interpret Explain Plan Results](https://www.mongodb.com/docs/manual/tutorial/analyze-query-plan/), [Remove Unnecessary Indexes](https://www.mongodb.com/docs/manual/data-modeling/design-antipatterns/unnecessary-indexes/), [Atlas Performance Advisor](https://www.mongodb.com/docs/atlas/performance-advisor/))
- `5` `MONGO-6` **If you shard a collection, choose a shard key with high cardinality, evenly spread and non-monotonic values, that most queries include, so that they go to one shard.** You can reshard later, but a key that concentrates writes or forces broadcast queries limits scaling. ([MongoDB, Choose a Shard Key](https://www.mongodb.com/docs/manual/core/sharding-choose-a-shard-key/), [Development Checklist: sharding](https://www.mongodb.com/docs/manual/administration/production-checklist-development/#sharding))

### Consistency and transactions

- `8` `MONGO-7` **Write data you can't lose with `w: "majority"`, the default, on replica sets with at least three data-bearing voting members, and read from the primary with `"majority"` read concern where a client must read its own writes.** Writes acknowledged with `w: 1` can be rolled back when the primary fails over. With an arbiter instead of a third data-bearing member, the implicit default can drop to `w: 1`. Don't use secondary reads to scale read throughput. ([MongoDB, Rollbacks: avoid replica set rollbacks](https://www.mongodb.com/docs/manual/core/replica-set-rollbacks/#avoid-replica-set-rollbacks), [Write Concern: implicit default](https://www.mongodb.com/docs/manual/reference/write-concern/#implicit-default-write-concern), [Read and write concern recommendations](https://www.mongodb.com/docs/manual/reference/write-concern/#read-and-write-concern-recommendations), [Development Checklist: data durability](https://www.mongodb.com/docs/manual/administration/production-checklist-development/#data-durability), [Development Checklist: replication](https://www.mongodb.com/docs/manual/administration/production-checklist-development/#replication))
- `7` `MONGO-8` **Use multi-document transactions only where several documents must change atomically, run them with the driver's callback API, which retries transient errors, and keep each one well under the 60-second default limit.** Transactions cost more than single-document writes and don't replace good schema design; for many cases embedding is the better model. ([MongoDB, Transactions](https://www.mongodb.com/docs/manual/core/transactions/), [Best Practices: atomicity](https://www.mongodb.com/docs/manual/data-modeling/best-practices/#atomicity), [Production Considerations: runtime limit](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/#runtime-limit))
- `7` `MONGO-9` **Leave retryable writes on, the driver default, and handle what they don't cover: retry failed operations with exponential backoff where that is safe (`OPS-3`), and make multi-document updates and deletes idempotent.** Drivers retry inserts and single-document updates and deletes once after a network error or election; `updateMany`, `deleteMany` and individual writes inside a transaction aren't retried. ([MongoDB, Retryable Writes](https://www.mongodb.com/docs/manual/core/retryable-writes/#retryable-write-operations), [Development Checklist: drivers](https://www.mongodb.com/docs/manual/administration/production-checklist-development/#drivers))

### Connections

- `7` `MONGO-10` **Create one `MongoClient` per process when it starts, outside request and serverless handlers, and reuse it for every operation; size `maxPoolSize` from the number of concurrent requests, starting at 110–115% of the typical number.** Each client has its own connection pool, so a client per request or per function invocation opens new connections every time and can exceed the database's connection limits. ([MongoDB, Connection Pool Overview](https://www.mongodb.com/docs/manual/administration/connection-pool-overview/#use-an-instance-of-your-drivers-mongoclient-object), [Atlas, Manage Connections with AWS Lambda](https://www.mongodb.com/docs/atlas/manage-connections-aws-lambda/), [Development Checklist: drivers](https://www.mongodb.com/docs/manual/administration/production-checklist-development/#drivers))

### Security

- `9` `MONGO-11` **Never expose MongoDB to the internet. Self-managed: bind it to private interfaces, firewall the port so that only application hosts can reach it, and turn on access control, which is off by default. Atlas: never add `0.0.0.0/0` to the IP access list, and connect staging and production projects through private endpoints.** ([MongoDB, Production Notes: use trusted networking environments](https://www.mongodb.com/docs/manual/administration/production-notes/#use-trusted-networking-environments), [Network and Configuration Hardening: IP binding](https://www.mongodb.com/docs/manual/core/security-hardening/#ip-binding), [Security Checklist: limit network exposure](https://www.mongodb.com/docs/manual/administration/security-checklist/#-limit-network-exposure), [Atlas, Configure IP Access List Entries](https://www.mongodb.com/docs/atlas/security/ip-access-list/#add-ip-access-list-entries), [Atlas Architecture Center, network security recommendations](https://www.mongodb.com/docs/atlas/architecture/current/network-security/#all-deployment-paradigm-recommendations))
- `9` `MONGO-12` **Never pass request data into a query filter or update document as an object: check that each value is a scalar of the expected type, or wrap it in `$eq`, so that a client can't send query operators such as `{"$ne": null}`.** In Mongoose, turn on the `sanitizeFilter` option. This applies `SEC-10`. ([CodeQL, Database query built from user-controlled sources](https://codeql.github.com/codeql-query-help/javascript/js-sql-injection/), [Mongoose, sanitizeFilter()](https://mongoosejs.com/docs/api/mongoose.html#Mongoose.prototype.sanitizeFilter%28%29), [PortSwigger, NoSQL injection](https://portswigger.net/web-security/nosql-injection))
- `8` `MONGO-13` **Give each application its own database user with roles scoped to the databases and actions it needs, never a cluster-wide or administrator role, and require TLS on every connection (`SEC-5`, `SEC-13`). On Atlas, authenticate production workloads with Workload Identity Federation, AWS IAM or X.509 certificates; Atlas recommends password (SCRAM) users only for development and test.** ([MongoDB, Security Checklist: configure role-based access control](https://www.mongodb.com/docs/manual/administration/security-checklist/#-configure-role-based-access-control), [Security Checklist: encrypt communication](https://www.mongodb.com/docs/manual/administration/security-checklist/#-encrypt-communication-tlsssl), [Atlas Architecture Center, authorization](https://www.mongodb.com/docs/atlas/architecture/current/auth/authorization/#rbac-and-predefined-roles), [Atlas Architecture Center, database authentication](https://www.mongodb.com/docs/atlas/architecture/current/auth/authentication/#atlas-database-authentication))
- `7` `MONGO-14` **Never build `$where`, `$function` or `$accumulator` expressions from user input, and turn server-side JavaScript off when the application doesn't use it: `--noscripting` or `security.javascriptEnabled: false` on self-managed servers, and the Allow Server-Side JavaScript setting on Atlas.** These operators run arbitrary JavaScript on the server. ([MongoDB, FAQ: how does MongoDB address query injection](https://www.mongodb.com/docs/manual/faq/fundamentals/#how-does-mongodb-address-sql-or-query-injection), [Security Checklist: secure configuration options](https://www.mongodb.com/docs/manual/administration/security-checklist/#-run-mongodb-with-secure-configuration-options), [Server-side JavaScript: disable](https://www.mongodb.com/docs/manual/core/server-side-javascript/#disable-server-side-javascript), [Atlas, Allow Server-Side JavaScript](https://www.mongodb.com/docs/atlas/cluster-additional-settings/#allow-server-side-javascript))

### Backups and upgrades

- `8` `MONGO-15` **Back up production clusters with point-in-time recovery, keep a copy in a second region, and test restores regularly (`DATA-8`). On Atlas, turn on Cloud Backup with Continuous Cloud Backup, multi-region snapshot distribution and a Backup Compliance Policy.** Atlas Free clusters have no Atlas backups. Self-managed deployments need Ops Manager or Cloud Manager, or file system snapshots with journaling; `mongodump` suits only small deployments. ([Atlas Architecture Center, backup recommendations](https://www.mongodb.com/docs/atlas/architecture/current/backups/#recommendations-for-atlas-backups), [Atlas Architecture Center, disaster recovery](https://www.mongodb.com/docs/atlas/architecture/current/disaster-recovery/#backup-strategy-rtorpo-trade-offs), [Atlas, Back Up, Restore, and Archive Data](https://www.mongodb.com/docs/atlas/backup-restore-cluster/), [MongoDB, Operations Checklist: backups](https://www.mongodb.com/docs/manual/administration/production-checklist-operations/#backups), [Backup Methods for a Self-Managed Deployment](https://www.mongodb.com/docs/manual/core/backups/))
- `7` `MONGO-16` **Choose the upgrade path on purpose. On Atlas clusters that upgrade automatically, declare the Stable API version in a strict client; elsewhere, test each new major version on a staging deployment first, upgrade before the current one reaches end of life, and raise the feature compatibility version only after testing, because after that you can't downgrade.** A strict Stable API client rejects commands outside the API, so that server upgrades don't change the application's behavior. This applies `SEC-17`. ([MongoDB, Stable API: create a strict client](https://www.mongodb.com/docs/manual/reference/stable-api/#create-a-strict-client), [MongoDB Versions and Upgrade Paths: before you upgrade](https://www.mongodb.com/docs/mongodb-versions/#before-you-upgrade), [feature compatibility version](https://www.mongodb.com/docs/mongodb-versions/#feature-compatibility-version), [MongoDB Software Lifecycle Schedules](https://www.mongodb.com/legal/support-policy/lifecycles))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [Atlas Resource Policies](https://www.mongodb.com/docs/atlas/atlas-resource-policies/#restrict-ip-addresses): organization-wide policies, written in Cedar, that Atlas checks on every change from the UI, API, CLI or Terraform. They can forbid `/0` entries in IP access lists, require an empty list so that only private endpoints connect, and impose a minimum TLS version. Partly checks `MONGO-11` and `MONGO-13`.
- `6` [CodeQL, Database query built from user-controlled sources](https://codeql.github.com/codeql-query-help/javascript/js-sql-injection/) and [NoSQL Injection (Python)](https://codeql.github.com/codeql-query-help/python/py-nosql-injection/): code-scanning queries that trace request data into MongoDB queries in JavaScript, TypeScript and Python. Partly checks `MONGO-12`.
- `6` [`notablescan` server parameter](https://www.mongodb.com/docs/manual/reference/parameters/#mongodb-parameter-param.notablescan): set it on the `mongod` that integration tests run against, so that every query that needs a collection scan fails. Don't set it in production. Partly checks `MONGO-5`.
- `4` [Semgrep `mongodb-nosqli` rule](https://github.com/semgrep/semgrep-rules/blob/develop/java/mongodb/security/injection/audit/mongodb-nosqli.yaml): flags non-constant data passed to `$where` through the Java driver. Partly checks `MONGO-14`.
