# Node.js and TypeScript back ends

Scope: server-side services that run on Node.js and are written in TypeScript, such as HTTP APIs, workers and scheduled jobs. For configuration, health checks, telemetry and resilience, follow [general/operations-reliability.md](../../general/operations-reliability.md); for secrets, authorization and the supply chain, follow [general/security.md](../../general/security.md). The rules here cover what is specific to Node.js and TypeScript.

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Adopted references

- `9` [Don't Block the Event Loop (or the Worker Pool)](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop) (Node.js): how Node.js runs many clients on a few threads, and how to keep each callback and task small. Read it before designing a service.
- `9` [Security Best Practices](https://nodejs.org/learn/getting-started/security-best-practices) (Node.js): Node.js-specific threats, such as HTTP denial of service, malicious dependencies and prototype pollution, with mitigations for each.
- `7` [Node.js Best Practices](https://github.com/goldbergyoni/nodebestpractices) (Yoni Goldberg and contributors): the largest community collection, covering project structure, error handling, testing, production, security and Docker. Use it as a checklist; it isn't an official source.

## Key rules

- `9` `NODE-1` **Don't block the event loop.** In request paths, don't call the synchronous file system, crypto, compression or child-process APIs, and either split CPU-heavy work into small steps or move it off the event loop, to a worker pool or a dedicated service. ([Node.js, Don't Block the Event Loop](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop), [Node.js Best Practices 7.1](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/performance/block-loop.md))
- `8` `NODE-2` **Await or return every promise, and don't pass async functions where the caller ignores the returned promise.** Since Node.js 15, an unhandled rejection crashes the process by default. ([typescript-eslint, no-floating-promises](https://typescript-eslint.io/rules/no-floating-promises/), [no-misused-promises](https://typescript-eslint.io/rules/no-misused-promises/), [Node.js CLI, --unhandled-rejections](https://nodejs.org/api/cli.html#--unhandled-rejectionsmode))
- `8` `NODE-3` **Validate all external input, such as request bodies, query strings and messages, at runtime with a schema library.** TypeScript types are erased before the code runs, so they don't check incoming data; schema validation also guards against prototype pollution. ([Node.js Best Practices 6.10](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/security/validation.md), [2.11](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/errorhandling/failfast.md), [TypeScript, Erased types](https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types), [Node.js, Prototype pollution](https://nodejs.org/learn/getting-started/security-best-practices#prototype-pollution-attacks-cwe-1321))
- `8` `NODE-4` **Commit the lockfile, install with `npm ci`, and check dependencies for known vulnerabilities in CI.** Consider `--ignore-scripts` and a minimum release age to reduce exposure to malicious packages. See [general/security.md](../../general/security.md) for provenance and dependency updates. ([Node.js, Supply chain attacks](https://nodejs.org/learn/getting-started/security-best-practices#supply-chain-attacks), [npm ci](https://docs.npmjs.com/cli/v12/commands/npm-ci/), [Node.js Best Practices 5.19](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/production/installpackageswithnpmci.md))
- `8` `NODE-5` **Run only Active LTS or Maintenance LTS releases of Node.js in production.** ([Node.js, Releases](https://nodejs.org/en/about/previous-releases), [Node.js Best Practices 5.17](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/production/LTSrelease.md))
- `7` `NODE-6` **Treat unknown errors as fatal: log them, shut down gracefully and let the platform restart the process.** Use `uncaughtException` only for synchronous cleanup before exiting, because the app is in an undefined state. ([Node.js, Using 'uncaughtException' correctly](https://nodejs.org/api/process.html#warning-using-uncaughtexception-correctly), [Node.js Best Practices 2.3](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/errorhandling/operationalvsprogrammererror.md), [2.6](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/errorhandling/shuttingtheprocess.md))
- `7` `NODE-7` **Structure the service by business components, each with its own entry points, domain logic and data access, and keep web-framework objects out of the domain logic.** ([Node.js Best Practices 1.1](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/projectstructre/breakintcomponents.md), [1.2](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/projectstructre/createlayers.md))
- `7` `NODE-8` **Type-check Node.js services in CI with `tsc`, and set `module` to `nodenext`.** Node.js runs TypeScript by stripping the types without checking them, so only `tsc` catches type errors, and `nodenext` makes the compiler resolve imports the way Node.js does. The compiler settings for any TypeScript codebase are `TS-1`, `TS-2` and `TS-5` in [TypeScript](../typescript/README.md). ([TypeScript, strict](https://www.typescriptlang.org/tsconfig/#strict), [Node.js, Modules: TypeScript](https://nodejs.org/api/typescript.html), [TypeScript, Choosing compiler options](https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html))
- `7` `NODE-9` **Shut down gracefully on `SIGTERM`: fail the readiness check, stop accepting connections, finish in-flight requests, close resources, then exit.** Start the process with `node`, not `npm start`, so that it receives the signal. ([Node.js Best Practices 8.6](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/docker/graceful-shutdown.md), [8.2](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/docker/bootstrap-using-node.md), [Node.js, server.close()](https://nodejs.org/api/http.html#serverclosecallback), [Kubernetes, Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/))
- `7` `NODE-10` **Log structured JSON to stdout with a mature logger such as Pino, add request context with child loggers, and redact secrets.** Let the platform route the logs, and keep sensitive data out of them as [general/security.md](../../general/security.md) requires. ([Node.js Best Practices 2.7](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/errorhandling/usematurelogger.md), [5.18](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/production/logrouting.md), [Pino, Child loggers](https://github.com/pinojs/pino/blob/main/docs/child-loggers.md), [Pino, Redaction](https://github.com/pinojs/pino/blob/main/docs/redaction.md))
- `6` `NODE-11` **Handle errors in one central handler that every entry point (HTTP routes, jobs, message consumers) calls, and throw only `Error` objects or subclasses of it.** ([Node.js Best Practices 2.4](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/errorhandling/centralizedhandling.md), [2.2](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/errorhandling/useonlythebuiltinerror.md))
- `6` `NODE-12` **Set HTTP server timeouts and connection limits, and put a reverse proxy in front of the service.** Idle or slow connections otherwise hold resources and enable denial of service. ([Node.js, Denial of service of HTTP server](https://nodejs.org/learn/getting-started/security-best-practices#denial-of-service-of-http-server-cwe-400))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [TypeScript `strict`](https://www.typescriptlang.org/tsconfig/#strict): with `strict` on, running `tsc --noEmit` in CI fails the build on type errors. Checks `NODE-8`.
- `7` [typescript-eslint `no-floating-promises`](https://typescript-eslint.io/rules/no-floating-promises/) and [`no-misused-promises`](https://typescript-eslint.io/rules/no-misused-promises/): type-aware lint rules, both in `recommended-type-checked`, that flag unhandled promises and promises passed where they aren't handled. Checks `NODE-2`.
- `7` [npm ci](https://docs.npmjs.com/cli/v12/commands/npm-ci/) and [npm audit](https://docs.npmjs.com/cli/v12/commands/npm-audit/): `npm ci` fails when `package.json` and the lockfile disagree, and `npm audit --audit-level=<level>` fails on known vulnerabilities. Pair them with Dependabot ([general/security.md](../../general/security.md)). Partly checks `NODE-4`.
- `6` [eslint-plugin-n `no-sync`](https://github.com/eslint-community/eslint-plugin-n/blob/master/docs/rules/no-sync.md): flags calls to synchronous `*Sync` methods. Partly checks `NODE-1`.
- `6` [eslint-plugin-regexp `no-super-linear-backtracking`](https://ota-meshi.github.io/eslint-plugin-regexp/rules/no-super-linear-backtracking.html): flags regular expressions with exponential or polynomial backtracking (ReDoS), which block the event loop. Partly checks `NODE-1`.
- `6` [dependency-cruiser](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md#group-matching): `forbidden` rules with group matching stop one business component from importing another's internals, and fail CI on violations. Partly checks `NODE-7`.
