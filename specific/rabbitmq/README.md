# RabbitMQ

Scope: designing exchanges, queues, publishers and consumers for RabbitMQ 4.x, following the current (4.4) documentation. Shared messaging rules aren't repeated here: publish events together with database changes through a transactional outbox (`DATA-4`, [general/data.md](../../general/data.md)), make operations safe to retry (`API-1`, [general/api-design.md](../../general/api-design.md)), buffer load with queues and retry with backoff (`OPS-7`, `OPS-3`, [general/operations-reliability.md](../../general/operations-reliability.md)), and say which event-driven pattern you mean (`STYLE-8` to `STYLE-10`, [general/architecture-styles.md](../../general/architecture-styles.md)). For a log-based broker, see [Apache Kafka](../kafka/README.md); for secrets and least privilege, see [general/security.md](../../general/security.md).

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Key rules

### Queues and data safety

- `9` `RABBITMQ-1` **Declare queues whose messages must survive the loss of a node as quorum queues, and make `quorum` the default queue type of the virtual host.** Classic queues aren't replicated in RabbitMQ 4.x, and a queue's type can't be changed after it's declared. Keep classic queues for temporary, exclusive or low-value data. ([RabbitMQ, Quorum Queues: use cases](https://www.rabbitmq.com/docs/quorum-queues#use-cases), [Classic Queues](https://www.rabbitmq.com/docs/classic-queues), [Virtual hosts: default queue type](https://www.rabbitmq.com/docs/vhosts#default-queue-type))
- `9` `RABBITMQ-2` **Publish with publisher confirms, and consume with manual acknowledgements, acknowledging each message only after it has been processed.** With automatic acknowledgements, a message counts as delivered as soon as it's sent and is lost if the consumer fails; a quorum queue confirms a message only once a majority of its replicas have it. ([RabbitMQ, Acknowledgement modes](https://www.rabbitmq.com/docs/confirms#acknowledgement-modes), [Quorum Queues: use cases](https://www.rabbitmq.com/docs/quorum-queues#use-cases), [Publishers: data safety](https://www.rabbitmq.com/docs/publishers#data-safety))
- `8` `RABBITMQ-3` **Make consumers idempotent: the same message can arrive twice, after a redelivery or when a publisher resends a message whose confirm it didn't receive.** RabbitMQ recommends idempotent processing over explicit deduplication; the `redelivered` flag marks deliveries that a consumer may have seen before. ([RabbitMQ, Reliability Guide: consumer side](https://www.rabbitmq.com/docs/reliability#consumer-side), [microservices.io, Idempotent Consumer](https://microservices.io/patterns/communication-style/idempotent-consumer.html))
- `7` `RABBITMQ-4` **Don't let unroutable messages disappear: publish with the `mandatory` flag and handle returned messages, or give the exchange an alternate exchange.** By default, a message that matches no binding is discarded. ([RabbitMQ, Publishers: unroutable message handling](https://www.rabbitmq.com/docs/publishers#unroutable), [Alternate Exchanges](https://www.rabbitmq.com/docs/ae), [Reliability Guide: routing](https://www.rabbitmq.com/docs/reliability#routing))

### Consumers and failed messages

- `8` `RABBITMQ-5` **Handle poison messages with the quorum queue delivery limit and a dead-letter exchange: keep the limit on (20 by default since RabbitMQ 4.0), and dead-letter messages that exceed it to a queue that someone monitors.** Without a dead-letter exchange, such messages are dropped. Where they matter, use at-least-once dead-lettering, because the default strategy can lose them in transit. ([RabbitMQ, Quorum Queues: poison message handling](https://www.rabbitmq.com/docs/quorum-queues#poison-message-handling), [Dead Letter Exchanges](https://www.rabbitmq.com/docs/dlx), [Quorum Queues: at-least-once dead-lettering](https://www.rabbitmq.com/docs/quorum-queues#activating-at-least-once-dead-lettering))
- `7` `RABBITMQ-6` **Give every consumer a bounded prefetch, starting between 100 and 300, and tune it by measurement.** With unlimited prefetch or automatic acknowledgements, unprocessed deliveries pile up and can exhaust the memory of consumers or nodes. Set prefetch per consumer: quorum queues don't support global QoS. ([RabbitMQ, Prefetch and throughput](https://www.rabbitmq.com/docs/confirms#channel-qos-prefetch-throughput), [Consumer Prefetch](https://www.rabbitmq.com/docs/consumer-prefetch), [Quorum Queues: global QoS](https://www.rabbitmq.com/docs/quorum-queues#global-qos))
- `6` `RABBITMQ-7` **Retry transient failures with the quorum queue's delayed retry (RabbitMQ 4.3 and later) instead of requeueing at once or building dead-letter cycles with TTLs.** Rapid requeue loops overload the queue; delayed retry adds a linear back-off without rewriting the message or risking its loss. ([RabbitMQ, Quorum Queues: delayed retry](https://www.rabbitmq.com/docs/quorum-queues#delayed-retry), [Dead Letter Exchanges: delayed retries](https://www.rabbitmq.com/docs/dlx#delayed-retries))

### Connections and channels

- `7` `RABBITMQ-8` **Keep connections long-lived, use separate connections for publishing and consuming, and give each thread its own channel.** Opening connections per operation causes high churn that wastes node resources, publishing concurrently on a shared channel is unsafe, and flow control on a publishing connection can hold up the acknowledgements of consumers on the same connection. ([RabbitMQ, Connections: high connection churn](https://www.rabbitmq.com/docs/connections#high-connection-churn), [Channels](https://www.rabbitmq.com/docs/channels), [Publishers: concurrency](https://www.rabbitmq.com/docs/publishers#concurrency), [Production checklist: connection management](https://www.rabbitmq.com/docs/production-checklist#apps-connection-management))

### Queue design

- `7` `RABBITMQ-9` **Keep queues short: run enough consumers to keep up, cap queue length with a policy, and use a stream instead of a queue for large backlogs, replay or large fan-outs.** Queues are optimised for being nearly empty and perform worse with millions of messages; classic queues no longer have a "lazy" mode for large backlogs. ([RabbitMQ, Streams: use cases](https://www.rabbitmq.com/docs/streams#use-cases), [Queue Length Limit](https://www.rabbitmq.com/docs/maxlength), [Quorum Queues: when not to use them](https://www.rabbitmq.com/docs/quorum-queues#when-not-to-use-quorum-queues), [Lazy queues](https://www.rabbitmq.com/docs/lazy-queues))
- `7` `RABBITMQ-10` **Configure dead-lettering, TTLs, length limits and delivery limits through policies, not through `x-` arguments hard-coded in applications.** Policies can be changed at any time for many queues at once, while hard-coded arguments need application changes and redeployment. The queue type is the exception: set it at declaration or through the default queue type. ([RabbitMQ, Dead Letter Exchanges: configuration](https://www.rabbitmq.com/docs/dlx#how-dead-lettering-is-configured), [Policies](https://www.rabbitmq.com/docs/policies#why))

### Security

- `9` `RABBITMQ-11` **Delete the default `guest` user, disable anonymous logins, and give each application its own user with only the permissions it needs.** The `guest` user has well-known credentials, and the `ANONYMOUS` mechanism, on by default, lets clients without credentials connect as `guest`. ([RabbitMQ, Production checklist: users](https://www.rabbitmq.com/docs/production-checklist#users), [Anonymous login](https://www.rabbitmq.com/docs/production-checklist#anonymous-login), [Access control: default virtual host and user](https://www.rabbitmq.com/docs/access-control#default-state), [Authentication mechanisms](https://www.rabbitmq.com/docs/access-control#available-mechanisms))
- `8` `RABBITMQ-12` **Use TLS for client connections with peer verification, and secure inter-node and CLI traffic too.** Where every client can use TLS, turn off the plain listeners. ([RabbitMQ, Production checklist: TLS](https://www.rabbitmq.com/docs/production-checklist#security-tls), [TLS Support: enabling TLS](https://www.rabbitmq.com/docs/ssl#enabling-tls), [peer verification](https://www.rabbitmq.com/docs/ssl#peer-verification), [Production checklist: inter-node authentication](https://www.rabbitmq.com/docs/production-checklist#inter-node-authentication))

### Operations

- `7` `RABBITMQ-13` **Monitor with the built-in Prometheus plugin, and alert on queue depth, unacknowledged messages, consumer counts, connection churn and resource alarms.** ([RabbitMQ, Monitoring with Prometheus-compatible tools](https://www.rabbitmq.com/docs/monitoring#with-prometheus), [Queue metrics](https://www.rabbitmq.com/docs/monitoring#queue-metrics), [Connections: high connection churn](https://www.rabbitmq.com/docs/connections#high-connection-churn), [Memory and disk alarms](https://www.rabbitmq.com/docs/alarms))
- `7` `RABBITMQ-14` **Stay on a release series that still has community support, and upgrade along the supported rolling upgrade paths, with all stable feature flags enabled first.** Community support for a series ends a few months after the next series ships. ([RabbitMQ, Release information](https://www.rabbitmq.com/release-information), [Upgrading: version upgradability](https://www.rabbitmq.com/docs/upgrade#rabbitmq-version-upgradability))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `6` [RabbitMQ Prometheus alerting rules](https://github.com/rabbitmq/cluster-operator/blob/main/observability/prometheus/rules/rabbitmq/README.md) (RabbitMQ Cluster Operator): ready-made Prometheus alerts, as Kubernetes `PrometheusRule` resources, for the metrics of the Prometheus plugin. [HighConnectionChurn](https://github.com/rabbitmq/cluster-operator/blob/main/observability/prometheus/rules/rabbitmq/high-connection-churn.yml) fires when connections are short-lived, and [UnroutableMessages](https://github.com/rabbitmq/cluster-operator/blob/main/observability/prometheus/rules/rabbitmq/unroutable-messages.yml) when messages are dropped or returned as unroutable. Partly checks `RABBITMQ-4`, `RABBITMQ-8` and `RABBITMQ-13`.
- `5` [Operator policies](https://www.rabbitmq.com/docs/policies#operator-policies) (RabbitMQ docs): limits such as `delivery-limit`, `max-length` and `overflow` that operators apply to every matching queue; when an application's policy sets the same key, the more conservative value wins. Partly checks `RABBITMQ-5` and `RABBITMQ-9`.
- `5` [`rabbitmq-diagnostics check_certificate_expiration`](https://www.rabbitmq.com/docs/man/rabbitmq-diagnostics.8#check_certificate_expiration) (RabbitMQ CLI): checks the expiry dates of the certificates on every TLS listener of a node, for example in a scheduled job. Partly checks `RABBITMQ-12`.
