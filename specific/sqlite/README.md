# SQLite

Scope: SQLite embedded in an application as its local database or file format: mobile and desktop apps, local-first data, game saves, tools, and small servers that keep the database on their own disk. The guidelines cover SQLite 3.54, the current release, and point out features that need a minimum version, because apps often use the copy of SQLite that the operating system provides. Hosted services built on SQLite, such as Cloudflare D1, aren't covered. Architecture-level data rules, such as versioned migrations and backups, are in [general/data.md](../../general/data.md) (`DATA-2`, `DATA-8`), and validating input in [general/security.md](../../general/security.md) (`SEC-10`). For save data in games, this file shows how to apply `GAMEDEV-10` and `GAMEDEV-11` from [Game development](../gamedev/README.md) in SQLite, and Steam Cloud saves are in [Steam and PC games](../steam/README.md) (`STEAM-9`). Offline-first mobile apps with a local database are covered in [Android](../android/README.md) (`ANDROID-7`) and [Flutter](../flutter/README.md), and backends that sync data to the cloud in [Firebase](../firebase/README.md) and [Supabase](../supabase/README.md). When the data lives on a server that many clients share, see [PostgreSQL](../postgres/README.md).

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Key rules

### Choosing and placing SQLite

- `8` `SQLITE-1` **Use SQLite where the data is on the same machine as the code that queries it and writers can take turns; choose a client/server database, such as PostgreSQL, when the data is on another machine, many processes must write at the same instant, or the data is heading for terabytes.** SQLite allows one writer at a time for each database file, but a write transaction usually takes only milliseconds. ([SQLite, Appropriate Uses: checklist for choosing the right database engine](https://www.sqlite.org/whentouse.html#checklist_for_choosing_the_right_database_engine), [SQLite Over a Network, Caveats and Considerations](https://www.sqlite.org/useovernet.html))
- `8` `SQLITE-2` **Never share a database between processes or machines through a network file system, such as NFS or SMB.** File locking is often broken on network file systems, which can corrupt the database, and WAL mode doesn't work over a network file system at all. ([SQLite, How To Corrupt: file systems with broken or missing lock implementations](https://www.sqlite.org/howtocorrupt.html#_filesystems_with_broken_or_missing_lock_implementations), [FAQ (5)](https://www.sqlite.org/faq.html#q5), [Write-Ahead Logging: overview](https://www.sqlite.org/wal.html#overview))

### Connections and concurrency

- `8` `SQLITE-3` **Configure every connection in one place as soon as it opens: `PRAGMA foreign_keys=ON`, a busy timeout, and `PRAGMA trusted_schema=OFF`.** These settings belong to the connection, not the database file. Foreign key enforcement is off by default, must be turned on for each connection and can't be changed inside a transaction, and the SQLite docs encourage every application to turn `trusted_schema` off. ([SQLite, Foreign Key Support: enabling foreign key support](https://www.sqlite.org/foreignkeys.html#fk_enable), [PRAGMA foreign_keys](https://www.sqlite.org/pragma.html#pragma_foreign_keys), [PRAGMA busy_timeout](https://www.sqlite.org/pragma.html#pragma_busy_timeout), [PRAGMA trusted_schema](https://www.sqlite.org/pragma.html#pragma_trusted_schema))
- `7` `SQLITE-4` **Use WAL mode (`PRAGMA journal_mode=WAL`) for databases that are read while they are written, set `PRAGMA synchronous=NORMAL` when each connection opens, and never set `synchronous=OFF` for data you need to keep.** In WAL mode, readers and the writer don't block each other, and `NORMAL` can't corrupt the database, though the last commits can be lost on a power failure; with `OFF`, a power failure can corrupt it. On Android, enable WAL through the framework rather than with the pragma; Room does so by default on devices that aren't low on RAM. ([SQLite, Write-Ahead Logging](https://www.sqlite.org/wal.html), [PRAGMA synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous), [How To Corrupt: disabling sync using pragmas](https://www.sqlite.org/howtocorrupt.html#_disabling_sync_using_pragmas), [Android, Best practices for SQLite performance](https://developer.android.com/topic/performance/sqlite-performance-best-practices))
- `7` `SQLITE-5` **Send all writes through one connection or a serial queue, start transactions that will write with `BEGIN IMMEDIATE`, and keep write transactions short.** Only one write transaction can run at a time. A transaction that starts with a read and then writes fails with `SQLITE_BUSY` if another connection has written in the meantime, and SQLite skips the busy handler when waiting could deadlock. ([SQLite, Transaction: read transactions versus write transactions](https://www.sqlite.org/lang_transaction.html#read_transactions_versus_write_transactions), [DEFERRED, IMMEDIATE, and EXCLUSIVE transactions](https://www.sqlite.org/lang_transaction.html#deferred_immediate_and_exclusive_transactions), [sqlite3_busy_handler()](https://www.sqlite.org/c3ref/busy_handler.html), [Android, Best practices for SQLite performance](https://developer.android.com/topic/performance/sqlite-performance-best-practices))

### Schema and queries

- `9` `SQLITE-6` **Bind values with SQLite's placeholders, `?` or `:name`, through the driver's parameter API, such as the second argument of Python's `execute()`.** This is how SQLite applies `SEC-18`, whose allowlist covers table and column names, which placeholders can't stand for. ([Python, sqlite3: how to use placeholders to bind values](https://docs.python.org/3/library/sqlite3.html#sqlite3-placeholders), [SQLite, Binding Values To Prepared Statements](https://www.sqlite.org/c3ref/bind_blob.html), [OWASP SQL Injection Prevention Cheat Sheet: parameterized queries](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html#parameterized-queries), [allow-list input validation](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html#allow-list-input-validation))
- `7` `SQLITE-7` **Record the schema version in `PRAGMA user_version`, and when the app opens a database, apply the missing migrations in order, each in a transaction. For changes that `ALTER TABLE` can't make, follow SQLite's 12-step procedure for rebuilding a table and finish with `PRAGMA foreign_key_check`.** This is how to apply `DATA-2`, and `GAMEDEV-10` for saves, in SQLite: `user_version` is an integer in the database header that SQLite leaves to the application. ([SQLite, PRAGMA user_version](https://www.sqlite.org/pragma.html#pragma_user_version), [ALTER TABLE: making other kinds of table schema changes](https://www.sqlite.org/lang_altertable.html#making_other_kinds_of_table_schema_changes), [Android, Best practices for SQLite performance](https://developer.android.com/topic/performance/sqlite-performance-best-practices))
- `6` `SQLITE-8` **Create new tables as `STRICT` tables once every SQLite version that opens the file is 3.37.0 or later.** In ordinary tables, column types are only advisory, so a column can quietly hold values of any type; a strict table rejects values that can't be converted losslessly, and `integrity_check` checks the types. Older versions of SQLite can't open a database that contains strict tables. ([SQLite, STRICT Tables](https://www.sqlite.org/stricttables.html), [Backwards compatibility](https://www.sqlite.org/stricttables.html#backwards_compatibility), [Quirks: flexible typing](https://www.sqlite.org/quirks.html#flexible_typing))
- `6` `SQLITE-9` **Group related writes into one explicit transaction instead of letting each statement commit on its own.** Every commit pays the full cost of syncing to disk, so batching makes bulk writes much faster and keeps related changes atomic. ([SQLite, FAQ (19)](https://www.sqlite.org/faq.html#q19), [Android, Best practices for SQLite performance](https://developer.android.com/topic/performance/sqlite-performance-best-practices))
- `5` `SQLITE-10` **Index the columns that frequent queries filter, sort or join on, including the child columns of foreign keys, check plans with `EXPLAIN QUERY PLAN`, and run `PRAGMA optimize` as SQLite recommends: before closing short-lived connections, periodically on long-lived ones, and after schema changes.** ([SQLite, Query Planning](https://www.sqlite.org/queryplanner.html), [EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html), [PRAGMA optimize](https://www.sqlite.org/pragma.html#pragma_optimize), [Foreign Key Support: required and suggested indexes](https://www.sqlite.org/foreignkeys.html#fk_indexes))

### Backups and file handling

- `8` `SQLITE-11` **Copy a live database only with the online backup API, `VACUUM INTO` or `sqlite3_rsync`, never copy the database file while a connection may be writing to it, and never delete, rename or separate it from its `-wal` or `-journal` file.** A file copied during a transaction can mix old and new content, and a database separated from its hot journal can't recover after a crash. For files that users copy or a cloud service syncs, such as game saves (`STEAM-9`), sync a copy made this way, or close every connection first: the last connection to close checkpoints and deletes the WAL file. ([SQLite, How To Corrupt: backup or restore while a transaction is active](https://www.sqlite.org/howtocorrupt.html#_backup_or_restore_while_a_transaction_is_active), [deleting a hot journal](https://www.sqlite.org/howtocorrupt.html#_deleting_a_hot_journal), [SQLite Backup API](https://www.sqlite.org/backup.html), [VACUUM INTO](https://www.sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause), [sqlite3_rsync](https://www.sqlite.org/rsync.html), [Write-Ahead Logging: the WAL file](https://www.sqlite.org/wal.html#the_wal_file))
- `6` `SQLITE-12` **Check backups and saves with `PRAGMA integrity_check`, or the faster `quick_check`, before you rely on them, and keep the previous good copy until the new one passes.** This is how to apply `GAMEDEV-11` and the restore tests of `DATA-8` in SQLite. `integrity_check` doesn't find foreign key violations; use `PRAGMA foreign_key_check` for those. ([SQLite, PRAGMA integrity_check](https://www.sqlite.org/pragma.html#pragma_integrity_check), [PRAGMA quick_check](https://www.sqlite.org/pragma.html#pragma_quick_check))

### Untrusted databases and SQL

- `6` `SQLITE-13` **Treat a database file that someone else could have written, such as a shared save, a mod or a downloaded file, as untrusted input (`SEC-10`): keep `trusted_schema` off, and in security-sensitive apps run `PRAGMA quick_check` before any other statement, reject files that fail, and set `PRAGMA cell_size_check=ON` and `PRAGMA mmap_size=0`.** SQLite is built to reject malformed files safely; these steps add defense against undiscovered bugs and against schemas that call the application's own SQL functions. ([SQLite, Defense Against The Dark Arts: untrusted SQLite database files](https://www.sqlite.org/security.html#untrusted_sqlite_database_files), [PRAGMA cell_size_check](https://www.sqlite.org/pragma.html#pragma_cell_size_check), [PRAGMA mmap_size](https://www.sqlite.org/pragma.html#pragma_mmap_size), [SQLite As An Application File Format: security considerations](https://www.sqlite.org/appfileformat.html#security_considerations))
- `5` `SQLITE-14` **If the app runs SQL written by users or mods, turn on `SQLITE_DBCONFIG_DEFENSIVE`, lower the limits with `sqlite3_limit()`, and restrict what statements may do with an authorizer callback.** The defensive flag stops ordinary SQL from deliberately corrupting the database file, for example through `PRAGMA writable_schema=ON` or `journal_mode=OFF`. ([SQLite, Defense Against The Dark Arts: untrusted SQL inputs](https://www.sqlite.org/security.html#untrusted_sql_inputs), [SQLITE_DBCONFIG_DEFENSIVE](https://www.sqlite.org/c3ref/c_dbconfig_defensive.html#sqlitedbconfigdefensive))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `6` [CodeQL, SQL query built from user-controlled sources](https://codeql.github.com/codeql-query-help/python/py-sql-injection/): code-scanning queries that trace untrusted input into SQL strings, also for [JavaScript and TypeScript](https://codeql.github.com/codeql-query-help/javascript/js-sql-injection/), [Java and Kotlin](https://codeql.github.com/codeql-query-help/java/java-sql-injection/) and [Swift](https://codeql.github.com/codeql-query-help/swift/swift-sql-injection/), whose examples use SQLite. Partly checks `SQLITE-6`.
- `6` [Ruff `hardcoded-sql-expression` (S608)](https://docs.astral.sh/ruff/rules/hardcoded-sql-expression/): flags Python strings that look like SQL and are built with formatting or concatenation. Partly checks `SQLITE-6`.
- `6` [`PRAGMA foreign_key_check`](https://www.sqlite.org/pragma.html#pragma_foreign_key_check) and [`PRAGMA integrity_check`](https://www.sqlite.org/pragma.html#pragma_integrity_check): built into SQLite; run them in tests against databases created and migrated by the app's own code, and fail the build on any result other than an empty list or `ok`. `foreign_key_check` reports rows that break foreign key constraints, such as rows written by a connection that never turned enforcement on. Partly checks `SQLITE-3` and `SQLITE-7`.
