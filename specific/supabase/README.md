# Supabase

Scope: web apps, mobile apps and games whose clients call Supabase directly, on the hosted Supabase platform (projects on Postgres 15 and 17), with the Supabase CLI 2 and `supabase-js` 2: Row Level Security and grants, API keys, Storage, Edge Functions, migrations and environments, database connections, backups and Auth settings. Because clients query the database through the Data API, Row Level Security carries the server-side authorisation that `SEC-1` asks for, and the key in the client is public (`SEC-11` in [Security](../../general/security.md)). A Supabase database is PostgreSQL, so [PostgreSQL](../postgres/README.md) applies to its schema, indexes and migrations; its rules aren't repeated here. Sign-in in general is covered in [Authentication and sessions](../../general/authentication.md), personal data in [Privacy and personal data](../../general/privacy.md), browser apps in [Web front end](../web/README.md), mobile games in [Mobile games](../mobile-games/README.md), and connecting from serverless functions in [Serverless and edge hosting](../web-hosting/README.md). For a document-database backend of the same kind, see [Firebase](../firebase/README.md).

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Key rules

### Row Level Security and grants

- `10` `SUPABASE-1` **Enable Row Level Security on every table in an exposed schema, such as `public`, and grant the `anon` and `authenticated` roles only the operations your app needs.** A table without RLS is readable and writable by any role with a grant on it, and policies don't remove grants. On existing projects, new tables in `public` get every privilege by default, so turn off "Automatically expose new tables" or revoke the default privileges. This applies `SEC-1` and `PG-15`. ([Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security), [Grants and policies](https://supabase.com/docs/guides/database/postgres/row-level-security#grants-and-policies), [Securing your API: default privileges](https://supabase.com/docs/guides/api/securing-your-api#default-privileges), [Production Checklist: security](https://supabase.com/docs/guides/deployment/going-into-prod#security))
- `9` `SUPABASE-2` **Never create `security definer` functions in an exposed schema, set `search_path = ''` on every one, and create views with `security_invoker = true` or keep them out of exposed schemas.** Both run with their owner's privileges and bypass RLS. A `security definer` function in an exposed schema can be called through the Data API, and new functions are executable by every role by default. ([Row Level Security: use security definer functions](https://supabase.com/docs/guides/database/postgres/row-level-security#use-security-definer-functions), [Views and RLS](https://supabase.com/docs/guides/database/postgres/row-level-security#views-and-rls), [Expose a view safely](https://supabase.com/docs/guides/database/postgres/row-level-security#expose-a-view-safely), [Securing your API: default privileges](https://supabase.com/docs/guides/api/securing-your-api#default-privileges))
- `8` `SUPABASE-3` **Write a separate policy for each operation, name its role with `to authenticated` or `to anon`, compare owner columns with `(select auth.uid())`, add `with check` to insert and update policies, and base authorisation on `app_metadata`, never on `user_metadata`, which users can change themselves.** ([Row Level Security: write a policy for each operation](https://supabase.com/docs/guides/database/postgres/row-level-security#write-a-policy-for-each-operation), [Specify roles in your policies](https://supabase.com/docs/guides/database/postgres/row-level-security#specify-roles-in-your-policies), [auth.jwt()](https://supabase.com/docs/guides/database/postgres/row-level-security#authjwt))
- `8` `SUPABASE-4` **Test the policies of every table with pgTAP: a test file per table under `supabase/tests` that asserts which operations each role may and may not perform, run with `supabase test db` on every pull request.** Until the tests pass, you don't know whether the policies do what you intended; test the denied cases as well as the allowed ones. ([Row Level Security: secure a table with RLS](https://supabase.com/docs/guides/database/postgres/row-level-security#secure-a-table-with-rls), [Policy tests](https://supabase.com/docs/guides/database/postgres/row-level-security#policy-tests), [Testing overview: best practices](https://supabase.com/docs/guides/local-development/testing/overview#best-practices))
- `7` `SUPABASE-5` **Index every column that policies filter on, and wrap `auth.uid()` and `auth.jwt()` in a `select` so that Postgres evaluates them once per statement instead of once per row.** This applies `PG-5` to policies. ([Row Level Security: add indexes](https://supabase.com/docs/guides/database/postgres/row-level-security#add-indexes), [Call functions with select](https://supabase.com/docs/guides/database/postgres/row-level-security#call-functions-with-select))
- `7` `SUPABASE-6` **If you enable anonymous sign-ins, check the `is_anonymous` claim in restrictive policies on data that only permanent users may reach, and protect the sign-in endpoint with CAPTCHA.** Anonymous users get the same `authenticated` role as permanent users, and bots can create them in bulk to fill your database. ([Anonymous Sign-Ins: access control](https://supabase.com/docs/guides/auth/auth-anonymous#access-control), [Abuse prevention and rate limits](https://supabase.com/docs/guides/auth/auth-anonymous#abuse-prevention-and-rate-limits))
- `7` `SUPABASE-7` **Keep Storage buckets private unless every file in them may be public, control access with policies on `storage.objects`, for example per user folder, and give temporary access to private files with signed URLs.** Anyone who has the URL of a file in a public bucket can download it. ([Storage Buckets: access model](https://supabase.com/docs/guides/storage/buckets/fundamentals#access-model), [Storage Access Control](https://supabase.com/docs/guides/storage/security/access-control#access-policies))

### Keys and Edge Functions

- `9` `SUPABASE-8` **Put only the publishable key, or the legacy `anon` key, in clients, and keep secret keys and the `service_role` key in servers and Edge Functions, out of source control.** Secret keys bypass RLS, so a leaked one exposes all of the project's data. Give each backend component its own secret key, so that one leak forces only one rotation, and move off the legacy JWT-based keys, which Supabase is deprecating by the end of 2026. This applies `SEC-11` and `SEC-2`. ([API keys: which key do you use?](https://supabase.com/docs/guides/getting-started/api-keys#which-key-do-you-use), [Handling secret keys safely](https://supabase.com/docs/guides/getting-started/api-keys#handling-secret-keys-safely), [Migrating to publishable and secret API keys](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys))
- `8` `SUPABASE-9` **Check every caller of an Edge Function: keep `verify_jwt` on for functions that users call, and query with the client that applies their RLS policies; use the admin client, which bypasses RLS, only for work that must cross policies, and verify the signature of external webhooks.** Keep third-party credentials in Edge Function secrets, and the local `supabase/functions/.env` file out of Git. ([Securing Edge Functions: authenticated user calls](https://supabase.com/docs/guides/functions/auth#authenticated-user-calls), [External webhooks](https://supabase.com/docs/guides/functions/auth#external-webhooks), [Edge Functions, Environment variables](https://supabase.com/docs/guides/functions/secrets))

### Migrations and environments

- `8` `SUPABASE-10` **Make every schema change, including RLS policies, grants and functions, a migration file in `supabase/migrations` under version control, and never change the production database directly in the dashboard.** Test migrations on the local stack and on a staging project or preview branch, and deploy them from CI or the GitHub integration rather than from a developer's machine. This applies `DATA-2` and `SEC-16`. ([Deploy database migrations: working with a team](https://supabase.com/docs/guides/deployment/database-migrations#working-with-a-team), [Row Level Security: enable RLS and set the grants](https://supabase.com/docs/guides/database/postgres/row-level-security#enable-rls-and-set-the-grants), [Managing Environments: deploy a migration](https://supabase.com/docs/guides/deployment/managing-environments#deploy-a-migration), [Branching](https://supabase.com/docs/guides/deployment/branching), [Production Checklist: deployment](https://supabase.com/docs/guides/deployment/going-into-prod#deployment))

### Connections and operations

- `8` `SUPABASE-11` **Plan backups for your recovery point objective: Supabase backs up only paid-plan projects daily, so on the Free plan export the database regularly with `supabase db dump` and keep the copies off-site, and on paid plans enable point-in-time recovery when losing up to a day of data is too much.** Database backups don't include the files in Storage, and deleting a project also deletes its backups. This is how Supabase projects follow `DATA-8`. ([Database Backups](https://supabase.com/docs/guides/platform/backups), [Point-in-Time recovery](https://supabase.com/docs/guides/platform/backups#point-in-time-recovery), [Production Checklist: availability](https://supabase.com/docs/guides/deployment/going-into-prod#availability))
- `7` `SUPABASE-12` **Connect each runtime the way Supabase recommends: clients through the Data API, serverless and edge functions through the shared pooler in transaction mode, with prepared statements off and a pool of one connection per instance, and migrations, `pg_dump` and long-running backends through a direct connection or the pooler's session mode.** This is how Supabase projects follow `PG-9` and `HOST-5`. ([Connect to your database: which connection method do you use?](https://supabase.com/docs/guides/database/connecting-to-postgres#choose-a-connection-method), [Configure your client](https://supabase.com/docs/guides/database/connecting-to-postgres#configure-your-client))
- `7` `SUPABASE-13` **Turn on SSL enforcement and network restrictions for the database.** Postgres and its poolers accept connections without SSL until you enforce it, and network restrictions limit which IP ranges can connect at all; the HTTP APIs always use TLS. This is how Supabase projects follow `SEC-13` and `PG-14`. ([Production Checklist: security](https://supabase.com/docs/guides/deployment/going-into-prod#security), [Postgres SSL Enforcement](https://supabase.com/docs/guides/platform/ssl-enforcement), [Network Restrictions](https://supabase.com/docs/guides/platform/network-restrictions))
- `6` `SUPABASE-14` **Leave the Spend Cap on, or watch the organization's usage page when it's off, so that an attack or a bug can't run up unlimited charges.** With the cap on, usage beyond the plan's quota is blocked for items such as egress, Edge Function invocations, monthly active users and storage; compute, point-in-time recovery and other add-ons you opted into aren't covered. ([Control your costs: Spend Cap](https://supabase.com/docs/guides/platform/cost-control#spend-cap))

### Auth settings

- `7` `SUPABASE-15` **Configure Supabase Auth for production: turn on email confirmations, send auth email through your own SMTP server, enable CAPTCHA on sign-up, sign-in and password reset, let one-time passwords expire within an hour, and review the rate limits.** The built-in email service sends only two emails an hour. Rate limits and CAPTCHA are how a Supabase project limits sign-in attempts (`AUTH-14`). ([Production Checklist: security](https://supabase.com/docs/guides/deployment/going-into-prod#security), [Enable CAPTCHA Protection](https://supabase.com/docs/guides/auth/auth-captcha), [Rate limits](https://supabase.com/docs/guides/auth/rate-limits))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [Supabase Advisors](https://supabase.com/docs/guides/observability/advisors): deterministic checks, based on the [splinter](https://github.com/supabase/splinter) lints, that run in the dashboard, or in CI with `supabase db advisors --fail-on error` against the local database. [`rls_disabled_in_public`](https://supabase.github.io/splinter/0013_rls_disabled_in_public/) flags exposed tables without RLS, [`rls_references_user_metadata`](https://supabase.github.io/splinter/0015_rls_references_user_metadata/) policies that read `user_metadata`, [`security_definer_view`](https://supabase.github.io/splinter/0010_security_definer_view/), [`function_search_path_mutable`](https://supabase.github.io/splinter/0011_function_search_path_mutable/) and `anon_security_definer_function_executable` views and functions that bypass RLS, [`auth_rls_initplan`](https://supabase.github.io/splinter/0003_auth_rls_initplan/) policies that call auth functions once per row, `auth_allow_anonymous_sign_ins` enabled anonymous sign-ins, and `public_bucket_allows_listing` public buckets whose files can be listed. Checks `SUPABASE-2`, and partly `SUPABASE-1`, `SUPABASE-3`, `SUPABASE-5`, `SUPABASE-6` and `SUPABASE-7`.
- `6` [`supabase test db`](https://supabase.com/docs/guides/database/testing): runs the pgTAP tests in `supabase/tests` against the local database, for example in a [GitHub Actions workflow](https://supabase.com/docs/guides/local-development/testing/overview#continuous-integration-testing) on every pull request. Checks `SUPABASE-4`, and partly `SUPABASE-1`, `SUPABASE-3`, `SUPABASE-6` and `SUPABASE-7`, as far as the tests cover them.
- `6` [GitHub secret scanning push protection](https://docs.github.com/en/code-security/reference/secret-security/supported-secret-scanning-patterns): blocks pushes that contain Supabase secret keys. Partly checks `SUPABASE-8`.
