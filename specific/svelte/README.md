# Svelte and SvelteKit

Scope: web apps built with Svelte 5 in runes mode and SvelteKit, following the current (SvelteKit 3) documentation. Framework-independent rules for accessibility, performance and security, such as WCAG, Core Web Vitals, sanitizing HTML before `{@html}` and Content Security Policy, are in [Web front end](../web/README.md). Server `load` functions, form actions, `+server.js` handlers and remote functions are backend code, so the [Node.js](../nodejs/README.md) and [Security](../../general/security.md) guidelines also apply to them.

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

## Adopted references

- `10` [Svelte documentation](https://svelte.dev/docs/svelte/overview): **the baseline for components**: runes, template syntax, styling, special elements, runtime APIs such as context and lifecycle, testing, TypeScript, and the compiler's errors and warnings.
- `10` [SvelteKit documentation](https://svelte.dev/docs/kit/introduction): **the baseline for apps**: project structure, routing, loading data, form actions, page options, state management, hooks, adapters, environment variables, server-only modules, and best practices for auth, performance and accessibility.
- `9` [Svelte, Best practices](https://svelte.dev/docs/svelte/best-practices): the official advice on `$state`, `$derived`, `$effect`, props, events, snippets, keyed each blocks, styling, context, and the legacy features to avoid.
- `8` [SvelteKit, State management](https://svelte.dev/docs/kit/state-management): avoiding shared state on the server, keeping `load` free of side effects, and keeping state in context, the URL or snapshots.
- `8` [SvelteKit, Performance](https://svelte.dev/docs/kit/performance): what SvelteKit optimizes by default, and how to diagnose issues, optimize assets, reduce code size, prevent waterfalls and choose hosting.
- `7` [SvelteKit, Accessibility](https://svelte.dev/docs/kit/accessibility): the built-in route announcements and focus management, and what each app still has to provide.
- `7` [Migrating to SvelteKit v3](https://svelte.dev/docs/kit/migrating-to-sveltekit-3): the breaking changes in SvelteKit 3, such as configuration in `vite.config.js`, the new environment variable modules, the wider server-only module rules and the CSRF settings, with an automatic migration command.

## Key rules

### Components and reactivity

- `7` `SVELTE-1` **Write new components in runes mode, and don't use legacy features that have modern replacements, such as `$:` statements, `export let`, `on:` directives, slots, and stores for shared state.** Runes mode will be the compiler's default in Svelte 6. ([Svelte, Best practices: avoid legacy features](https://svelte.dev/docs/svelte/best-practices#Avoid-legacy-features), [svelte/compiler, CompileOptions](https://svelte.dev/docs/svelte/svelte-compiler#CompileOptions))
- `7` `SVELTE-2` **Compute values from state and props with `$derived`, not by assigning state in an `$effect`, and keep `$effect` as an escape hatch for things such as analytics and direct DOM manipulation.** Handle user interaction in event handlers. A value computed once from props goes stale, because SvelteKit reuses page and layout components when the user navigates. ([Svelte, When not to use $effect](https://svelte.dev/docs/svelte/$effect#When-not-to-use-$effect), [Best practices: $props](https://svelte.dev/docs/svelte/best-practices#$props), [SvelteKit, Component and page state is preserved](https://svelte.dev/docs/kit/state-management#Component-and-page-state-is-preserved))
- `7` `SVELTE-3` **Type-check `.svelte` files in CI with `sv check` (svelte-check).** The editor extension shows the same errors while you work. ([Svelte, TypeScript](https://svelte.dev/docs/svelte/typescript), [sv check](https://svelte.dev/docs/cli/sv-check))
- `6` `SVELTE-4` **Share reactive state between components with `$state` objects or classes with `$state` fields, defined in `.svelte.js` or `.svelte.ts` modules, and keep stores for complex asynchronous streams or for when you need manual control over updates.** In server-rendered apps, provide that state through context rather than from a shared module. ([Svelte, When to use stores](https://svelte.dev/docs/svelte/stores#When-to-use-stores), [Best practices: avoid legacy features](https://svelte.dev/docs/svelte/best-practices#Avoid-legacy-features), [Best practices: context](https://svelte.dev/docs/svelte/best-practices#Context))

### Data loading and mutations

- `9` `SVELTE-5` **Never keep user or request data in module-level variables or other shared state on the server: return it from `load`, pass it down as props or through context, and persist it in a database. Keep `load` functions free of side effects for the same reason.** A server is long-lived and shared by all users, so such state leaks one user's data to the next. ([SvelteKit, Avoid shared state on the server](https://svelte.dev/docs/kit/state-management#Avoid-shared-state-on-the-server), [No side-effects in load](https://svelte.dev/docs/kit/state-management#No-side-effects-in-load), [Svelte, Context: replacing global state](https://svelte.dev/docs/svelte/context#Replacing-global-state))
- `7` `SVELTE-6` **Load data that needs the database, the filesystem or private credentials in server `load` functions (`+page.server.js`), and use universal `load` functions (`+page.js`) only for public APIs or for values that can't be serialized.** ([SvelteKit, Universal vs server: when to use which](https://svelte.dev/docs/kit/load#Universal-vs-server-When-to-use-which))
- `6` `SVELTE-7` **Avoid request waterfalls: make dependent backend calls in server `load` functions, use the `fetch` that `load` receives, and call `await parent()` only after the requests that don't depend on it.** SvelteKit runs `load` functions in parallel and inlines the responses of `load`'s `fetch` into the server-rendered HTML. ([SvelteKit, Preventing waterfalls](https://svelte.dev/docs/kit/performance#Navigation-Preventing-waterfalls), [Making fetch requests](https://svelte.dev/docs/kit/load#Making-fetch-requests), [Using parent data](https://svelte.dev/docs/kit/load#Using-parent-data))
- `6` `SVELTE-8` **Implement mutations as form actions that work without JavaScript, return validation errors with `fail()`, and progressively enhance the form with `use:enhance`.** Remote functions are an alternative, but they are still experimental. ([SvelteKit, Form actions](https://svelte.dev/docs/kit/form-actions), [Progressive enhancement](https://svelte.dev/docs/kit/form-actions#Progressive-enhancement), [Remote functions](https://svelte.dev/docs/kit/remote-functions))

### Rendering and deployment

- `7` `SVELTE-9` **Choose rendering per route with page options: prerender pages that every user sees the same, server-render dynamic pages, and turn off `ssr` only for pages that can't run on the server.** Prerendered content is shown to all users, and SPA mode adds network round trips before the first render. ([SvelteKit, Page options](https://svelte.dev/docs/kit/page-options), [When not to prerender](https://svelte.dev/docs/kit/page-options#prerender-When-not-to-prerender), [Preventing waterfalls](https://svelte.dev/docs/kit/performance#Navigation-Preventing-waterfalls))
- `5` `SVELTE-10` **Replace `adapter-auto` with the adapter for your platform once you've chosen where to deploy, and host the app in the same data center as its backend.** ([SvelteKit, Zero-config deployments](https://svelte.dev/docs/kit/adapter-auto), [Performance: hosting](https://svelte.dev/docs/kit/performance#Hosting))

### Security

- `9` `SVELTE-11` **Treat every form action, `+server.js` handler and remote function as a public HTTP endpoint: make sure an authorization check covers it, and validate its input on the server.** Give remote functions a Standard Schema for their arguments. For remote function requests, `url`, `params` and `route` in the `handle` hook describe the calling page and can be manipulated, so never base authorization on them. ([SvelteKit, Remote functions: query arguments](https://svelte.dev/docs/kit/remote-functions#query-Query-arguments), [Hooks: handle](https://svelte.dev/docs/kit/hooks#handle), [Form actions: validation errors](https://svelte.dev/docs/kit/form-actions#Anatomy-of-an-action-Validation-errors))
- `9` `SVELTE-12` **Declare environment variables in `src/env.ts`, mark one `public: true` only if its value may be public, and import secrets only from `$app/env/private`.** SvelteKit refuses to import `$app/env/private` into code that runs in the browser. The older `$env/*` modules are deprecated. ([SvelteKit, Environment variables](https://svelte.dev/docs/kit/environment-variables), [Server-only modules](https://svelte.dev/docs/kit/server-only-modules))
- `8` `SVELTE-13` **Check authentication in the `handle` hook or in each `+page.server.js` `load` function, not only in a `+layout.server.js` `load` function.** Layout `load` functions don't rerun on every request, and they run in parallel with page `load` functions. ([SvelteKit, Implications for authentication](https://svelte.dev/docs/kit/load#Implications-for-authentication), [Auth: integration points](https://svelte.dev/docs/kit/auth#Integration-points))
- `7` `SVELTE-14` **Put code that uses secrets, the database or other server-only APIs in server-only modules: files with a `server` segment in their name, such as `db.server.ts`, or files in a `server` directory.** SvelteKit then raises an error when code that runs in the browser imports them, even indirectly. ([SvelteKit, Server-only modules: your modules](https://svelte.dev/docs/kit/server-only-modules#Your-modules))

### Accessibility

- `6` `SVELTE-15` **Give every page a unique, descriptive `<title>` in `<svelte:head>`, and set the `lang` attribute in `src/app.html`.** SvelteKit announces the title to screen readers after each client-side navigation. ([SvelteKit, Route announcements](https://svelte.dev/docs/kit/accessibility#Route-announcements), [The lang attribute](https://svelte.dev/docs/kit/accessibility#The-lang-attribute))
- `6` `SVELTE-16` **Fix the compiler's accessibility warnings, and silence one with `<!-- svelte-ignore -->` only for a false positive, with a note saying why.** ([Svelte, Compiler warnings](https://svelte.dev/docs/svelte/compiler-warnings))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [sv check](https://svelte.dev/docs/cli/sv-check): runs svelte-check, which reports TypeScript errors and compiler warnings, including accessibility warnings. In CI, run it with [`--fail-on-warnings`](https://svelte.dev/docs/cli/sv-check#Options-fail-on-warnings), or turn chosen warnings into errors with [`--compiler-warnings`](https://svelte.dev/docs/cli/sv-check#Options-compiler-warnings-warnings). Checks `SVELTE-3` and `SVELTE-16`.
- `7` [Server-only module check](https://svelte.dev/docs/kit/server-only-modules#How-it-works): built into SvelteKit, which raises an error when code that runs in the browser imports `$app/env/private`, `$app/server` or a server-only module, directly or indirectly. Checks `SVELTE-14`, and partly `SVELTE-12`.
- `6` [eslint-plugin-svelte](https://sveltejs.github.io/eslint-plugin-svelte/rules/): [`svelte/prefer-writable-derived`](https://sveltejs.github.io/eslint-plugin-svelte/rules/prefer-writable-derived/) (recommended) flags `$state` that an `$effect` only keeps in sync, [`svelte/valid-compile`](https://sveltejs.github.io/eslint-plugin-svelte/rules/valid-compile/) reports compiler warnings, including accessibility warnings, as lint problems, and [`svelte/no-unused-svelte-ignore`](https://sveltejs.github.io/eslint-plugin-svelte/rules/no-unused-svelte-ignore/) flags ignore comments that no longer suppress anything. Checks `SVELTE-16`, and partly `SVELTE-2`.
- `6` [Svelte compiler `runes` option](https://svelte.dev/docs/svelte/svelte-compiler#CompileOptions): forces runes mode, so legacy syntax such as `$:` and `export let` fails to compile. Set it with a function that returns `true` only for your own files, because `true` also forces components in `node_modules` into runes mode. Partly checks `SVELTE-1`.
