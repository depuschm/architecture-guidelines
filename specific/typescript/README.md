# TypeScript

Scope: the TypeScript language and compiler setup in any TypeScript codebase, such as front ends, back ends, libraries and tools, for TypeScript 6.0 and 7.0 (the native compiler). Platform files add their own rules: [Node.js](../nodejs/README.md) covers handling promises (`NODE-2`), validating server input at runtime (`NODE-3`) and type-checking services in CI (`NODE-8`), and [React](../react/README.md), [Next.js](../nextjs/README.md), [Vue](../vue/README.md) and [Svelte](../svelte/README.md) cover their frameworks. For versioning published packages, see [general/releases.md](../../general/releases.md); for monorepo layout, see [general/repositories.md](../../general/repositories.md).

> Entries are sorted by score from 1 to 10 ([criteria](../../RANKING.md)): 9–10 start here or strongly recommended, 6–8 recommended, 1–5 further reading or conditional.

- `8` [Modules](https://www.typescriptlang.org/docs/handbook/modules/introduction.html) (TypeScript Handbook): how TypeScript models the module format and module resolution of the runtime or bundler that loads your code, with [a guide to choosing compiler options](https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html) for apps, bundlers, Node.js and libraries.
- `7` [Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) (TypeScript team, 2026): the native compiler, the defaults it adopts from TypeScript 6.0, the options it no longer supports, and running it side by side with TypeScript 6.0 for tools that need the compiler API.
- `7` [Project References](https://www.typescriptlang.org/docs/handbook/project-references.html) (TypeScript): splitting a codebase into projects that reference each other and build incrementally with `tsc --build`.
- `7` [Declaration Files](https://www.typescriptlang.org/docs/handbook/declaration-files/introduction.html) (TypeScript): writing and publishing `.d.ts` files, including [Do's and Don'ts](https://www.typescriptlang.org/docs/handbook/declaration-files/do-s-and-don-ts.html) for the types you expose.

## Key rules

### Compiler settings

- `8` `TS-1` **Keep `strict` on in every project, and don't turn off the checks it includes.** It is the default since TypeScript 6.0. TypeScript highly recommends it for libraries, because their declaration files can otherwise fail to compile in projects that use it. ([TSConfig, strict](https://www.typescriptlang.org/tsconfig/#strict), [TypeScript 7.0, new behaviors from 6.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#updates-since-5x-and-new-behaviors-from-60), [Choosing compiler options: I'm writing a library](https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html#im-writing-a-library))
- `7` `TS-2` **When another tool compiles your TypeScript, turn on `isolatedModules`, add `erasableSyntaxOnly` if that tool only strips types, and type-check with `tsc --noEmit` in CI.** Bundlers and transpilers such as Vite and esbuild compile one file at a time without type-checking, and Node.js type stripping runs only syntax it can erase, which excludes enums and parameter properties. ([TSConfig, isolatedModules](https://www.typescriptlang.org/tsconfig/#isolatedModules), [erasableSyntaxOnly](https://www.typescriptlang.org/tsconfig/#erasableSyntaxOnly), [Vite, Transpile only](https://vite.dev/guide/features#transpile-only), [esbuild, TypeScript caveats](https://esbuild.github.io/content-types/#typescript-caveats), [Node.js, Type stripping](https://nodejs.org/api/typescript.html#type-stripping))
- `6` `TS-3` **In new projects, also turn on `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`.** `strict` leaves them off. The first adds `undefined` to values read through an index signature, and the second stops code from assigning `undefined` to an optional property that doesn't allow it. Since TypeScript 5.9, `tsc --init` turns both on. ([TSConfig, noUncheckedIndexedAccess](https://www.typescriptlang.org/tsconfig/#noUncheckedIndexedAccess), [exactOptionalPropertyTypes](https://www.typescriptlang.org/tsconfig/#exactOptionalPropertyTypes), [TypeScript 5.9, Minimal and updated tsc --init](https://devblogs.microsoft.com/typescript/announcing-typescript-5-9/#minimal-and-updated-tsc---init))
- `6` `TS-4` **Remove the options that TypeScript 6.0 deprecated, such as `baseUrl`, `moduleResolution: node10`, `target: es5` and AMD or UMD output, instead of silencing the warnings with `ignoreDeprecations`.** TypeScript 7.0 rejects them, and compiling cleanly on 6.0 first makes the move to 7.0 easier. ([TypeScript 6.0, Breaking changes and deprecations](https://devblogs.microsoft.com/typescript/announcing-typescript-6-0/#breaking-changes-and-deprecations-in-typescript-60), [TypeScript 7.0, new behaviors from 6.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#updates-since-5x-and-new-behaviors-from-60))

### Modules

- `7` `TS-5` **Set `module` for the host that loads your code: `nodenext` when Node.js runs it, and `esnext` or `preserve` with `moduleResolution: bundler` when a bundler does.** TypeScript checks imports by modeling that host, so a mismatch hides import errors until runtime. ([TypeScript, Modules: Theory](https://www.typescriptlang.org/docs/handbook/modules/theory.html), [Choosing compiler options](https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html), [TSConfig, module](https://www.typescriptlang.org/tsconfig/#module))
- `7` `TS-6` **Turn on `verbatimModuleSyntax`, and import and export types with `import type` and `export type`.** The emitted JavaScript then keeps exactly the imports you wrote without a `type` modifier, so other compilers produce the same output and no import is dropped by surprise. It doesn't work when one source file is compiled to both ES modules and CommonJS. ([TSConfig, verbatimModuleSyntax](https://www.typescriptlang.org/tsconfig/#verbatimModuleSyntax), [Choosing compiler options](https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html))

### Types

- `7` `TS-7` **Don't use `any`. Use `unknown` for values whose type you don't know, and narrow them with type guards before you use them.** `any` turns off type checking, and every property you read from it is `any` too, so it spreads. Keep it for code you are migrating from JavaScript. ([TypeScript, Do's and Don'ts: any](https://www.typescriptlang.org/docs/handbook/declaration-files/do-s-and-don-ts.html#any), [Everyday Types: any](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#any), [More on Functions: unknown](https://www.typescriptlang.org/docs/handbook/2/functions.html#unknown))
- `7` `TS-8` **Type data from outside the program, such as `JSON.parse` results, `fetch` responses, storage and messages, as `unknown`, and check it at runtime before you narrow it to your own types. Don't claim its shape with an `as` assertion.** Types and type assertions are erased at compile time, so they check nothing at runtime. For server input, `NODE-3` asks for a schema library. ([TypeScript, Erased types](https://www.typescriptlang.org/docs/handbook/2/basic-types.html#erased-types), [Type assertions](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#type-assertions), [Using type predicates](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#using-type-predicates))
- `6` `TS-9` **Model a value that can be in one of several states as a discriminated union, and make `switch` statements over it exhaustive with a `never` check.** When you add a state, the compiler then reports every place that doesn't handle it. ([TypeScript, Discriminated unions](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#discriminated-unions), [Exhaustiveness checking](https://www.typescriptlang.org/docs/handbook/2/narrowing.html#exhaustiveness-checking))

### Libraries

- `6` `TS-10` **Check a library with the settings its consumers might use: `module` set to `node18` or `nodenext` rather than `moduleResolution: bundler`, `declaration` on, and the lowest `target` you support.** Code that resolves under `bundler` can fail in Node.js, while code that works in Node.js almost always works in bundlers. If you bundle the library, bundle its declaration files too. ([Choosing compiler options: I'm writing a library](https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html#im-writing-a-library))
- `6` `TS-11` **Publish declaration files with the package and point to them from `exports`: put the `types` condition first in each entry, and give the ES module and CommonJS entry points separate declaration files.** ([TypeScript, Publishing](https://www.typescriptlang.org/docs/handbook/declaration-files/publishing.html), [TypeScript 4.7, package.json exports](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-4-7.html#packagejson-exports-imports-and-self-referencing), [Modules reference, package.json "exports"](https://www.typescriptlang.org/docs/handbook/modules/reference.html#packagejson-exports))

### Large codebases

- `6` `TS-12` **Give each environment, such as browser, server, worker and tests, its own `tsconfig.json`, and connect them, and the packages of a monorepo, with project references built by `tsc --build`.** One `tsconfig.json` can describe only one set of globals and module behavior; references also speed up builds and enforce the logical separation between projects. ([Choosing compiler options: I'm writing an app](https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html#im-writing-an-app), [Project References](https://www.typescriptlang.org/docs/handbook/project-references.html), [TypeScript wiki, Performance](https://github.com/microsoft/TypeScript/wiki/Performance))
- `4` `TS-13` **Turn on `isolatedDeclarations` only when declaration emit limits your build, as in large monorepos, or when another tool generates your declaration files.** It requires explicit types on everything a module exports, and TypeScript advises adopting it case by case. ([TypeScript 5.5, Isolated declarations](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-5.html#isolated-declarations), [TypeScript 7.0, Project reference builder parallelization](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#project-reference-builder-parallelization))

## How to enforce

Tools that check the key rules above automatically, in CI, the IDE or a commit hook. "Partly" means the tool covers only some of what the rule asks.

- `7` [tsc](https://www.typescriptlang.org/docs/handbook/compiler-options.html) (the TypeScript compiler): run `tsc --noEmit` in CI, or `tsc --build` with project references. Once the options are set in `tsconfig.json`, it fails on code that breaks them, and TypeScript 7.0 fails on options deprecated in 6.0. It can't tell whether an option is missing. Checks `TS-4`, and partly `TS-1`, `TS-2`, `TS-3` and `TS-6`.
- `7` [typescript-eslint `no-explicit-any`](https://typescript-eslint.io/rules/no-explicit-any/) and the `no-unsafe-*` rules, such as [`no-unsafe-assignment`](https://typescript-eslint.io/rules/no-unsafe-assignment/) and [`no-unsafe-member-access`](https://typescript-eslint.io/rules/no-unsafe-member-access/): flag explicit `any`, and values of type `any`, such as an unchecked `JSON.parse` result, that are assigned, called, returned or passed on. The first is in `recommended`, the others in `recommended-type-checked`. The opt-in [`no-unsafe-type-assertion`](https://typescript-eslint.io/rules/no-unsafe-type-assertion/) flags `as` assertions that narrow a type. typescript-eslint [supports TypeScript up to 6.0](https://typescript-eslint.io/users/dependency-versions/), so with TypeScript 7 [install TypeScript 6 side by side](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-60). Checks `TS-7`, and partly `TS-8`.
- `7` [typescript-eslint `switch-exhaustiveness-check`](https://typescript-eslint.io/rules/switch-exhaustiveness-check/): a type-aware rule, not in the shared configs, that reports a `switch` over a union of literal types or an enum that misses a case and has no `default`. Checks `TS-9`.
- `6` [arethetypeswrong CLI](https://github.com/arethetypeswrong/arethetypeswrong.github.io/blob/main/packages/cli/README.md): `attw --pack .` packs the library and checks how its types resolve under `node10`, `node16` and `bundler` resolution, reporting problems such as missing types, types that masquerade as ES modules or CommonJS, and wrong default exports. Choose a `--profile`, such as `node16` or `esm-only`, for the environments you support. Checks `TS-11`, and partly `TS-10`.
- `6` [publint rules](https://publint.dev/rules): lints `package.json` against the files you publish, for example [`EXPORTS_TYPES_SHOULD_BE_FIRST`](https://publint.dev/rules#exports_types_should_be_first) and [`EXPORTS_TYPES_INVALID_FORMAT`](https://publint.dev/rules#exports_types_invalid_format). The CLI's [`--strict`](https://publint.dev/docs/cli) option reports warnings as errors. Partly checks `TS-11`.
